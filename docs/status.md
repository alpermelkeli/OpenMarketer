What is built, how it was checked, and where the code differs from the [design report](design-report/report.pdf). The report describes the whole design; this page describes the repository as it is. Last updated 2026-10-14.

Four things run (five with the benchmark, `make evaluate`, described [below](#golden-repository-evaluation)): the command line, end to end; the API, which registers a repository, hands its analysis to the worker and reads, edits and approves the resulting profile; the worker, which executes the analysis as a Temporal workflow; and the dashboard, where a person does all of that in a browser. How one analysis runs end to end through the last three is drawn in [analysis-flow.png](analysis-flow.png) (source: `analysis-flow.html`): the path of a run from the click in the dashboard to the stored draft profile, with the file and function behind each step. The drawing was not redrawn when credentials began to be resolved at each attempt: nothing it shows became untrue, but it does not show that the two graph steps resolve the model provider's key for the run's workspace before the graph runs, or that the clone resolves the repository tokens (see [Stored credentials](#stored-credentials)). The command line first:

```bash
make analyze repo=https://github.com/owner/name
```

It clones the repository, scans and redacts secrets, runs the extractors, lets the analyzer agent explore the files, and prints a draft Product Profile as JSON. Nothing is published, and nothing is stored unless the run is started with `save=1` (next section). The profile is a draft: no person has reviewed it.

### Storing a run

`make analyze repo=... save=1` passes `--save` to `openmarketer analyze`, which writes the run to PostgreSQL after the profile has been printed (or written with `--out`). It needs the dev stack, a migrated database, and a `DATABASE_URL` in `.env` that points at it. For the dev stack that is `postgresql+psycopg://openmarketer:openmarketer@localhost:5433/openmarketer`; the value in `.env.example` uses the host name of the compose network and does not work from the host.

```bash
make up          # start PostgreSQL (and the rest of the dev stack)
make migrate     # create the tables
make analyze repo=https://github.com/owner/name save=1
```

The database is checked before the repository is cloned, so a missing `DATABASE_URL` or an unreachable or unmigrated database ends the command before any model call is made.

The database check also creates a workspace called `local` if there is none; it stands in for a user account in single-user mode. One saved run then writes, in a single transaction:

- a `project` row in that workspace for the repository, the first time that repository is saved. It is named after the product in the profile and keeps that name if a later profile names the product differently;
- a `repo_snapshot` row: the commit and the branch that were analysed;
- one `evidence` row per extractor fact: extractor, kind, value, file and lines;
- a `product_profile` row holding the profile as JSON, with status `draft` and a version one higher than the project's highest so far. Saving the same repository again adds a snapshot and version 2; it does not replace version 1.

To look at what was stored, open a shell in the dev database with `make psql`:

```sql
-- Every stored profile version, newest first, with the commit it was drafted from
SELECT p.name, p.source_repo_url, s.commit_sha, s.ref, pp.version, pp.status, pp.created_at
FROM product_profile pp
JOIN project p ON p.id = pp.project_id
LEFT JOIN repo_snapshot s ON s.id = pp.snapshot_id
ORDER BY pp.created_at DESC;

-- The extractor facts of the most recent snapshot
SELECT extractor, kind, file, start_line, value
FROM evidence
WHERE snapshot_id = (SELECT id FROM repo_snapshot ORDER BY created_at DESC LIMIT 1)
ORDER BY extractor, kind;

-- One section of the most recent profile
SELECT jsonb_pretty(content -> 'product') FROM product_profile ORDER BY created_at DESC LIMIT 1;
```

What storing a run does not do yet:

- **No approval.** Every profile stored by a run is a draft. A version is approved by a person in the dashboard, through the API (`approveProfileVersion`, see [The API](#the-api)); no command does it.
- **What the analyzer read is not stored.** The `evidence` table holds the extractor facts only, which the analyzer receives as hints. The evidence behind each claim in the profile (file and lines) is stored inside the profile JSON, not as rows, and the analyzer's tool calls are not stored at all.
- **A project is matched by the exact repository URL.** `https://host/a/b` and `https://host/a/b.git` become two projects, and so does the same repository analysed once from its URL and once from a local folder (stored as a `file://` URL).
- **No workspace isolation in the database.** Queries are scoped to a workspace in code. The database has one application role, and no table has a row-level security policy (see the differences below).
- **A project stored by the command line cannot be analysed from the dashboard.** It is listed there and its profile can be reviewed, but a project stored from a local folder has a `file://` repository, which the API does not clone; the dashboard says so, shows the address as text and builds no evidence links for it.

If saving fails after the analysis, the profile has already been printed or written, and the command exits with an error saying it was not stored.

### Profile versions and approval

`db/profile_versions.py` holds the database side of reviewing a profile. The API's profile routes call it.

- `save_edited_profile` stores an edited profile as a new draft with the project's next version number. The version that was edited is left as it is; the new row keeps its snapshot and records it in `edited_from_id`.
- `approve_profile_version` marks one version as approved, with the approver's user id and the database's time. Approving a version a second time raises `ProfileAlreadyApproved`.
- `latest_approved_profile` and `latest_draft_profile` return the approved version, or the draft, with the highest version number, or nothing. The latest draft can be older than the latest approved version; the caller compares the numbers.

Each function takes a workspace and a project, and a project of another workspace is treated like one that does not exist. They return a `ProfileVersion` holding the validated `ProductProfile`, not a database row.

The database enforces the rules itself, so they also hold for `INSERT`, `UPDATE` and `DELETE` statements written by hand:

- a trigger on `product_profile` accepts a new row only as a draft, so a version becomes approved only by an update of a stored draft;
- the same trigger lets an update of a draft change `status`, `approved_by` and `approved_at` and nothing else: not the content, the version number, the project, the snapshot or the creation time. It compares whole rows, so a column added later is frozen too unless the trigger is changed;
- it refuses every update of an approved row, and every deletion, draft or approved. A version number is therefore never used twice, and approving "version 2" always approves the content that was stored as version 2;
- a CHECK constraint requires an approved row to have both `approved_by` and `approved_at`, and a draft to have neither.

A consequence: a project that has profile versions cannot be deleted with plain SQL, because its versions cannot be. Removing a project will need a deliberate, privileged path when that feature is built.

What this does not do:

- **No command.** The API routes edit and approve a profile and the dashboard uses them; no CLI command does.
- **The approver is not checked.** There is no user table; `approved_by` is whatever id the caller passes. The API passes the one local user (see [The API](#the-api)).
- **No rule about which version may be approved.** An older draft can be approved after a newer version; "latest approved" follows the version number, not the time of approval.
- **`TRUNCATE` is not stopped, and the trigger can be removed.** Row triggers do not fire for `TRUNCATE`, and the owner of the table can disable or drop the trigger. Downgrading the migration does exactly that: while a database is downgraded nothing protects its versions, and a later upgrade cannot tell whether approved content was rewritten in between.
- **An approved row without an approver stops the upgrade.** The first revision allowed one, though no code wrote it. The migration refuses rather than guess; its docstring says how to repair the row.
- **Writes are serialised only under READ COMMITTED**, PostgreSQL's default. Under a stricter isolation level a write that had to wait fails on the unique constraint instead of taking the next version number.
- **A version says where it comes from in words a person can read.** `ProfileVersion` carries `edited_from_version` (a version number; none for a version stored by an analysis) and `commit_sha` (the analysed commit; an edit keeps the commit of the version it was made from) beside the row ids. Both come with the statement that reads the version, through two outer joins, so no function makes a second query for them.
- **The list of versions never reads a profile.** `list_profile_versions` selects the columns of a `ProfileVersionSummary` and not `content`, which can be large; a test reads the SQL that was sent and fails if the column is named. `profile_version` reads one version by its number.

### The API

`make api` serves the API on `http://127.0.0.1:8000`. It needs the dev stack, a migrated database and `DATABASE_URL` in `.env`, like a stored run. An analysis also needs `make worker` running: the API stores the run and starts its workflow, the worker executes it. So, to analyse a repository through the API: `make up`, `make migrate`, `make worker` and `make api`. The API itself clones nothing, calls no model and uses no credential: of the three it can store (see [Stored credentials](#stored-credentials)) it looks at whether the environment sets each, encrypts a value it is given, and never decrypts one. `ENCRYPTION_KEY` is optional: without it the API starts and stores no credential, and with one that is not 32 bytes in base64 it refuses to start, saying what to set and not repeating the key.

The API finds Temporal through `TEMPORAL_ADDRESS` and `TEMPORAL_NAMESPACE`, read the same way as by the worker (`WorkflowServer` in core's `workflow_server.py`): empty means `localhost:7233` and `default`. It does not connect when it starts. The first analysis that is started, or the first decision on a proposal, connects, and the connection is kept; so the API starts without Temporal, and projects, run status, profile review and proposals work without it (a decision is then stored, and its run reads it later: see [Policy gate](#policy-gate)).

Every profile response (`ProfileVersionResponse`) names the version it was edited from (`edited_from_version`, null for a version an analysis stored) and the commit that was analysed (`commit_sha`); no response carries the row id of a version or a snapshot.

The four lists are paged the same way. A request takes `limit` (1 to 100, 50 when left out) and `cursor`; the answer holds its items under a named key (`projects`, `runs`, `versions`, `proposals`) and `next_cursor`, which is null on the last page and otherwise the `cursor` of the next request. A cursor is the position of the last item returned (creation time and id for projects and runs, the version number for versions), so the next page starts after that item whatever was added in between: a row added between two requests neither repeats an item nor hides one. A walk that has begun does not see a row added at the head; reading from the start again does. A client passes a cursor back unchanged and never builds one; a value the API did not write is a 422. The orderings and queries are in the stores (`db/pages.py` and the three store modules), the query parameters in `apps/api/src/openmarketer_api/pagination.py`.

A project or a list asked for under another workspace is answered exactly like one that does not exist: `project_not_found` for a project and for the two lists under it, `profile_not_found` for a version, as for the draft and the approved profile.

Errors have one shape, `{"code": ..., "message": ...}`, except request validation, which is FastAPI's 422. A conflict over an existing project adds `existing_project_id`; the field is left out of every other error, never null. On the three credential routes a 422 does not quote the request, because the request holds a secret: FastAPI's answer repeats what was sent (`input`, `ctx`, and the name a client gave an unexpected field), so there each error keeps its `type`, its `msg` and a `loc` made only of names the API defines (`secret_bodies.py`, a route class set on that router; every other route keeps FastAPI's answer). A credential's name in the path has a fixed form (a lower-case letter, then up to 63 lower-case letters, digits or underscores), so a secret pasted there by mistake is a 422 that does not repeat it, or, if it happens to have that form, a 404 that does not repeat it either. The error the route class raises does not lead back to FastAPI's original, which holds the body. A value that breaks core's rule is answered in the same shape, beside `body.value`, with the rule and never the value. The contract is `apps/api/openapi.json`: `make openapi` writes it without starting the server, and a test fails when the committed file no longer matches the routes. The dashboard's types are generated from it (`pnpm api:types` in `apps/web`), and a check in `make lint` and CI fails when they are stale.

When the workflow of a run cannot be started (Temporal unreachable within 5 seconds, or refusing), the run that was just stored is marked `failed` with the text "the analysis could not be handed to a worker", and the request is answered 503 with the code `analysis_not_started` and the run's id in the message. The failed run does not block the project: the client starts a new one. The order is fixed in `request_analysis` (`repository_analysis/request.py`): the run is committed first, so the worker finds the row; then the workflow is started. A workflow that already exists for the run counts as started.

What the API does not do yet:

- **The lists of projects and of runs sort every row of the workspace or of the project to return one page.** `project` is indexed on `workspace_id` and `analysis_run` on `project_id`, neither on the creation time, so a page costs a read of all the workspace's projects, or all the project's runs, and a top-N sort. That is nothing at the sizes of a single-user installation; an index on `(workspace_id, created_at DESC, id DESC)` and one on `(project_id, created_at DESC, id DESC)` would make a page cost a page, and they need a migration that has not been written. The list of versions reads only its page, backwards through the unique index on `(project_id, version)`.
- **A list has no total and no filter.** A client learns that more follows, not how much; runs cannot be filtered by status.
- **There is no login.** The user is whoever is at this machine: a request is served only if it comes from a loopback address, carries exactly one `Host` header that is `localhost`, `127.0.0.1` or `[::1]` with an optional numeric port, and, when a browser sent an `Origin`, every such header is `http://` or `https://` followed by one of those. Both headers are matched whole, not parsed: a missing, repeated or malformed `Host` (`localhost@evil.example`, `localhost#.evil.example`) and a malformed `Origin` are refused. Everything else gets 403. The server binds to `127.0.0.1`. Do not put it behind a proxy or bind it to another address: a proxy on the same machine makes every request look local. Approvals are recorded under one fixed identifier for the local user (`LOCAL_USER_ID` in `identity.py`); it never comes from the request. The credential routes raise the stakes of this: any process on this machine can `PUT` or `DELETE` a credential on `127.0.0.1:8000` directly, a replaced model key routes every later analysis's repository content through another account, and who stored a value is recorded as the same fixed user (see [Stored credentials](#stored-credentials)).
- **A run cannot be cancelled through the API**, and nothing times out a run whose workflow is lost; the cases are listed under [The worker](#the-worker).
- **A start can be answered 503 although a workflow was started.** If Temporal starts the workflow but its answer does not arrive within 10 seconds, the run is marked failed; the worker then finds a finished run and does not analyse it.
- **Any https host is cloned from**, including hosts on the local network. That is acceptable while only the local user can call the API and has to be decided before it is exposed.
- **A browser on another origin is not served.** There is no CORS configuration; the dashboard calls the API through its own server (see [The dashboard](#the-dashboard)).

### The dashboard

`make web` serves the dashboard on `http://localhost:3000` (Next.js 16, `apps/web`). It needs `make api`, and `make worker` for an analysis. Everything it shows comes from the API; nothing is kept in the browser. Five screens:

| Screen | Address | What it does |
|---|---|---|
| Projects | `/` | Every project of the workspace from `listProjects`, newest first, with "load more". Each row says where the project stands, from the summary fields: an analysis in progress, a draft that awaits review (a draft newer than what is approved), the approved version, or "not analysed yet". An empty state explains the three steps. "New project" takes a name and an https repository URL and shows the API's validation, refusal and conflict messages beside the fields; on a conflict it links to the existing project (`existing_project_id`) |
| Analyses | `/projects/{id}/analyses` | Starts an analysis and shows the project's runs from `listAnalyses`, newest first, with "load more". An unfinished run is polled every two seconds until it has finished, so a run in progress is there, and followed, after a reload or from another browser; a finished run is not asked for again. Each run shows its status, the time it took, the failure text, or the profile version it stored with a link that opens that version. A 409 points at the run in progress in the list; 503 `analysis_not_started` is explained in words; a run queued for 20 seconds says that no worker may be running. For a repository that is not `https://` the screen says before any click that the API will refuse it |
| Profile review | `/projects/{id}/profile`, `?version=N` for one version | One version at a time, read with `getProfileVersion`: the one in the address, or else the draft that awaits review, or else the latest approved version. Above it, the latest draft and the latest approved version as two cards, and the version history from `listProfileVersions` (status, created and approved times, the version it was edited from, the short commit), each opening that version. The state of what is shown is said in a band that stays in view: dashed and amber for a draft, solid green with a lock for an approved version. Then where the version comes from (an analysis, or an edit of which version) and, for an edit, which parts differ from its parent; then "Needs your attention"; then every section and feature with its confidence and evidence. "Edit" changes a working copy of the version shown and saves it as a new draft through `saveProfileEdit`; "Approve" asks for confirmation, says that approval is permanent, warns when a newer version is already approved, and calls `approveProfileVersion` |
| Approvals | `/projects/{id}/approvals` | The project's proposals from `listProposals` (see [Policy gate](#policy-gate)): first those waiting for a decision, each with its action, what it does (publishes, spends money), exactly what the agent asks (the payload as indented JSON, shown as text), and how long is left before it expires; then those decided. "Approve" and "Reject" each ask for confirmation, saying what follows, and call `approveProposal` or `rejectProposal`; a refusal (decided elsewhere, expired) is said in the dialog. The project's tab counts the proposals waiting among those loaded |
| Settings | `/settings`, which opens its first section, `/settings/credentials` | A menu of sections beside the open one, a row above it on a narrow screen. There is one section, Credentials; the link to Settings is the last entry of the sidebar. Each credential from `listCredentials` shows what it is for, where its value comes from ("Not set", "Set here", "Set by the environment") and, for a stored value, how long ago it was stored. A password field saves a first value or replaces the stored one through `setCredential`; "Remove" asks for confirmation, says what stops working and that the value cannot be recovered, and calls `removeCredential`. A value is never shown. A credential the environment sets has no field; a value stored for it earlier is said to be kept and ignored, and can be removed. While the API has no `ENCRYPTION_KEY` (`can_store` false) the fields are disabled and a notice says how to generate a key. A refused value is explained beside the field in the API's words, and a conflict or an unreachable API in the row. What each credential is called and is for is the dashboard's own wording (`src/lib/settings/credential-labels.ts`); a credential the API lists and the dashboard does not know is shown by its name |

How it is put together:

- **Types come from the contract.** `pnpm api:types` writes `src/lib/api/schema.d.ts` from `apps/api/openapi.json` (`make openapi` runs it too), and `pnpm api:types:check`, part of `make lint` and of the web job in CI, fails when the file is stale. `src/lib/api/types.ts` only gives the generated schemas short names. Requests go through `openapi-fetch` and TanStack Query hooks in `src/lib/api/`; the three lists are infinite queries that ask for 20 items at a time and merge the pages, showing an item once if a new arrival moved it onto the next page.
- **The browser never calls the API.** It calls the dashboard's own route handler, `src/app/api/v1/[...path]/route.ts`, which forwards to the API from the server (`OPENMARKETER_API_URL`, default `http://127.0.0.1:8000`). The rules are in `src/lib/server/api-proxy.ts`:
  - the `Host` header must name this machine, so a foreign name pointed at 127.0.0.1 is refused;
  - `Sec-Fetch-Site`, when the browser sends it, must be `same-origin` (or `none` for a read);
  - `Origin`, when present, must be the dashboard's own origin, and every request that is not a `GET` (a `POST`, a `PUT`, a `DELETE`) must carry it. This replaces the API's own `Origin` check, which a server-side proxy hides from the API: a page of another site that posts to `/api/v1/projects/{id}/profile/versions/{n}/approval` is answered 403 here and nothing is forwarded;
  - only the sixteen method-and-path pairs the dashboard uses are forwarded (eight reads, eight writes: six `POST`, one `PUT`, one `DELETE`), matched whole with a UUID for each identifier, digits for the version and the fixed form of a credential's name; `getDraftProfile` and `getApprovedProfile` are not among them, because the dashboard no longer uses them;
  - the four lists take `limit` (1 to 100) and `cursor` (up to 200 URL-safe characters), each once. Any other query parameter, a value outside those forms, and any query on another route is refused with 400 rather than dropped, so a caller learns it had no effect. A cursor of the right form that the API did not issue is the API's 422;
  - the upstream address is built from the configured origin, the matched path and the two validated parameters, never from the incoming URL, and no cookie or browser header travels upstream;
  - a body must be `application/json` and at most 1 MB, and a `DELETE` that carries one is refused with 400. A body can hold a secret (a credential being stored): it is passed on to the API and nowhere else, and the proxy neither logs it nor puts it in an answer.
- **A typed secret does not stay in the query cache.** TanStack Query keeps the variables of a mutation for as long as it keeps the mutation. `setCredential` is therefore given a `OneTimeValue` (`src/lib/api/one-time-value.ts`), a holder the request empties, and the finished mutation is dropped at once (`gcTime: 0`); the field is cleared after a save. It is not encryption, and the value is in the page's memory while it is being typed. The field is marked for password managers to leave alone; whether they do was not tried.
- **The dashboard listens on 127.0.0.1 only** (`next dev` and `next start` default to all interfaces; the scripts pass `--hostname 127.0.0.1`), and every page is sent with `frame-ancestors 'none'`, so another site cannot put the approve button in a frame.
- **Profile text is shown as text.** Nothing from a profile, a project or a run is rendered as HTML or Markdown or turned into a link automatically. A repository URL is a link only when it is `https://`; anything else, such as the `file://` address of a project stored by the command line, is text. An evidence reference becomes a link only for a repository on github.com, gitlab.com or bitbucket.org, built from a fixed origin and encoded path segments (`src/lib/profile/evidence-link.ts`). With the version's `commit_sha` it is a permalink to the file at the analysed commit; the value is used only if it is a full hexadecimal commit id. Without one the link points at the default branch as it is today, and the screen says which of the two applies. A palette colour reaches a style only if it is a six-digit hex colour.
- **Design tokens are in one file**, `src/app/globals.css`: colour (light and dark, following the system setting), type scale, radius, layout measures and motion, as Tailwind 4 theme variables.

What the dashboard does not do:

- **The comparison between versions is a list, not a diff.** For a version that was edited from another, the screen names what differs from that parent: the values the dashboard can edit by name ("Status of sync", "Product name"), anything else by its part ("Measurement", "Evidence or confidence of sync"), and features added or removed. It does not show the old and the new text, and it compares with the parent only, not any two versions.
- **"Needs your attention" is a reading aid, decided in the browser.** A part is listed when a feature's status is `unknown`, when it cites no evidence, or when its confidence is below 0.6 (`src/lib/profile/confidence.ts`). Nothing is blocked or allowed by it. If the product defines what needs review, the API should say so and the dashboard should display it. The same holds for "a draft awaits review", which the dashboard takes to mean a draft newer than the approved version.
- **Editing covers part of the profile.** The product name, a feature's description and status, the brand voice, the primary audience and the business model type can be changed. Lists (platforms, pains, palette), evidence, confidence, and adding or removing a feature cannot.
- **A list is refreshed when something is done, not by itself.** Only an unfinished run is polled. A project created, a run started, a version approved or a proposal stored somewhere else appears on the next visit, when the window is focused again, or on reload. The sidebar names the eight most recent projects of what the list has loaded.
- **An earlier version of the dashboard kept a list in the browser's local storage** (key `openmarketer.dashboard.remembered.v1`). Nothing reads or removes it now; it is inert.
- **No light/dark switch** (it follows the system), no sign-in, no cancelling of a run, no project deletion or renaming, no search or filter in a list (the Approvals screen splits what it has loaded by status, in the browser, because the proxy forwards no `status` filter).

### Analysis runs

The design runs an analysis in a Temporal workflow that the API starts. `db/analysis_runs.py` and the `analysis_run` table hold the state of such a run, so the API and the worker share it and it survives a restart of either. The API requests a run and reads its status; the worker reports to it.

- `request_analysis_run` adds a `queued` run for a project. A project has at most one unfinished run (a partial unique index); a second request raises `AnalysisAlreadyRunning`, so a repeated request does not pay for the model twice.
- `mark_run_started`, `mark_run_succeeded` and `mark_run_failed` are what the worker reports. A run only moves forwards: `queued` to `running` to `succeeded`, or `queued` or `running` to `failed`. A report that repeats what is already recorded changes nothing, because Temporal can deliver an activity twice. A finished run is never changed (`AnalysisRunFinished`), and a run that was never started cannot succeed (`AnalysisRunNotStarted`).
- `analysis_run` reads one run: status, times, the failure message, and for a succeeded run the profile version it stored and that version's snapshot.
- `run_to_execute` gives a run's project and workspace from the run id alone, or nothing. It is the one read that is not scoped by a workspace, because it is what finds the scope: the worker's graph is handed a run by its kind and id, and everything it then does with the run goes through the scoped functions with what this returns. It says nothing else of the run and changes nothing.
- `save_analysis_of_project` in the evidence store stores a run's snapshot, evidence and draft profile under a project given by id, where the command line's `save_analysis` finds or creates the project by repository URL. The worker stores the result and reports the success in one transaction.

Every other function takes the workspace, the project and the run, including those the worker calls; a run of another workspace or project is treated like one that does not exist, and a project the workspace does not have is `ProjectNotFound` from `db/projects.py`. CHECK constraints keep a row consistent: a profile version if and only if the run succeeded, an error if and only if it failed, an end time if and only if it is finished, a start time once it is running. A foreign key over both columns makes the profile version belong to the run's project.

What this does not do:

- **No workflow id is stored.** The caller derives it from the run id (`analysis_workflow_id`).
- **Nothing here times a run out.** The workflow reports the failure; the cases in which it cannot are listed under [The worker](#the-worker).
- **Runs are never deleted.** There is no clean-up and no way to cancel.
- **The failure message is stored as given**, cut to 2000 characters. What may be written there is the caller's decision; the worker's is described below.
- **A finished row is protected in code only.** Unlike profile versions there is no trigger, so SQL written by hand can rewrite a finished run within what the CHECK constraints allow.
- **The snapshot's repository is not compared with the project's** when a result is stored under a project id.
- **The list sorts all runs of the project.** `list_analysis_runs` returns a page of a project's runs, newest first, with the profile version of each succeeded run from the same statement; no index covers the ordering (see [The API](#the-api)).
- **No access token.** The token for a private repository does not pass through these functions and is not part of a run's row. One stored from the dashboard is in the `credential` table, encrypted (see [Stored credentials](#stored-credentials)).

### The worker

`make worker` runs a Temporal worker (`python -m openmarketer_worker`) that executes one workflow, `AnalyzeRepository`, on the task queue `openmarketer-analysis`. It needs the dev stack, a migrated database, and in `.env`: `DATABASE_URL`, and `TEMPORAL_ADDRESS` set to `localhost:7233` or left empty (the value in `.env.example`, `temporal:7233`, is the host name inside the compose network and does not resolve from the host, like the one in `DATABASE_URL`). The worker refuses to start, with the name of the setting, when one of these is missing or wrong or Temporal cannot be reached, and when `DATABASE_URL` is not the URL of a PostgreSQL database, which the checkpoints need, or carries an option the PostgreSQL driver does not accept; the message names the problem and does not repeat the URL. It also refuses to start when the model configuration cannot be read, when `GITLAB_HOST` is not a host name, when `ENCRYPTION_KEY` is set and is not 32 bytes in base64 (the message says what to set and does not repeat the key), and when the folder for the runs' clones (below) exists and is not a folder of the user the worker runs as.

**The worker reads no credential when it starts.** Until this change it asked for the model provider's key at start-up and stopped without one, and it read the repository tokens once, then. It now starts without `OPENROUTER_API_KEY`: the key is resolved for the run's workspace when an attempt at a graph step begins, and the repository tokens each time a clone or a fetch is made, from the environment or from what was stored in the dashboard (`credentials.py` at the top level of the worker; see [Stored credentials](#stored-credentials)). A run that finds no key ends `failed` at its first step, before anything is cloned, with a sentence that says where to set one. `ENCRYPTION_KEY` is optional; without it a stored credential cannot be read, which the run that needs it is told.

What the API and the worker share is in `openmarketer_core/repository_analysis/workflow_contract.py`, which imports nothing from Temporal: the workflow name, the task queue, `analysis_workflow_id(run_id)`, the kind of run (`analysis-run`, which the analyzer's agent is declared with and a run's thread name starts with) and the workflow's input, `AnalyzeRepositoryInput` (workspace, project and run identifiers). Temporal keeps every input and result in the workflow history, readable in its UI, so nothing else travels through it: no repository URL, no token, no profile. The worker reads the repository URL from the database.

The analyzer is an agent on the [agent runtime](#agent-runtime), and `AnalyzeRepository` is that agent's workflow with two hooks of its own (`repository_analyzer/workflow.py`, 84 lines). An analysis is five activities in a row, or six when it fails. The middle three are the runtime's; what they do for an analysis is in `repository_analyzer/analysis.py`:

| Activity | What it does | One attempt may take | Attempts |
|---|---|---|---|
| `start_run` (hook `before`) | `mark_run_started`; returns the limits of a graph step, which the workflow cannot read from the environment itself | 30 s | 5, half a second apart at first. A run that is not found is tried again, because the request that created it may not have committed yet |
| `run_graph_step`, first | Takes the run's thread, reads the run's project and workspace by the run id (`run_to_execute` in `db/analysis_runs.py`) and starts the graph. Its first node, `clone`, asks for the action `clone_repository` with the run's three identifiers, and the graph pauses. Nothing is cloned and no model is called, but the attempt's chat model is made first, which resolves the model provider's key for the run's workspace: a run with no key ends here | 30 min (`ANALYSIS_TIMEOUT_MINUTES`); a heartbeat every 20 s, missed for 60 s, ends the attempt | 5 (`ANALYSIS_MAX_ATTEMPTS`), waiting 1, 2, 4 and 8 minutes between them |
| `run_action` for `clone_repository` | Reads the project's URL, resolves the repository tokens of the run's workspace if a clone is really made, clones into the run's folder on this worker's disk, scans and redacts it (intake), and returns `{"commit_sha": ...}` and nothing else | 15 min; a heartbeat every 20 s, missed for 60 s, ends the attempt | 5, waiting 1, 2, 4 and 8 minutes. These are constants declared on the action in core (`analyzer_agent/definitions.py`), not settings |
| `run_graph_step`, second | Continues the graph with the outcome of the clone: keeps the commit in the graph's state, runs the extractors and builds the repository map (`prepare`), runs the loop of model calls and tool calls until a profile is accepted, then stores the result (`save_analysis_of_project`) and marks the run succeeded in one transaction (`AnalysisWork.finish`). Returns `{"profile_id": ...}` | as the first | as the first |
| `record_failure` (hook `failed`) | `mark_run_failed` with the reason. Runs whenever anything above ends without a result, also on a timeout and on cancellation | 30 s | Until it works, for up to an hour |
| `forget_run` | Removes the run's checkpoints and then the run's clone from this worker's disk. Runs last in every case: after success, after `record_failure`, after a cancellation | 30 s | Until it works, for up to an hour; it does not fail for a database that is down |

The activity `analyse_and_store`, which did all of the middle three in one attempt, no longer exists.

**The commit is pinned for the life of a run.** The clone happens once, and the commit it read is in the graph's state, which is checkpointed. Every later attempt reads that commit, whatever the repository's branch has become since, so the analyzer's limits (`max_steps`, `max_cost_usd`, `max_submissions`) hold for the whole run and another attempt pays for at most the one model call that was in flight. Before this change each attempt cloned the default branch again and an analysis started over, with its budget, when it found a new commit; that case no longer exists.

**Which limit is which.** `ANALYSIS_TIMEOUT_MINUTES` and `ANALYSIS_MAX_ATTEMPTS` limit each of the two graph steps separately, not the run: with the defaults a run can make up to five attempts of thirty minutes at the first step and five more at the second. The first step does almost nothing, so in practice the numbers bound the model's work. The clone's limits are the constants in the table. The reasons for every number are in the docstring of `repository_analyzer/policy.py` and beside the constants in `definitions.py`. The worker keeps everything of the repository analyzer in `repository_analyzer/`, and above it only the process (`main.py`), its own settings (`settings.py`, which hold `ENCRYPTION_KEY`), the schedule of checkpoint cleanups and what every agent shares: `agent_runtime/` and `credentials.py`, which resolves the installation's credentials for a run's workspace.

**What is tried again.** The retries are for what can pass: a worker that died or was restarted, a model provider that did not answer, timed out (HTTP 408), limited the rate (429) or failed (5xx), a database that was unreachable, and an earlier attempt at the same step that is still running (below). An unexpected error is retried too. A repository that cannot be cloned, a URL that is not `https://`, a request the model provider refuses (any other 4xx: a wrong key, no credit, an unknown model), a profile the analyzer could not produce within its limits (`AnalysisError`), a model key that is set nowhere, a stored credential that cannot be read (`CREDENTIAL_FAILURES` in `analysis.py`), a configuration error and a run that does not exist or is already finished are not tried again. A database that fails while a credential is resolved is tried again like any other failure of the database. `LLMError.may_pass` in core holds the rule for the provider. A refused repository travels a longer way than before: the clone's handler fails for good with the sentence, the runtime tells the graph a failed outcome, the `clone` node raises `AnalysisError` with those words, and the step fails for good with them.

**Where a run's clone lives** (`repository_analyzer/clones.py`, `LocalClones`). One folder per run, `<system temporary folder>/openmarketer-analysis/<run id>/`, with the repository in `repo` under it; the name comes from the run's id and from nothing a repository or a URL says, and the root and each run's folder are readable by the worker's user only (mode 0700). What is kept of a clone is intake's result, in the memory of the worker process, so the repository is still read only through `RepoFiles` after the secret scan. The disk is one worker's own:

- A step on the worker that made the clone reads it and does not clone again.
- A step on another worker, or on this one after a restart or after the folder was removed, fetches the run's commit again (`at_commit`, through intake's fetch of one commit) and reads that.
- The clone is released by the runtime's `forget_run`, which calls the analyzer's run-ended function (`release_the_clone` in `wiring.py`) after the checkpoints are forgotten, for a run that succeeded, failed or was cancelled. An attempt that finishes and finds its run recorded failed meanwhile releases it too. A clone that fails leaves nothing of the run on the disk.
- What a dead worker left is removed by a sweep when a worker starts, and only then: every entry under the root that was last written longer ago than a run can last (`longest_analysis_seconds`, about 33 hours with the defaults) is removed. There is no periodic sweep.

`longest_analysis_seconds` (`policy.py`) is the bound both the sweep and the checkpoint cleanup use. It sums what the workflow can spend: `start_run` at every attempt's limit with its waits, each of the two graph steps at every attempt's limit with the waits between them, the clone the same way, the hour `record_failure` keeps trying, the hour `forget_run` keeps trying, and a day's allowance for attempts waiting while no worker serves the queue. With the defaults that is 118,957.5 seconds, 33 hours and 3 minutes (it was 27 hours 45 minutes before the clone and the second step were counted). `test_policy.py` writes the parts out as numbers.

- **A repeated activity does not repeat its work.** A repeated first step finds the thread waiting and returns the same request. A repeated clone answers with the clone this worker holds, so with the commit the first one read. A repeated second step continues from the last checkpoint; when the graph had already finished, it stores the profile without asking the model, and when the run already has its result it stores nothing.
- **One attempt at a time works on a run's thread.** An attempt at a step takes the run's checkpoints before it does anything, with a PostgreSQL advisory lock on its own connection, and holds them until its thread returns. Temporal can give up on an attempt whose thread is still working (after the time limit, a missed heartbeat, or when the worker is asked to stop); the next attempt is then refused at once with the retried failure `AttemptStillRunning`, and analyses nothing. It is tried again after the usual wait. The database releases the lock when the holder returns, its connection is lost or its process dies. The run's transition rules remain underneath: if two attempts did both analyse, the first to finish stores its result and the second's transaction is rolled back, so there is one profile version per run. The clone has no such lock in the database; within one worker process `LocalClones` lets one thread at a time work on a run's clone.
- **The failure message** holds nothing a repository host or a model provider wrote. A clone that fails gives one of six fixed sentences (see [Cloning from an untrusted host](#cloning-from-an-untrusted-host)); a refused model call gives `the model provider answered HTTP <status>`; a timeout, a lost worker, a cancellation, a failed write and an unexpected error each have a fixed sentence. A credential that is missing or unreadable gives the sentence of its error, which names what to set and holds no value: "the model provider's API key is not set: set it in the dashboard's Settings, or with the environment variable OPENROUTER_API_KEY" (for a model configuration that names another variable, only that variable is named), or "the stored value of github_token cannot be read: set ENCRYPTION_KEY to the key it was stored with, or set the credential again". What git printed and what the provider answered go to the worker's log. Any other error of the analysis is passed on with every path under the run's folder replaced by `<clone>` (`failure_message` in `repository_analysis/failures.py`); of those, a profile that does not match the schema lists the fields that are wrong, which the model wrote. Only failures of the types the analyzer declared as worded (`WORDED_BY_THE_ACTIVITY` in `steps.py`) pass with their message; any other is recorded in a fixed sentence. The runtime's own sentences ("the action did not finish in time", "an earlier attempt at the run is still running") are turned into the analyzer's ("the analysis did not finish in time", "an earlier attempt at the analysis is still running") by `in_the_analyzers_words`. Activities attach no cause to a failure, because Temporal stores causes too.
- **What Temporal's history holds**: the three identifiers of the run (the workflow's input, `start_run`'s input and the payload of the clone request), the kind `analysis-run` with the run id in each step's input, the limits, the commit that was cloned, the id of the stored profile version, the failure message, and for a failed activity the stack trace Temporal records (file names and source lines of the worker's code, no values). Nothing else: no repository URL, no folder, no profile, nothing the analyzer read, and no credential. A credential is resolved inside the activity that uses it and is in no input, result, failure or checkpoint; a test runs an analysis with a stored key and a stored token and searches the decoded history for both.
- **Left-over checkpoints are removed by every worker** when it starts and every ten minutes after that (`checkpoint_cleanup.py` at the top level of the worker, since the checkpoint tables are shared by every graph). That module keeps the schedule and knows no rule: each agent's wiring hands it a cleanup for each kind of run that keeps checkpoints, and every round runs each of them in a transaction of its own, so one that fails does not keep the others from running. Today there is one, for analysis runs (the rule in core's `db/checkpoint_cleanup.py`, handed over by `repository_analyzer/wiring.py`). It never changes a run. A cleanup that fails is logged and tried again the next time; it stops neither the worker nor an analysis.
- **A project stored from the command line with a local folder is refused**: the worker clones `https://` URLs only.

What the worker does not do:

- **Some failures leave a run unfinished**, and an unfinished run blocks its project until the row is changed by hand:
  - the workflow is terminated (from the UI, the CLI, or by an execution timeout set by whoever started it): a terminated workflow runs no further code;
  - Temporal loses the workflow or its history (for the dev stack: `make reset`, which deletes its volume), or the API process died between committing the run and starting its workflow, or the database refused the API's attempt to mark such a run failed;
  - the database stays unreachable for the hour `record_failure` keeps trying;
  - no worker is running: the run waits, `queued` or `running`, until one is started. This is the intended behaviour and has no time limit.
- **Workflows that were in flight under the earlier `AnalyzeRepository` cannot be continued by this code.** The earlier workflow scheduled `start_run` and then `analyse_and_store`; this one schedules `start_run` and then `run_graph_step`. A worker with this code that replays the history of a run started before it meets an activity it would not have scheduled, which Temporal reports as a non-deterministic workflow, and the run hangs. There is no versioning or patch marker in the workflow. Let the queue drain, or terminate what is in flight (and mark those runs failed by hand), before deploying. This is read from the two versions of the workflow; it was not tried.
- **No cancellation of the work itself.** Cancelling the workflow marks the run failed, but the thread that is analysing or cloning cannot be stopped: it runs until the analyzer's own limits or git's time limit end it, and its result is then discarded. The same holds when a worker is stopped: the process ends only after the work in progress returns.
- **An attempt that outlives the retries fails the run.** While an attempt that was given up on is still running, the attempts after it are refused, 1, 2, 4 and 8 minutes apart. If it runs for longer than the attempts that are left wait, the run ends `failed` with "an earlier attempt at the analysis is still running", although that attempt may still produce a profile, which is then discarded.
- **A heartbeat shows that the worker process is alive, not that the analysis is making progress.** An analysis that hangs is ended by the attempt's time limit.
- **The extractors run twice in a successful analysis**: once in `prepare`, for the hints the model is given, and once when the result is stored, for the evidence rows, because what they found is not kept in the graph's state. They are deterministic and read the same commit, and cost time, not money. They run again, like `prepare` as a whole, in an attempt that continues from before `prepare` finished.
- **A clone can stay on a disk after its run ended.** `forget_run` releases the clone on the worker that happens to execute it. With more than one worker on the queue that need not be the worker that holds the clone, and a clone on another worker stays until that worker next starts and the folder is older than the bound. The same holds for the clone of a run whose workflow was terminated or lost, and for a worker that is killed: its folders stay until a worker starts on that disk after the bound. This is read from the code (`LocalClones` is per process, and Temporal gives an activity to any worker of the queue); it was not observed, since only one worker has been run.
- **The clone's time limit and retries are not exercised on a real Temporal server with a real clone.** The workflow tests check that the clone is scheduled under the limits declared on the action and how a failed outcome ends the run; a clone that actually takes too long, or a worker that dies during one, is covered for git's own time limit in core's clone tests and not through the workflow.
- **A workflow started with a real run id and another workspace's or project's identifiers has that run's thread forgotten and its clone released.** Nothing is analysed, stored or recorded for it: `start_run` and `record_failure` are scoped to the workspace and the project and find no such run. But the thread and the clone are found by the kind and the run id alone, so `forget_run` at the end of that workflow removes them, and a real run of that id that was in progress would continue from nothing. The API derives a workflow's input from the row it stored, so this needs someone who can start workflows on the Temporal server directly.
- **No progress.** A run says `running`; it does not say which step it is at. The checkpoints are not read for that.
- **More code than before.** The worker's side of the analyzer is 1,235 lines in ten modules, counted with `wc -l` on 2026-10-12; it was 1,122 in nine before credentials were resolved at each attempt, and this page recorded 747 in seven before the analyzer moved onto the runtime. Most of the difference is `clones.py` (223) and `analysis.py` (294), and the workflow itself shrank from 103 lines to 84. `credentials.py` at the worker's top level adds 102. In core, `analyzer_agent/` went from 783 lines to 836. The wiring an agent must write to stand between its graph and the worker's database, disk and model is the known cost of the runtime.

### Graph checkpoints

The design stores the checkpoints of a graph in PostgreSQL so that it can resume after a failure (the report's section "Agent graphs and durable workflows"). That is built, and the repository analyzer uses it when the worker runs it. The analyzer's graph is compiled from its agent (`compile_agent`, by `AgentSteps`) with the run's checkpoint store, and core's `GraphThread` takes it step by step on a thread named for the analysis run (`analysis-run:` followed by the run's id). LangGraph's own PostgreSQL checkpointer stores a checkpoint after every node, and each is in the database before the next node starts. The command line and the benchmark do not use any of this: `analyze` runs the same graph in memory from its `prepare` node (`run_from`), with a repository the caller cloned, and an interrupted run starts again.

How an attempt at a step begins is no longer a rule of the analyzer (`resumption` in `rules.py`, with its four cases and `Analysis.resumption`, is gone). It is what `GraphThread.advance` does for every graph:

| What the thread holds | What the attempt does |
|---|---|
| Nothing | Starts the graph from the run's initial state (the run's identifiers, nothing read, nothing spent) |
| A pause at the clone, and no outcome is given | Returns the same request and runs nothing |
| A pause at the clone, and the clone's outcome | Continues from the pause with the outcome |
| Checkpoints after the clone, no accepted profile | Continues after the last finished node. Steps, cost, submissions and the conversation carry over, so `max_steps`, `max_cost_usd` and `max_submissions` count every attempt of the run |
| A finished graph | Runs no node and calls no model; `finish` stores the accepted profile, or finds it stored |

Nothing is compared before continuing: a thread that has checkpoints is continued. The commit is part of the state, so the question of "the same input" that the earlier rule asked does not arise.

The node that was running when an attempt stopped is run again. `run_tools` only reads files; a repeated `call_model` pays for one model call; a repeated `prepare` runs the extractors again; a repeated `clone` asks for the same action and is given the same outcome. So a model call that finished and whose node was recorded is not made again, and at most the one call in flight is paid for twice.

How it is put together:

- **The store is shared; each kind of run brings its own rules.** `graph_checkpoints/` is what every graph uses for checkpoints: the type a graph receives (`RunCheckpoints`, in a module that loads no database driver) and the PostgreSQL store (`postgres.py`: the connection, the attempt lock, the strict serializer). It holds no rule. The thread of a run is named by `thread_id(kind, run_id)` of `agent_runtime/threads.py`; for an analysis run that is `run_thread_id` in `db/analysis_runs.py`, with the prefix `ANALYSIS_RUN_THREADS`, and the cleanup rule of analysis runs touches only threads with that prefix. Another kind of run would name its threads with its own kind and bring its own rule. The analyzer is the only agent the product has.
- **The tables are the library's, created by a migration.** `checkpoints`, `checkpoint_blobs`, `checkpoint_writes` and `checkpoint_migrations` belong to `langgraph-checkpoint-postgres`, which defines them as a numbered list of statements and reads and writes them with its own SQL. They have no model in `db/models.py`. The fourth migration runs the library's statements 0 to 9 and records each number in `checkpoint_migrations` as the library's own `setup()` would, so `make migrate` creates them and nothing calls `setup()` when the worker runs. The range is fixed in the migration, and so is the text: the revision computes the SHA-256 of the statements exactly as it is about to send them and refuses to run when it differs from the hash recorded in the revision (taken with `langgraph-checkpoint-postgres` 3.1.2, after the statements were read), so a library version that words them differently is not run unread. The dependency is bounded below 4. The three `CREATE INDEX CONCURRENTLY` statements run without `CONCURRENTLY`, which cannot run inside the migration's transaction and makes no difference on tables created empty in it. `db/migrations/env.py` leaves the four tables out of autogenerate, which would otherwise propose dropping them. `CHECKPOINT_SCHEMA_VERSION` in `db/checkpoint_schema.py` is the last statement the migrations run; a test fails when the installed library has a later one, and another compares the migrated tables with the ones the library creates for itself. On a library upgrade, later statements go in a new revision that pins them the same way; the fourth revision and its hash are not edited.
- **What is read back is data, never something to run.** The library's serializer can rebuild an object by importing a module and calling a name that the stored bytes give, and by default does so for any name. Whoever could write to the checkpoint tables would then run code in the worker, which can read the model provider's key and the repository tokens: from its environment, and the stored ones with `ENCRYPTION_KEY`. The store is therefore built with the strict serializer (`JsonPlusSerializer(allowed_msgpack_modules=None)`), set in code and not by the environment: only the library's short list of plain value types is rebuilt, and anything else comes back as the plain data it was stored with. The analyzer's state is plain data, so nothing it stores needs more; what a node needs that is not plain data (the model client, the repository) is in the attempt's context, which is never stored. So the worker does not trust the tables for code. It does trust them for content: a conversation, a commit or a finished profile found for the run is continued or stored as it is, without a check that the worker wrote it.
- **One connection per attempt at a step** (`run_checkpoints` in `graph_checkpoints/postgres.py`), opened from `DATABASE_URL` translated to the driver's connection string and closed when the attempt ends, beside the worker's session pool. The same connection holds the attempt's advisory lock on the thread (see [The worker](#the-worker)); the lock belongs to the connection's session. An error of the driver is raised as `DatabaseError` with its first line, like any other failure of the database, and is retried by the worker.
- **A run's checkpoints are forgotten when the run ends**, by `forget_run`, the last activity of every run: after its profile is stored, after its failure is recorded, after a cancellation. A failure that will be tried again keeps them. Forgetting never fails the run: if it does not work, that is logged and the rows are left to the cleanup.
- **The cleanup removes what forgetting missed.** `remove_checkpoints_of_analysis_runs(session, longest_run=...)` (`db/checkpoint_cleanup.py`) deletes, in one statement, the rows of every thread named for an analysis run that no run needs. It considers only threads whose name starts with `analysis-run:`. Such a thread is kept only while the run it is named for is unfinished and either has not started or started less than `longest_run` ago, by the database's clock. So these go: threads of succeeded and failed runs, of runs that no longer exist, threads with the prefix followed by something that is not a run id, and threads of runs still marked `running` that started longer ago than a run can last. A thread of any other name is left alone, whatever its age. The last case is a run whose workflow was terminated or lost: its checkpoints are removed, the run itself stays `running` and still blocks its project. The bound is `longest_analysis_seconds` (see [The worker](#the-worker)), 33 hours and 3 minutes with the defaults. Workers with different `ANALYSIS_*` settings each apply their own bound. A run that outlasts it and is attempted after all starts from the beginning, with a new clone. A queued run is kept however long ago it was requested. It is maintenance across workspaces, not scoped to one, and returns only a count. The price of each rule touching only its own threads: a thread of a kind no rule knows, such as one named with a bare run id, is nobody's to remove and its rows stay.

What it does not do, and what to know before relying on it:

- **Repository content rests in these tables while a run is in flight.** A checkpoint holds the analyzer's conversation: the files it read, after intake's scan and redaction, and the drafted profile.
- **The tables have no workspace or project column.** A thread belongs to a workspace only through the run it is named for. Nothing in the database keeps one workspace's checkpoints from another: like every other table they are reachable by the one application role, with no row-level security, and here there is not even a column a policy could use. The code reaches a thread by the kind and the id of a run it was handed; the cleanup reads thread names across workspaces and no content. A consequence is listed under [The worker](#the-worker): a workflow started with a run id and the wrong workspace forgets that run's thread.
- **Rows can outlive their run by up to the cleanup interval of ten minutes**, or longer while no worker is running: a process killed between storing the profile and forgetting; an attempt that was given up on and still writes after its run was recorded failed (it forgets again when it returns). The checkpoints of a run whose workflow was terminated or lost stay much longer: until the run started longer ago than a run can last.
- **Removed is not erased.** Forgetting and the cleanup delete rows. PostgreSQL keeps the content in dead tuples until vacuum, in the write-ahead log, and in any backup taken meanwhile.
- **The worker needs a direct or session-mode connection to PostgreSQL.** The one-attempt-per-thread lock is an advisory lock of the session. A connection pooler in transaction mode hands the session to others between statements, which breaks the lock. This has not been tried against a pooler.
- **The cost a provider reports is not checked for NaN or a negative number.** `cost_usd` is taken from the reply as it is and added to the run's cost. Noticed, not tested, not fixed.
- **A thread grows with the square of the number of steps.** The library stores the whole conversation at each version. Measured by the agents who built the checkpoints, before the analyzer moved onto the runtime, on scripted runs with tool results of 5 to 40 KB per turn, as uncompressed payload of one thread: about 1.9 MB after 10 turns, 7.7 MB after 20 and 31 MB after 40, the default step limit. The rows are temporary. No live run was measured, and the measurement was not repeated on this code.
- **A deploy between two attempts of one run is not detected.** There is no version on a thread. If the new code changed the shape of the graph's state (`AnalyzerState`), a stored thread may not be continuable: a missing key raises, which the worker reports as an unexpected error and retries until the attempts are used up. The same goes for a changed graph (a node renamed or removed while a thread waits at it). Changed limits and prompts apply silently to the conversation the old code began. A thread stored by the analyzer before this change has neither the run's identifiers nor the commit in its state; see the note on workflows in flight under [The worker](#the-worker).
- **The checkpoint connection has no connect timeout of its own.** It waits as long as the driver does unless `DATABASE_URL` carries `connect_timeout`. The heartbeat does not end such a wait; the attempt's time limit does.
- **The command line stores no checkpoints.** `openmarketer analyze` runs the analyzer in memory, with or without `--save`, and an interrupted run starts again.
- **Nothing reads a checkpoint except to continue.** There is no progress report from them, no way to stop a running analysis through them, and no history kept after the run.

### Agent runtime

The design runs an agent's graph inside a Temporal activity (the report's section "Agent graphs and durable workflows"). A graph that only reads files and calls a model needs nothing more. A graph that has to clone a repository, send an e-mail, call a service or publish cannot do that inside the activity that runs it: the work needs timeouts and retries of its own, a key that makes a repeat harmless, and one place where a policy gate and an approval can stand. The agent runtime is the layer for that. A graph runs inside one activity until it finishes or asks for an *action*; the workflow runs the action as an activity of its own and gives what came of it back to the same graph thread, which continues where it paused. On top of it is a small set of decorators (below, "Writing an agent") with which an agent is declared. The repository analyzer runs on it, with one action, `clone_repository`; it is the only agent that does.

The code is in two places, and the dependency runs from the worker to core. Below, *core* is `packages/core/src/openmarketer_core/agent_runtime/` and *worker* is `apps/worker/src/openmarketer_worker/agent_runtime/`.

| Module | What it holds |
|---|---|
| core `actions.py`, `steps.py`, `threads.py` | Plain data and rules, no framework: `ActionRequest`, `ActionOutcome`, `ActionPolicy` (how an action is tried, within ceilings), and `ActionDefinition` and `ActionCatalog` (the allowlist); `GraphRunRef`, `StepOutcome` and the reasons a thread refuses a step (`StepError` and its kinds); `thread_id(kind, run_id)`, which gives `<kind>:<run id>` |
| core `model_input.py` | How text a model wrote is read: as strict JSON, into types that forbid unknown fields and name no file or import, with errors that name the fields at fault and never a value |
| core `agent.py`, `tools.py` | `Agent`, whose decorators (`action`, `node`, `edge`, `route`, `tool`) only record what an agent is, as plain data; `Toolbox`, the tools an agent's model may call. No framework, so a workflow's module may load them |
| core `langgraph_steps.py`, `langgraph_agent.py` | The LangGraph side: `request_action`, which a node calls, and `GraphThread`, which takes a graph one step at a time on its thread; `compile_agent`, `AgentSteps` (the steps of an agent's runs, which the worker is handed) and `run_from` (the same graph in memory, for a run with no workflow) |
| worker `vocabulary.py` | Plain data the workflow sandbox loads: activity names, failure types, fixed texts, `GraphRunPolicy`, `DatabaseWritePolicy`, the bounds on what enters a history |
| worker `driver.py`, `workflow_support.py`, `workflow_dsl.py` | Workflow code: `run_graph_with_actions` (the driver), `database_write` and `reason_shown`, and `agent_workflow`, which makes a class the workflow of an agent |
| worker `activities.py`, `routes.py`, `activity_support.py`, `agent_worker.py` | For the worker process only: `RuntimeActivities` (`run_graph_step`, `run_action`, `forget_run`), the routes of an agent's actions, the helpers every activity needs (failure wording, heartbeats around blocking work, checkpoint access, the size of what a history would store), and `AgentWorker`, where handlers are declared and a registration is made |

**How a run goes.**

1. The agent's workflow, made by `agent_workflow`, refuses a run whose kind is not the agent's, calls its `before` hook, and then the driver, `run_graph_with_actions(run, actions=agent.policies, policy=...)`, with a `GraphRunRef` (the kind of run and its id: the thread is `<kind>:<run id>`).
2. The driver runs the activity `run_graph_step` with the run and, after the first step, what came of the last action. The activity refuses a run of another kind, takes the run's checkpoints for the attempt (an attempt is refused, and retried, while an earlier one still holds them) and calls the agent's `AgentGraph.advance` in a thread, with heartbeats. The graph runs until it finishes or a node calls `request_action`, which pauses it (a LangGraph interrupt). The step returns a `StepOutcome`: what the agent reports of the finished run, or the `ActionRequest` (`action_id`, `name`, `payload`) it waits for.
3. For a request, the driver refuses in the workflow a name that is not in the allowlist, and a run that has already asked for `max_actions` actions (200 unless the policy says otherwise). Either ends the run and nothing runs; the model's text never becomes the name of an activity. Otherwise it runs the activity `run_action` under that action's own `ActionPolicy`: attempt time limit, attempts, first wait (doubled after each) and, for an action that runs long, a heartbeat timeout.
4. `run_action` checks the request against the `ActionCatalog` of the agent's routes: the name must be in it and the payload must fit the action's model, read as strict JSON. A refusal names the action and the fields at fault and never repeats a value. The activity then calls the action's handler in a thread with the validated payload and an `ActionContext` whose `action_id` is the key of the work. The handler's result must be JSON of at most 32 KiB.
5. The driver takes the next step with the `ActionOutcome`, and `GraphThread.advance` continues the graph from where it paused, until a step says the graph finished. The workflow then calls its `after` hook, or `failed` when the run did not finish, and in every case the activity `forget_run`.

**The allowlist** is the agent's declarations and nothing else. `@agent.action(name, ...)` on a payload model records the name, the model and the limits. The workflow is given `agent.policies` (the names with their limits) and the worker's routes are built from `agent.definitions`, so both sides read one list; `AgentWorker.registration` refuses to build a registration while a declared action has no handler. A node asks with the payload alone, `request_action(SendEmail(...))`, and the name is the one the model's class was declared with, so a node cannot ask by a misspelt name, and a model that no agent declared is refused before anything is asked (`NotAnAction`).

**A failure.** A failed action reaches the graph as an outcome with `succeeded` false and an `error` text of at most 500 characters, so the agent decides what to do. That is what happens when the action's attempts are used up, when an attempt took too long, when the worker stopped sending heartbeats, and when the handler raised a failure of a type the agent declared as worded (its message passes as it is). A failure of any other type, such as one the worker's library makes itself, is told as "the action stopped unexpectedly", and its detail is in the log only. Of the actions, only a defect of the agent ends the run: an action that is not allowed, a payload that does not fit, a result that is not JSON or is over 32 KiB, and more actions than `max_actions`; none of these is tried again. A step that fails ends the run too, after its attempts, and at once when the thread or the graph refuses the step (`StepRefused`: an outcome nobody asked for, a graph that waits for two actions at once or paused on something that is not an action request, a node that broke a rule below, a route that chose a node it was not given, a step outcome over 32 KiB).

**A step is safe to repeat; an action is repeated with a key.** An attempt at a step that died is retried with the same input. A thread that waits and is advanced without an outcome returns the same request and runs nothing; an outcome that an earlier attempt already applied is not applied again, and the graph continues, or returns the next request. The id of an action is `<thread id>:<interrupt id>`, the same each time the same step is attempted again. An action is not safe to repeat by itself: Temporal runs an activity at least once, and a thread cannot be stopped, so an attempt that timed out or was cancelled may still be running its handler when the next one starts. The handler gets the id as its idempotency key, for instance as the key of a request to the service it calls. For that reason an action is tried once unless its declaration says otherwise (`attempts=`): whether a repeat is harmless is a fact about the service behind the handler, which the runtime cannot check.

**The rules for a node**, which `request_action` states and checks:

- **One action per node.** A node that needs two is two nodes. Asking a second time in one run of a node is refused (`TwoActionsInOneNode`), and so is a graph that waits for several actions at once.
- **Nothing with a side effect before the call.** When the outcome arrives, the node runs again from its start, so anything it did before `request_action` is done twice.
- **Ask for the same thing every time.** The outcome is delivered with a digest of the request it answers, and a node that asks for something else when it runs again (a draft a model made anew, say) is refused (`RequestChangedOnResume`). Work that is not repeatable belongs in an earlier node, whose result the state keeps.
- **A tool may not ask for an action.** A tool is a function the model chose to call; it answers with text. An action is asked for by a node, from what the model submitted. A tool that calls `request_action` is refused (`ActionAskedByTool`). The check sees a tool that runs in the context of its caller; a tool that started a thread of its own would get round it.
- **A node answers with a mapping of what it changes in the state**, nothing else: the route after a node decides which node follows, and a route may choose only among the targets it was declared with.
- **Plain data.** The state of the graph, the payload (stored as JSON) and the result of an action are dicts, lists, strings, numbers, booleans and `None`, because the checkpoint store's strict serializer rebuilds nothing else. What a node needs that is not plain data comes in the agent's *context*, built for each attempt by the wiring and never stored.

**What enters the workflow history, and its bounds.** Identifiers, names and small JSON: the input of a step (the kind and id of the run, and the outcome of the last action), its result (what the agent's `finish` reports, or the request it waits for), the request of an action (its id, name and payload) and its outcome, and for a failure a type and a message that code chose, with the stack trace Temporal records (file names and source lines, no values). The activities refuse, for good, a step outcome over 32 KiB (`MAX_STEP_BYTES`: the request with its payload, or the final output) and an action outcome over 32 KiB (`MAX_RESULT_BYTES`), and what is not JSON. An error that nobody worded is logged and replaced by a fixed sentence, and a worded one leaves as a copy without the errors it was raised from, so a message written for a log never reaches the history; a test has a handler fail with a secret in its message and searches the decoded history for it. No checkpoint and no state of the graph between steps is in the history. The final state never is either: `AgentSteps` hands it to the agent's `finish`, and what `finish` returns is what is stored.

#### Writing an agent

An agent is four modules. The split is not a convention: the workflow sandbox, which loads a workflow's module and everything it imports, cannot load LangGraph or the database, so what the workflow needs of the agent (its kind and the limits of its actions) has to be in a module that imports neither. The greeter in `apps/worker/tests/agent_runtime/dsl/` is a complete agent written this way, and the tests run it on Temporal and PostgreSQL; the repository analyzer is the real one (`analyzer_agent/definitions.py` and `graph.py` in core, `repository_analyzer/workflow.py` and `wiring.py` in the worker). The outline below follows the greeter; its names (`RunCampaign`, `SendEmail`) are made up, and it was not run as written.

```python
# definitions.py: what the workflow may load. No LangGraph, no database.
agent = Agent("campaign-run", state=CampaignState, context=CampaignContext)   # context is optional

@agent.action("send_email", timeout=30, attempts=3, retry_after=2)   # attempts defaults to 1
class SendEmail(BaseModel):
    model_config = ConfigDict(extra="forbid")   # a payload that allows extra fields is refused
    to: str

# graph.py: the nodes. Importing this module is what puts them on the agent.
@agent.node(start=True)
def notify(state: CampaignState, context: CampaignContext) -> dict[str, Any]:
    outcome = request_action(SendEmail(to=state["address"]))   # the graph pauses here
    return {"sent": outcome.succeeded, "error": outcome.error}

agent.edge(notify, END)   # or @agent.route(after=notify, to=[...]) on a function that names the next node

# workflow.py: loaded by the sandbox; imports definitions.py, never graph.py or wiring.py.
@agent_workflow(agent, name="RunCampaign", graph=GraphRunPolicy(
    attempt_timeout_seconds=600, heartbeat_timeout_seconds=60, max_attempts=3, retry_after_seconds=10))
class RunCampaign:
    async def failed(self, run: GraphRunRef, reason: str) -> None:
        ...   # workflow code: call an activity that records why

# wiring.py: the worker's process only; imports graph.py, so the nodes are declared.
worker = AgentWorker(agent, task_queue="campaigns")

@worker.handler(SendEmail)
def send_email(payload: SendEmail, context: ActionContext) -> Mapping[str, Any]:
    ...   # blocking; context.action_id is the idempotency key; returns small JSON

steps = AgentSteps(agent, initial_state=..., finish=..., context=..., recursion_limit=20)
registration = worker.registration(
    checkpoints=checkpoints_in(database_url), graph=steps, workflows=[RunCampaign],
    activities=[...], checkpoint_cleanups=[...])
```

- **The hooks and their order.** The class given to `agent_workflow` defines no `run`; the decorator writes it. It may define three hooks, each an `async def` given the workflow's input. `before(run)` is first, for marking the run started; it may return a `GraphRunPolicy` that replaces the default, which is how limits from the worker's settings reach a run (workflow code cannot read the environment). Then the graph runs with its actions. `after(run, output)` follows a graph that finished, with what `finish` reported. `failed(run, reason)` is called instead when `before`, the graph or `after` failed or the workflow was cancelled, with a sentence that may be shown: the message of the failure when its type is one of `worded_types`, and one of the agent's fixed `texts` otherwise. Then, in every case, `forget_run` removes the run's checkpoints and calls the function the wiring registered with `@worker.run_ended`, for what a run left outside the checkpoints. `failed` and the forgetting are waited for to their end even when the workflow is cancelled meanwhile. A workflow whose starter has an input of its own gives `input=` and `run_of=`, as the analyzer does.
- **What `finish` is for.** `AgentSteps` calls it inside the step that ends a run, with the run and the final state. It may store what the run produced, so it must be safe to repeat, and it returns the small projection that enters the history: an identifier and a summary, never the state, which holds the model's whole conversation. The analyzer stores the profile there and returns its id. `initial_state` makes the state a run starts from and is called only for a thread with no checkpoint; `context` makes, for each attempt, what the nodes take as a second parameter.
- **What is checked when the worker starts, not at the first run.** A limit of an action that is not a finite positive number or is over the ceilings (10 attempts, a day per attempt, an hour's first wait), a payload model that allows extra fields or has a field that reads text as a file path or an import name, an action or a node declared twice: when the module is loaded. An agent with no node or no start, an edge or a route to a function that is not its node, a context given for an agent that declared none (or the reverse): when `AgentSteps` is made, which compiles the graph once. A handler for a model the agent did not declare, a second handler, an `async def` handler: at the decorator. An action with no handler and a workflow class that this agent's `agent_workflow` did not make: at `registration`. A workflow class that defines `run` or `proposal_decided`, a hook that is not an `async def` of the right parameters, a class not at the top of a module, an agent with an action that publishes or spends and no `scope_of`: at `agent_workflow`. Such an agent's registration without the database `sessions`: at `registration`.
- **An agent that keeps checkpoints brings its cleanup**: a rule in core that touches only threads of its kind, handed over as a `CheckpointCleanup`. Without one, rows that `forget_run` missed stay.

**Why not the official plugin.** The installed temporalio (1.34.0) has `temporalio.contrib.langgraph`, which its README calls experimental. It runs the nodes of a graph as activities (each node is marked `execute_in` `activity` or `workflow`), so the history grows with the nodes, and it uses LangGraph's in-memory saver with Temporal's history as the record: its README says third-party checkpointers such as PostgreSQL are not needed. This project runs the graph in one activity between actions and keeps its PostgreSQL store, its attempt lock and its cleanup, so it deliberately did not adopt the package.

What the agent runtime does not do, and what to know before relying on it:

- **The policy gate is the smallest one.** It holds every action that publishes or spends for a person and lets every other one run; see [Policy gate](#policy-gate) for what it does not weigh yet.
- **The worker serves exactly one agent.** `main.py` names the repository analyzer in one import and builds one `Worker` for its registration. The runtime's activities have fixed names (`run_graph_step`, `run_action`, `forget_run`) and Temporal refuses two activities of one name on a `Worker`, so a second agent needs a `Worker` and a task queue of its own, which `main.py` does not build.
- **The cleanup of checkpoints knows analysis runs only.** `remove_checkpoints_of_analysis_runs` (`db/checkpoint_cleanup.py`) considers only threads named `analysis-run:`. A thread of another kind is never removed by it, however old, so a second kind of run needs its own rule.
- **No Continue-As-New.** A run that asks for more than `max_actions` actions ends, where it could continue in a new workflow. A run of 200 actions was not produced, and neither the size of such a history nor how near it is to a limit of Temporal's was measured.
- **No progress.** Heartbeats carry no details, and nothing reads a checkpoint to say where a run is.
- **Cancellation reaches the work late or not at all.** A thread cannot be stopped: a step or an action that is cancelled runs until it returns, and what it returns is dropped. An action is told of the cancellation only at a heartbeat, so one whose declaration has no heartbeat timeout is never told. The next attempt may therefore start while an earlier one is still running its handler, which is what the key is for. For a step the thread is held by the earlier attempt, and the next one is refused and retried.
- **One action at a time.** A node asks for one action and the graph waits for one, so actions cannot run in parallel.
- **`@agent.tool` has no user.** `Toolbox` and the `tool` decorator are built and tested, and no agent declares a tool with them: the analyzer's tools are still its own (`rules.run_tool_calls` over `RepoTools`).
- **A failure's message is not bounded by the runtime.** What the graph is told of a failed action is cut to 500 characters, and a step's and an action's results are bounded; the message of a failure that an agent's own code worded enters the history as long as it is. (The analysis run's record cuts it to 2000 characters.)
- **`GraphThread` reads the whole history of a thread** when it is given an outcome that is not for the action pending, to tell an action asked earlier (an outcome an earlier attempt already applied) from one nobody asked for. It does so only then. A thread grows with the square of its steps (see [Graph checkpoints](#graph-checkpoints)), and this read grows with it.
- **A deploy while runs are in flight is not handled.** There is no workflow versioning and no version on a thread; see the notes under [The worker](#the-worker) and [Graph checkpoints](#graph-checkpoints).
- **The wiring is the cost.** What stands between an agent's graph and the worker's database, disk and services (`initial_state`, `context`, `finish`, the handlers, the run-ended function, the wording of failures) is the agent's to write; for the analyzer that is `analysis.py`, `clones.py` and `wiring.py`, 714 lines (656 before credentials were resolved at each attempt).
- **The dev Temporal server waits at least a second before a retry**, whatever interval is asked for. Measured on 2026-10-11 against the dev stack, with a one-off workflow: retry intervals of 0.1 s and of 0.5 s both gave about one second between attempts. So `START_RUN`'s half second of the analyzer, and any `retry_after` below one in the tests, behave as one second there. Whether another server does the same is not known.

### Policy gate

The design's policy gate (the report's section "Safety: Approvals, Budgets and Autonomy") stands where an action is started: in the driver of the agent runtime, which every action passes, so no node can skip it and no model can avoid it. It is built in its first, smallest form: **every action that publishes or spends waits for a person, and every other action runs.** Nothing else is weighed yet.

How it works:

1. **An action says what it does.** `@agent.action(name, effect=ActionEffect.PUBLISHES, approval_wait=...)`. The effect is `internal` by default (the clone is), `publishes` or `spends`; it is declared in code with the action and never read from a request, which a model may have shaped. `approval_wait` is how long a person has, three days by default and a month at most. An agent with such an action gives its workflow `scope_of` (which workspace and project a run works for) and its registration the database sessions; both are refused when the worker starts if missing.
2. **The gate decides** (`agent_runtime/gate.py`, `verdict_for`): `internal` runs; `publishes` and `spends` ask a person.
3. **The run proposes and waits** (`approval_wait.py`). The activity `propose_action` stores the action as a row of `proposal`, keyed by the action's idempotency key so that a retry finds the same row, with the payload, the run, its workflow and a deadline. The workflow then waits with no activity running, for the signal `proposal_decided`, for the deadline, or for 15 minutes, whichever comes first, and reads the proposal back each time with `settle_proposal`, which expires it once the deadline passed. The decision is always read from the database: the signal carries a proposal id and approves nothing, since anyone who reaches the workflow server can send one. A run cancelled while it waits expires its proposal.
4. **A person decides** through the API (`approveProposal`, `rejectProposal`), as the current user: `approvals/decision.py` stores the decision, then signals the run. A run that cannot be signalled reads the decision at its next check, within 15 minutes; a decision after the deadline is refused (409).
5. **The action runs, or the graph is told why not.** Approved, the driver runs it as any action. Rejected or expired, it does not run, and the graph gets a failed outcome ("a person rejected the action", "nobody approved the action before its deadline"), so the agent can revise what it asked for or give up.
6. **`run_action` checks again.** Before the handler of an action that publishes or spends runs, the activity checks that a person approved that very action (`proposal_status_of_action`), and ends the run otherwise (`ActionNotApproved`). That holds when a workflow did not go through the gate, for instance one started by hand on the workflow server.

A proposal moves once: `pending` to `approved` or `rejected` by a person, or to `expired` by its run; the database holds the decider and the time with checks of its own. It was checked with a test agent that publishes an announcement (`apps/worker/tests/agent_runtime/announcer/`), on the dev stack's Temporal and PostgreSQL: approved and run once, rejected, expired at its deadline, a signal with no decision behind it approving nothing, a cancelled run expiring its proposal, and `run_action` refusing an action nobody approved; and with tests of the store and the routes.

What the gate does not do yet, from the design:

- **No budget, no content filter, no banned content.** No cap is checked and nothing is reserved in a ledger; the text of a payload is not filtered. The order of the design's checks (banned, budget, content filter, then risk) is where these go, in `verdict_for` and around it, before a person is asked.
- **No risk levels and no autonomy.** Every held action is treated as the design's L1 (an approval queue); nothing is L0 (automatic) or L2 (human only), and the project's `autonomy_level` column is not read. There is no dry-run mode and no kill switch.
- **No policy file.** There are no YAML rules and no CEL; the one rule is in code.
- **A proposal cannot be edited**, only approved or rejected. The design's "approve, edit or reject" needs an edited payload to pass the gate again.
- **No audit log, no rationale or evidence on a proposal, no reminders.** A proposal holds the payload and not the agent's reasons, the evidence or the profile version it used; nobody is notified of a proposal, and a deadline that passes is not escalated.
- **No product agent uses it.** The analyzer's one action is internal. The first agent that publishes will be its first user.

### Stored credentials

The installation has three credentials, the secrets the code uses: the model provider's API key (`openrouter_api_key`, environment variable `OPENROUTER_API_KEY`) and the access tokens of the two repository hosts (`github_token`, `GITHUB_TOKEN`; `gitlab_token`, `GITLAB_TOKEN`). Each could only be set in the environment. Each can now also be stored for a workspace from the dashboard's Settings, and is then kept encrypted in the table `credential` (migration `e96ec2276ea4`), one row per workspace and name.

The code is in core's `credentials/`: `catalog.py` is the list of the three and the rule for an acceptable value, `cipher.py` seals and opens a value, and `resolution.py` says which value a credential has, where each comes from, and sets or removes a stored one. The rows are read and written by `db/credentials.py`. The API's routes are listed under [The API](#the-api), the screen under [The dashboard](#the-dashboard), and the worker's side is `credentials.py` at the top level of the worker (`WorkspaceCredentials`), with the analyzer's `repository_analyzer/repository_tokens.py`.

- **The environment wins.** A credential whose environment variable is not empty has that value, and a value stored for it is ignored. Storing one while the variable is set is refused (`CredentialSetByEnvironment`, the API's 409), because it would have no effect. A value stored earlier is kept, and its status still says it is stored, so the screen can say it is being ignored. Removing a stored value is always allowed and never touches the environment. A variable that is empty or holds only whitespace sets nothing, and a value from the environment is used without the whitespace around it; the model router and `RepositoryTokens` read their variables the same way, so this holds for the command line too.
- **A value is write-only.** It enters in the body of `setCredential` and nothing returns it or anything derived from it. A status is where the value in use comes from (`environment`, `stored`, `not_set`), the variable that would set it, and who stored a value and when. The query behind a status selects the name, the time and the user and never the nonce or the ciphertext; two tests read the SQL that was sent. Only `sealed_credential` reads those two columns, and what it returns is still encrypted. The one function that decrypts is `credential_value`, and its one caller is the worker. The API's request model holds the value as a `SecretStr`, and a refused request is not quoted back (see [The API](#the-api)).
- **A stored value is bound to its workspace and its name.** It is sealed with AES-256-GCM under the installation's `ENCRYPTION_KEY` (32 random bytes in base64; `openssl rand -base64 32` makes one), with a fresh random 96-bit nonce for every value. The workspace's id and the credential's name are the associated data, so a row copied to another workspace or under another name does not open. A value that does not open is not told apart: a wrong key, a changed row and a moved row read the same, and neither the key nor a value appears in an error or in `repr`. `cipher.py` is the only module of core that imports `cryptography`; a test holds it to that.
- **What a value may be.** Whitespace around it is dropped, since a pasted key often ends with a line break; what is left must be 1 to 4096 printable ASCII characters with no space. A refusal names the rule and never repeats the value or a part of it. The rule is applied when a value is stored, not to a value from the environment. A name the catalog does not have is not repeated either ("there is no such credential"), since it may be a secret written in the wrong place.
- **Resolved at each attempt, so nothing is restarted.** The worker keeps no credential. It asks for the model provider's key when an attempt at a graph step begins, and for the two repository tokens each time a clone or a fetch of the run's commit is really made, with the workspace of the run. A key stored, replaced or removed in the dashboard is what the next attempt finds; a test stores a key after the worker's parts were built and another replaces one between two steps of a run. 
- **The stored model key is OpenRouter's and goes to no other provider.** The model configuration names the variable of its provider's key (`provider.api_key_env` in `config/models.yaml`), and the worker looks at that variable first. Only when it is `OPENROUTER_API_KEY`, as shipped, is the stored value used when the variable is not set. A configuration that names another variable is another provider's: its key comes from that variable alone, neither `OPENROUTER_API_KEY` nor the stored value is sent to its endpoint, and a run without it fails with "the model provider's API key is not set: set the environment variable" and the variable's name, without pointing at Settings.
- **A credential that cannot be resolved ends the run, not the worker.** A model key set nowhere (`ModelKeyNotSet`) and a stored value that cannot be read, because the worker has no `ENCRYPTION_KEY` or another one (`CredentialUnreadable`), end the analysis with a sentence that names what to set and holds no value. Neither is tried again. A stored value that cannot be read does not matter while the environment sets that credential.
- **A credential is in no history and no checkpoint.** It is not in the graph's state, not in a workflow or activity input or result, and not in a failure; see [The worker](#the-worker).
- **`ENCRYPTION_KEY` is needed only for stored values, by both processes.** Without it the API answers `can_store: false` and refuses a `PUT` with 409 `encryption_key_missing`, and the worker cannot read what is stored. A key that is set and is not 32 bytes in base64 stops either process when it starts. The API and the worker must be given the same key. Credentials set in the environment work without it.
- **Who stored a value is the current user**, never a field of the request; in local mode that is the one fixed local user (`LOCAL_USER_ID`). Storing again replaces the value, the user and the time, which is the database's.

The model router gained what this needs and nothing else: `ModelRouter.headers(api_key=None)` takes the key to use, and `RouterChatModel.api_key` carries it, left out of `repr`. Without a key handed in, both read the environment as before, which is all the command line and the benchmark do.

What this does not do:

- **No key rotation.** Nothing re-encrypts. After `ENCRYPTION_KEY` is changed, every stored value is unreadable and has to be set again.
- **A status does not say whether a stored value can still be opened.** The list decrypts nothing, so a value sealed under another key is shown as "Set here" until a run fails on it.
- **The API and the worker each decide "the environment wins" from their own environment**, and the API reports `source` and `can_store` from its own. With a variable set for the worker only, the API stores a value and shows it as in use ("Set here") while the worker uses its environment's. With one set for the API only, the screen says "Set by the environment" and the worker finds no value. With no `ENCRYPTION_KEY` on the worker, or another one, the API reports that values can be stored, and every run that needs a stored one fails with the unreadable-credential sentence. Nothing compares the two processes. A model configuration that names another variable for the key is not read by the API either: the screen still offers the OpenRouter key, which that configuration never uses.
- **A value from the environment is not checked** against the rule for a stored one; apart from the whitespace around it, it is used as it is.
- **Whether a value is one its provider accepts is not checked**, when it is stored or later. There is no "test" button; a wrong key shows as a failed analysis ("the model provider answered HTTP 401").
- **Both repository tokens are resolved for every clone.** A stored GitLab token that cannot be read ends the analysis of a repository on GitHub too, and the reverse.
- **There is no login, and these routes raise what that costs.** Any process on this machine can store, replace and remove a credential by calling the API on `127.0.0.1:8000` directly; the dashboard's proxy stops another web site, not a local program. Whoever replaces the model provider's key with one of their own has every later analysis send the repository's content through an account they control. `set_by` is always the fixed local user, so nothing records who did it. See "There is no login" under [The API](#the-api).
- **"Not kept in this browser" is true of the dashboard's own code only.** The field is a password field, marked for password managers to leave alone, and a browser's password manager may still offer to save what is typed. This was not tried in a browser.
- **A secret pasted as the name in the path is not answered back, but it is logged.** The 422 and the 404 do not repeat it; the request path is still in uvicorn's access log.
- **No history of changes.** Replacing overwrites who stored a value and when, and a removal leaves no trace. There is no audit log.
- **Nothing erases a value from memory.** The API holds a submitted value for the request, and the worker holds the model key in the attempt's chat model for as long as the attempt runs, so a key replaced during a step is used from the next attempt on. A removed row is deleted, not erased from the database's files (as for [checkpoints](#graph-checkpoints)).
- **`GITLAB_HOST` is the environment's only.** It is not a credential, is read when the worker starts, and changing it needs a restart.
- **The command line and the benchmark do not read stored credentials.** `make analyze` and `make evaluate` take the key and the tokens from the environment, as before.
- **Downgrading the migration drops the table, and the stored values with it.**
- **Only these three credentials exist.** The other keys in `.env.example` (media providers, platform and advertising clients, OIDC, tracing) are read by no code. The table does not check a name: a row under a name the code no longer knows is never read, and nothing removes it.
- **No workspace isolation in the database**, as for every table: the scoping is in the queries, and beyond that in the binding of a sealed value to its workspace.
- **The value travels in clear on this machine**: from the browser to the dashboard on `localhost:3000` and from there to the API on `127.0.0.1:8000`, over plain HTTP on the loopback interface.

### Private repositories

The two repository tokens reach intake as `RepositoryTokens`. The CLI reads `GITHUB_TOKEN` and `GITLAB_TOKEN` from the environment. The worker resolves both for the run's workspace each time a clone or a fetch is made: the environment's value, otherwise the one stored from the dashboard (`repository_analyzer/repository_tokens.py`; see [Stored credentials](#stored-credentials)). Wherever a value came from, it is handed over under the same two names, and `repository_analysis/intake/credentials.py` alone decides which one, if any, a clone may carry.

- `GITHUB_TOKEN` is for `github.com`. `GITLAB_TOKEN` is for `gitlab.com`, or for the host named by `GITLAB_HOST` when that is set (a self-hosted GitLab; `host` or `host:port`).
- A token is offered only to an `https://` URL whose host is exactly the configured one: compared in lower case, without a trailing dot, on port 443 unless the configuration names another. There is no suffix matching (`github.com.evil.example`), and a URL with a user name, a backslash, a space or a control character gets no token.
- A repository on any other host is cloned without credentials, so public repositories work as before.
- git receives the token as a header configured for that origin only (`http.<origin>.extraHeader`). Scoping the header is not enough: after a redirect git sends its extra headers to the new host on the following requests, which is one of the two reasons no redirect is followed (next section).
- The token is not in the stored project URL (credentials in a URL are refused), not in a workflow or activity input, and not in an error message: errors of a clone are fixed sentences, and the token is removed from git's output before that is logged.

Before this, the command line sent whichever of the two tokens was set to any host a URL named.

What this does not do: a private repository has not been cloned with a real token (see below); one GitLab host can be configured, not several, and only in the environment (`GITLAB_HOST`); a token in the environment is per installation and a stored one per workspace, of which there is one, and none is per project.

### Cloning from an untrusted host

A repository URL comes from whoever can create a project, and the host behind it answers as it likes. `repository_analysis/intake/git.py` runs git so that neither can do more than be cloned:

- **git does not get the environment of the process.** Its environment is built from a list: `PATH`, `TMPDIR`, the proxy variables for HTTPS (`HTTPS_PROXY`, `https_proxy`, `NO_PROXY`, `no_proxy`) and the variables that add a certificate authority (`GIT_SSL_CAINFO`, `GIT_SSL_CAPATH`, `SSL_CERT_FILE`, `SSL_CERT_DIR`, `CURL_CA_BUNDLE`). An installation behind a proxy or with its own authority needs those; none of them switches a check off. Everything else is withheld: the model key, `DATABASE_URL` and the tokens never reach git or a program it starts, and `GIT_SSL_NO_VERIFY`, `GIT_CONFIG_*`, `GIT_TRACE*`, `GIT_ASKPASS`, `HTTP_PROXY` and `ALL_PROXY` set in the process change nothing. `HOME` is `/dev/null`, so there is no user configuration and no `~/.netrc`, and `LC_ALL=C` keeps git's messages in the language their cause is read from.
- **git asks nobody for a password.** `GIT_ASKPASS` and `SSH_ASKPASS` are set and empty, `core.askPass` and `credential.helper` are empty, and prompts are off. Before this, git inherited the environment, and a host that answered 401 made git run the askpass program of the process (the terminal of an editor sets one) and send its output to that host; a test keeps that reproduction.
- **No redirect is followed**, with or without a token (`http.followRedirects=false`). Without a token a redirect could still send the clone to an address the caller did not name, such as one inside the network the worker runs in.
- **Only HTTPS is used for a remote repository** (`protocol.allow=never`, `protocol.https.allow=always`; a local folder given on the command line allows `file` instead). If redirects were followed, a redirect to `http://` would still not be contacted.
- **What the host writes is not repeated.** git prints text from the host (`remote: ...`). It is logged, with the token removed, and the error is one of: the repository was not found or needs a token that is not configured or has no access; the URL redirects; the clone did not finish within 300 seconds; the host could not be reached; the connection could not be secured (TLS); the repository could not be cloned. The cause is read from git's own `fatal:` and `error:` lines only, with quoted text such as the URL removed, so neither the host nor the URL chooses it. Output that is not valid UTF-8 no longer stops the clone with an unexpected error.

Consequences:

- **A repository whose URL redirects cannot be analysed** until the project uses the address it redirects to. That is the case for a renamed or moved repository, and on gitlab.com for every URL that does not end in `.git` (`https://gitlab.com/group/project` redirects; `https://gitlab.com/group/project.git` does not). github.com and bitbucket.org serve both forms. The failure message says so. Projects are not changed to the new address automatically.
- **Any HTTPS host is still cloned from**, including one on the local network: redirects to such an address are closed, a URL that names one directly is not.
- **`gitleaks` still gets the environment of the process.** It is a local program that opens no connection; it has not been given a reduced environment.
- The operator of a terminal sees git's output and the provider's answer as log lines on standard error, because the command line does not configure logging.

### Golden-repository evaluation

The benchmark measures the analyzer against expected profiles. It is in `packages/evaluation/` and runs from the command line:

```bash
make evaluate                       # says what a run would make and spend, and stops
make evaluate live=1                # runs it: every case, 3 analyzer runs each
make evaluate live=1 case=excalidraw runs=1 judge=claude-code
make evaluate rescore=evals/results/<id>   # scores a stored run again, without a model call
```

- **A golden case** is a folder in `evals/cases/` with `case.yaml` (the repository, a full commit id, how the label was made, whether it lists every feature, and notes on what is weak about it) and `expected_profile.json`, checked against the schema when the case is loaded. A case names a commit, never a branch. How a label was made is one of four values, from an analyzer draft approved unchanged to written by a person, and the report prints it next to every score of the case.
- **Running** goes through the benchmark's own `analyze_repository` (`packages/evaluation/src/openmarketer_evaluation/runner.py`), with the case's commit: intake, the extractors and the analyzer's `analyze`, in memory and in one call. These are the steps the worker takes one by one in a workflow, not the worker's code path: no clone action, no checkpoints, no stored result. For this, intake can fetch one commit instead of the default branch (`run_intake(..., commit=...)`, `clone(..., commit=...)`): only a full 40-character id is accepted, that commit alone is fetched into a new repository, under the same lock-down and the same timeout as a clone, and a commit the host does not serve or that comes out different is an `IntakeError` that leaves nothing behind. The product's clone of a run is still of the default branch; the worker uses the same fetch of one commit when a later step needs the run's commit on a disk that does not hold the clone. A run that ends without a profile (a failed clone, a provider error, the step or cost limit) is recorded and scored as such, and the benchmark goes on with the next run. Runs are made one after another.
- **The judge** answers what code cannot decide: which drafted feature is which expected one, whether the lines a claim cites say what it says (at most 30 claims per run by default), and whether the free-text brand voice and audience agree. Its replies are parsed strictly; one that does not have the asked shape is recorded as malformed, and nothing is read into it. A benchmark does not start when the judge is the analyzer's model or one of its fallbacks, and a run that a fallback of the analyzer judged is marked in the report. The judge is reached in one of two ways: the `judge` role through the model router (the default, spends provider credit), or `--judge claude-code`, Claude Code's headless mode on the maintainer's subscription. The second runs with no tools, MCP servers, skills, hooks or project instructions, in an empty temporary folder, with an environment that holds no provider key, and every reply whose session report shows anything else is refused. On that route the role's temperature, length limit and structured output are not applied and the cost is not known; the report says so.
- **Scoring** is pure functions over the expected profile, the draft and the verdicts, one named function per metric in `scoring.py`: product name, type and platforms; features matched, missed and not in the label; recall, and precision only when the label says it lists every feature; drafted `live` features whose counterpart is not `live` (the costly error); agreement of statuses; claims that cite evidence and how many of them the judge found supported; the sections, business model, attribution, deep links, palette and analytics tools. The analyzer's cost, model calls and time, and the judge's calls and cost, are reported next to them.
- **Results** go to `evals/results/<benchmark id>/`: `config.json` (models of both roles, limits, the code's commit and whether it had uncommitted changes, the cases with a hash of each label), the drafts in `raw/`, the verdicts in `verdicts/`, `scores.json` and `report.md`. Scores are computed again from `raw/` and `verdicts/` alone, so a changed metric is applied to an old run without a model call; a label that changed since the run is pointed out. The cited lines shown to the judge (`excerpts/`) and replies that could not be read (`malformed_replies/`) repeat repository content and are kept out of git by a `.gitignore` the run writes into its own folder. The report gives, for every metric, the number of runs it comes from with the minimum, median and maximum, and starts with the limits of the result.

The first benchmark run is committed: `evals/results/20261010T085633Z/`, one run on Excalidraw at commit `4c00f31`, with the free analyzer model and a judge reached through Claude Code. The draft named the product and its type and platforms correctly, matched 13 of the 18 expected features (recall 0.72), marked no feature `live` whose counterpart is not, and agreed on the status of all 13 matched features. Every one of its 28 features was `live`, 15 of them not in the label, which is not exhaustive. Of 30 claims the judge was asked about, 14 were supported by the cited lines and 16 partly; 3 were not asked about. The run took 29 model calls, 169 seconds and no money; the judge made 33 calls. One run on one repository, against a label written by an AI assistant: this shows that the benchmark works end to end, not how good the analyzer is.

## Differences from the design report

| Topic | The original design said | The code does | Why |
|---|---|---|---|
| Role of the extractors | Deterministic extractors run first and the model "only synthesises and fills gaps" | The analyzer is an agent that explores the repository itself with read-only tools (`list_files`, `search`, `read_file`). Extractor output is given to it as hints. | Repositories are too varied, and too often monorepos, for extractors to carry the understanding. Covering each stack deterministically did not scale. |
| Files with secrets | A secret scanner runs, and `.env*`, key files and build output are excluded. What happens to a finding inside an ordinary file is not specified; the first implementation excluded the whole file. | The secret is replaced by `[REDACTED]` in place and the file is scanned again; a file is excluded only if a finding cannot be redacted. `.env*`, key files and build output are still excluded outright. | Excluding whole files removed configuration and source files the analyzer needs. |
| Product type and platforms | A fixed list (`consumer_app`, `b2b_saas`, …; `ios`, `android`, …) | Open vocabularies: any lowercase slug is valid, and the listed values are only the well-known ones | A product can be anything: a browser extension, a watch app, a hardware device. |
| Workspace isolation | PostgreSQL row-level security binds a session to one project; the checkpoint library's tables, which carry no project identifier, get a policy that joins a thread to its run | The identifiers are there, on the project's own tables and through the run for the checkpoint tables. No row-level security policy exists on any table, and the database has one application role | Not done yet. |
| Where the analyzer runs | Inside a Temporal activity, with a checkpoint after every step | In two places. In the worker: inside the `run_graph_step` activity of the `AnalyzeRepository` workflow that the API starts, with stored checkpoints, in two steps with the clone between them as an activity of its own. And synchronously inside the CLI and the benchmark, in memory and without checkpoints, so an interrupted run starts again | The CLI is the direct way to try the analyzer; it needs no Temporal, and no database unless `--save` is given. |

## Model for the analyzer

The `repo_analyzer` role uses the fast tier, and the fast tier is the free model `apodex/apodex-1.1-mini:free`. This is a design decision, described in the report's section on model configuration: analysing a repository costs nothing, and the model's output is checked in code and reviewed by a person. The first version of the design had the role on the strong tier. The quality of profiles from the free model has not been measured; `LLM_MODEL__REPO_ANALYZER` moves the role to another model.

## Model behaviour worth knowing

Weak or free models produced these failures against the analyzer; each is handled in code and covered by a test:

- Nested sections of the profile sent as JSON text instead of objects. They are decoded before validation.
- `confidence` left out, or the schema default `0` copied back. The tool schema shown to the model now requires `confidence` and shows no default, and a submission with a missing confidence, or `0` next to cited evidence, is rejected.
- The same rejected submission sent again. After three submissions, or when the run is out of steps or budget, the profile is repaired in code (bad evidence removed, unevidenced features set to `unknown`) and the corrections are reported. A submission that still does not match the schema at that point ends the run with an error.

Other things observed:

- A request names fallback models. When the primary model fails, OpenRouter serves the next one, which may be paid. The reply states which model answered and the CLI prints it. The name is kept only if it is printable text of 1 to 200 characters; otherwise the name that was asked for is used, because the name is stored with the run and a NUL character in it made every checkpoint write fail.
- Free models are rate limited upstream (HTTP 429). Runs are best started one at a time.
- Prompt caching is not used.

## What comes next

Saving results to the database is done, the API can create a project, have the worker analyse it as a workflow, and read, edit and approve its profile, and the dashboard does all of it in a browser. The dashboard reads projects, runs and profile versions from the API's list and read routes, and its Settings store the model provider's key and the repository tokens, which the worker resolves at each attempt; no analysis has yet run on a stored one outside the tests. A retried analysis in the worker continues from stored checkpoints, on the commit the run first read. The layer through which a graph asks for side effects (the agent runtime) is built and the analyzer runs on it, with a first policy gate: an action that publishes or spends waits for a person's approval through the API. Budgets, the content filter, risk levels and a dashboard screen for proposals come next, before an agent that publishes is added. The golden-repository evaluation runs with one command and has scored one run on one case. Next: more golden cases across stacks (mobile, CLI, library), labels reviewed by a person, and several runs per case, so that the analyzer's quality, and the free model's, can be stated. Whether a proposed strategy belongs to Phase 1 is open: the roadmap caption mentions it, the phase description does not.
