# Implementation status

What is built, how it was checked, and where the code differs from the [design report](design-report/report.pdf). The report describes the whole design; this page describes the repository as it is. Last updated 2026-10-17.

## What is built

Phase 1 of the roadmap is "repository analyzer and Product Profile": extractors, secret scan, evidence store, LLM synthesis, review UI, golden-repository evaluation and the orchestrator console's chat turn, which the roadmap places with this phase rather than with the agents the console supervises (see [The orchestrator chat](#the-orchestrator-chat)). The next step is a few agents, tested together with the chat turn (see [What comes next](#what-comes-next)). Core is organised by feature: everything of the repository analysis is in `packages/core/src/openmarketer_core/repository_analysis/`, the orchestrator console's chat in `orchestrator/` beside it, the researcher in `research/`, the installation's credentials in `credentials/`, the choices a workspace makes in the dashboard's settings (its models, the limits of an analysis) in `workspace_settings/`, and what several features share (`db/`, `graph_checkpoints/`, `agent_runtime/`, `llm.py`, `llm_config.py`, `profile.py`, `workflow_server.py`) is above them.

Four things run (five with the benchmark, `make evaluate`, described [below](#golden-repository-evaluation)): the command line, end to end; the API, which registers a repository, hands its analysis to the worker and reads, edits and approves the resulting profile; the worker, which executes the analysis as a Temporal workflow; and the dashboard, where a person does all of that in a browser. How one analysis runs end to end through the last three is drawn in [analysis-flow.png](analysis-flow.png) (source: `analysis-flow.html`): the path of a run from the click in the dashboard to the stored draft profile, with the file and function behind each step. The drawing was not redrawn when credentials began to be resolved at each attempt: nothing it shows became untrue, but it does not show that the two graph steps resolve the model provider's key, the workspace's models and the limits of an analysis for the run's workspace before the graph runs, or that the clone resolves the repository tokens (see [Stored credentials](#stored-credentials) and [Workspace settings](#workspace-settings-models-and-analysis-limits)). The command line first:

```bash
make analyze repo=https://github.com/owner/name
```

It clones the repository, scans and redacts secrets, runs the extractors, lets the analyzer agent explore the files, and prints a draft Product Profile as JSON. Nothing is published, and nothing is stored unless the run is started with `save=1` (next section). The profile is a draft: no person has reviewed it.

### Storing a run

`make analyze repo=... save=1` passes `--save` to `openmarketer analyze`, which writes the run to PostgreSQL after the profile has been printed (or written with `--out`). It needs the dev stack, a migrated database, and a `DATABASE_URL` in `.env` that points at it. For the dev stack that is `postgresql+psycopg://openmarketer:openmarketer@localhost:5433/openmarketer`; the value in `.env.example` uses the host name of the compose network and does not work from the host.

```bash
make up          # start PostgreSQL (and the rest of the dev stack)
make migrate     # create the tables
make analyze repo=https://github.com/owner/name save=1
```

The database is checked before the repository is cloned, so a missing `DATABASE_URL` or an unreachable or unmigrated database ends the command before any model call is made.

The database check also creates a workspace called `local` if there is none; it stands in for a user account in single-user mode. One saved run then writes, in a single transaction:

- a `project` row in that workspace for the repository, the first time that repository is saved. It is named after the product in the profile and keeps that name if a later profile names the product differently;
- a `repo_snapshot` row: the commit and the branch that were analysed;
- one `evidence` row per extractor fact: extractor, kind, value, file and lines;
- a `product_profile` row holding the profile as JSON, with status `draft` and a version one higher than the project's highest so far. Saving the same repository again adds a snapshot and version 2; it does not replace version 1.

To look at what was stored, open a shell in the dev database with `make psql`:

```sql
-- Every stored profile version, newest first, with the commit it was drafted from
SELECT p.name, p.source_repo_url, s.commit_sha, s.ref, pp.version, pp.status, pp.created_at
FROM product_profile pp
JOIN project p ON p.id = pp.project_id
LEFT JOIN repo_snapshot s ON s.id = pp.snapshot_id
ORDER BY pp.created_at DESC;

-- The extractor facts of the most recent snapshot
SELECT extractor, kind, file, start_line, value
FROM evidence
WHERE snapshot_id = (SELECT id FROM repo_snapshot ORDER BY created_at DESC LIMIT 1)
ORDER BY extractor, kind;

-- One section of the most recent profile
SELECT jsonb_pretty(content -> 'product') FROM product_profile ORDER BY created_at DESC LIMIT 1;
```

What storing a run does not do yet:

- **No approval.** Every profile stored by a run is a draft. A version is approved by a person in the dashboard, through the API (`approveProfileVersion`, see [The API](#the-api)); no command does it.
- **What the analyzer read is not stored.** The `evidence` table holds the extractor facts only, which the analyzer receives as hints. The evidence behind each claim in the profile (file and lines) is stored inside the profile JSON, not as rows, and the analyzer's tool calls are not stored at all.
- **A project is matched by the exact repository URL.** `https://host/a/b` and `https://host/a/b.git` become two projects, and so does the same repository analysed once from its URL and once from a local folder (stored as a `file://` URL).
- **No workspace isolation in the database.** Queries are scoped to a workspace in code. The database has one application role, and no table has a row-level security policy (see the differences below).
- **A project stored by the command line cannot be analysed from the dashboard.** It is listed there and its profile can be reviewed, but a project stored from a local folder has a `file://` repository, which the API does not clone; the dashboard says so, shows the address as text and builds no evidence links for it.

If saving fails after the analysis, the profile has already been printed or written, and the command exits with an error saying it was not stored.

### Profile versions and approval

`db/profile_versions.py` holds the database side of reviewing a profile. The API's profile routes call it.

- `save_edited_profile` stores an edited profile as a new draft with the project's next version number. The version that was edited is left as it is; the new row keeps its snapshot and records it in `edited_from_id`.
- `approve_profile_version` marks one version as approved, with the approver's user id and the database's time. Approving a version a second time raises `ProfileAlreadyApproved`.
- `latest_approved_profile` and `latest_draft_profile` return the approved version, or the draft, with the highest version number, or nothing. The latest draft can be older than the latest approved version; the caller compares the numbers.

Each function takes a workspace and a project, and a project of another workspace is treated like one that does not exist. They return a `ProfileVersion` holding the validated `ProductProfile`, not a database row.

The database enforces the rules itself, so they also hold for `INSERT`, `UPDATE` and `DELETE` statements written by hand:

- a trigger on `product_profile` accepts a new row only as a draft, so a version becomes approved only by an update of a stored draft;
- the same trigger lets an update of a draft change `status`, `approved_by` and `approved_at` and nothing else: not the content, the version number, the project, the snapshot or the creation time. It compares whole rows, so a column added later is frozen too unless the trigger is changed;
- it refuses every update of an approved row, and every deletion, draft or approved, but one: a deletion made while the transaction names the version's project as the one it is deleting (below). A version number is therefore never used twice within a project, and approving "version 2" always approves the content that was stored as version 2;
- a CHECK constraint requires an approved row to have both `approved_by` and `approved_at`, and a draft to have neither.

A consequence: a project that has profile versions cannot be deleted with plain SQL, because its versions cannot be. Deleting a project is the one deliberate path that removes them.

### Deleting a project

`delete_project` (`db/project_removal.py`) deletes a project of the workspace with its analysis runs, snapshots, evidence, every profile version, approved ones included, its proposals, decided or expired, its chats with their turns and messages, and the events its runs recorded (`run_event`), in the caller's transaction. Nothing is kept to restore it from, and a project registered again for the same repository starts with no history. The API's `DELETE /v1/projects/{project_id}` calls it, and the dashboard has "Delete" on every project's screen.

- **A project with an unfinished run is not deleted.** While a run is `queued` or `running`, `ProjectHasUnfinishedRun` is raised (409 `analysis_already_running` in the API): the worker would store a profile for a project that is gone, and nothing here stops a workflow. A run that never ends because its workflow was lost therefore keeps its project from being deleted, as it keeps it from being analysed again (see [Analysis runs](#analysis-runs)).
- **Nor is a project with a pending proposal.** While a proposal of the project is `pending`, `ProjectHasPendingProposal` is raised (409 `proposal_pending`): a run waits for a person to decide it, and would find neither the proposal nor the project. The project can be deleted once the proposal is approved, rejected or has expired.
- **It is serialised with the other writes.** It takes the workspace lock and then locks the project's row, so a run stored, an edit saved or an approval made at the same time waits for it, and a run requested at the same moment is either seen and refused, or refused afterwards by its foreign key (a 500, not a clean answer: the race is narrow and nothing is left behind).
- **The trigger's one exception.** The versions' trigger lets a version be deleted only while the transaction's setting `openmarketer.deleted_project` holds the version's project id (`set_config(..., true)`, so it ends with the transaction). `delete_project` sets it for the one statement that deletes the versions and clears it straight after. Any session can set the setting, as any session that can change the trigger can drop it: it keeps versions from being deleted by mistake, on their own, not from someone with the database's password. Migration `3c8d1e5f7a92` added the exception; its downgrade refuses every deletion again.

What it does not do:

- **A project with research runs cannot be deleted.** `delete_project` removes no `research_run`, `research_report` or `research_page` row, and the foreign keys to the project (and, for a run started from a chat, `research_run.chat_thread_id` to the chat) have no `ON DELETE CASCADE`, so the deletion stops on a foreign-key violation (`IntegrityError`) and nothing is deleted. This was so before chat events were added; the new column adds a second foreign key that would stop it. It was checked on 2026-10-17 with a throwaway test against the dev stack's PostgreSQL (not committed): a project with one research run, and one with a run started from a chat, both raised `IntegrityError`. What the API answers to it was not tried; no handler maps that error, so it is expected to be a 500. Not fixed. A fix has two more things to settle: `ProjectHasUnfinishedRun` looks at analysis runs only, so a research run in progress would not keep its project from being deleted, and the pages a run stored in object storage would have to be removed with their rows.
- **The checkpoints of the project's runs are left to the cleanup.** Each run's checkpoints were forgotten when it ended; what was missed belongs to a run that no longer exists, which the worker's periodic cleanup removes (see [Graph checkpoints](#graph-checkpoints)). Deleted rows stay in PostgreSQL's dead tuples until vacuum, in the write-ahead log and in backups.
- **No archive, no undo, no soft deletion.** `project.status` has an `archived` value that nothing writes; deleting does not use it.
- **The repository is not touched**, and neither are the workspace's credentials and settings, which are not the project's.

What this does not do:

- **No command.** The API routes edit and approve a profile and the dashboard uses them; no CLI command does.
- **The approver is not checked.** There is no user table; `approved_by` is whatever id the caller passes. The API passes the one local user (see [The API](#the-api)).
- **No rule about which version may be approved.** An older draft can be approved after a newer version; "latest approved" follows the version number, not the time of approval.
- **`TRUNCATE` is not stopped, and the trigger can be removed.** Row triggers do not fire for `TRUNCATE`, and the owner of the table can disable or drop the trigger. Downgrading the migration does exactly that: while a database is downgraded nothing protects its versions, and a later upgrade cannot tell whether approved content was rewritten in between.
- **An approved row without an approver stops the upgrade.** The first revision allowed one, though no code wrote it. The migration refuses rather than guess; its docstring says how to repair the row.
- **Writes are serialised only under READ COMMITTED**, PostgreSQL's default. Under a stricter isolation level a write that had to wait fails on the unique constraint instead of taking the next version number.
- **A version says where it comes from in words a person can read.** `ProfileVersion` carries `edited_from_version` (a version number; none for a version stored by an analysis) and `commit_sha` (the analysed commit; an edit keeps the commit of the version it was made from) beside the row ids. Both come with the statement that reads the version, through two outer joins, so no function makes a second query for them.
- **The list of versions never reads a profile.** `list_profile_versions` selects the columns of a `ProfileVersionSummary` and not `content`, which can be large; a test reads the SQL that was sent and fails if the column is named. `profile_version` reads one version by its number.

### The API

`make api` serves the API on `http://127.0.0.1:8000`. It needs the dev stack, a migrated database and `DATABASE_URL` in `.env`, like a stored run. An analysis also needs `make worker` running: the API stores the run and starts its workflow, the worker executes it. So, to analyse a repository through the API: `make up`, `make migrate`, `make worker` and `make api`. The API itself clones nothing and calls no model except a chat turn (see [The orchestrator chat](#the-orchestrator-chat)), whose route resolves the model provider's key and so decrypts a stored one when it is in use. Of the three credentials it can store (see [Stored credentials](#stored-credentials)) it otherwise looks at whether the environment sets each and encrypts a value it is given. `ENCRYPTION_KEY` is optional: without it the API starts and stores no credential, and with one that is not 32 bytes in base64 it refuses to start, saying what to set and not repeating the key. The API reads the model configuration when it starts (`LLM_CONFIG_PATH`, `config/models.yaml` by default, with the environment's overrides), to show what each role resolves to and to check a workspace's choice of models; one that cannot be read or is not valid stops the start, as it stops the worker's.

The API finds Temporal through `TEMPORAL_ADDRESS` and `TEMPORAL_NAMESPACE`, read the same way as by the worker (`WorkflowServer` in core's `workflow_server.py`): empty means `localhost:7233` and `default`. It does not connect when it starts. The first analysis that is started, or the first decision on a proposal, connects, and the connection is kept; so the API starts without Temporal, and projects, run status, profile review and proposals work without it (a decision is then stored, and its run reads it later: see [Policy gate](#policy-gate)). One adapter (`TemporalWorkflows` in `temporal_workflows.py`) starts the workflows of every kind of run over that one connection: it is handed a `WorkflowStart` (core's `workflow_start.py`), the workflow's name, id, task queue and input as the run's contract describes it (`analysis_workflow` in `workflow_contract.py` for an analysis), and knows no workflow by name. It starts analyses and research runs; the chat's follow-up turn is started by the `Research` workflow, not by the API. The same adapter tells a run that waits for a person of a decision (`tell_decided`, the signal `proposal_decided` with the proposal's id).

Every profile response (`ProfileVersionResponse`) names the version it was edited from (`edited_from_version`, null for a version an analysis stored) and the commit that was analysed (`commit_sha`); no response carries the row id of a version or a snapshot.

The nine lists (the eight above and the research runs of [The researcher](#the-researcher)) are paged the same way. A request takes `limit` (1 to 100, 50 when left out) and `cursor`; the answer holds its items under a named key (`projects`, `runs` for analyses and for research runs, `versions`, `proposals`, `chats`, `messages`, `events`) and `next_cursor`, which is null on the last page and otherwise the `cursor` of the next request. A cursor is the position of the last item returned (creation time and id for projects, runs and messages, the version number for versions, the last activity for chats, the event's `id` for events), so the next page starts after that item whatever was added in between: a row added between two requests neither repeats an item nor hides one. A walk that has begun does not see a row added at the head; reading from the start again does. A client passes a cursor back unchanged and never builds one; a value the API did not write is a 422. The orderings and queries are in the stores (`db/pages.py` and the store modules beside it), the query parameters in `apps/api/src/openmarketer_api/pagination.py`.

**The stream of a chat's events** (`streamChatEvents`, `apps/api/src/openmarketer_api/event_stream.py`). The stream begins with a `retry: 1000` line (a browser waits a second before it reconnects), then reads the `run_event` table about once a second, each read in a short transaction of its own, at most 100 events a read, and reads again at once after a read that found events. Each event is sent as `id: <id>`, `event: <kind>` and `data: <the event as JSON, the same object listChatEvents returns>`. While nothing happens a `: keep-alive` comment is sent every 15 seconds. The stream ends after 5 minutes, when the chat is gone, or when the database cannot be read, and the browser's `EventSource` reconnects with `Last-Event-ID`, which is where the next stream starts; so no request holds the server for longer, whatever a client does. The answer carries `Cache-Control: no-cache` and `X-Accel-Buffering: no`. The request's own session is used only to answer a missing chat with 404, and ends before the first event is sent. The numbers are `StreamTiming`'s defaults. There is no `LISTEN`/`NOTIFY`: a new event reaches an open stream at the next read. Why a reader never misses an event that commits late is under [Chat events and the follow-up turn](#chat-events-and-the-follow-up-turn).

**The stream of the workspace's events** (`streamWorkspaceEvents`) is the same mechanism over every run event of the workspace's projects (`events_of_workspace` in `db/run_events.py`): this is what the dashboard's notifications follow, wherever the person is. Its one difference is where it starts without a cursor: after the newest event of the workspace (`latest_event_id_of_workspace`), so a client that opens it afresh hears what happens from then on, not the whole history. Both streams draw on one count of open streams per process (`OpenStreams`), and both answer 503 `too_many_streams` beyond it.

A project, a list or a chat asked for under another workspace is answered exactly like one that does not exist: `project_not_found` for a project and for the lists under it, `chat_not_found` for a chat the project does not have, `profile_not_found` for a version, as for the draft and the approved profile.

Errors have one shape, `{"code": ..., "message": ...}`, except request validation, which is FastAPI's 422. A conflict over an existing project adds `existing_project_id`; the field is left out of every other error, never null. On the three credential routes a 422 does not quote the request, because the request holds a secret: FastAPI's answer repeats what was sent (`input`, `ctx`, and the name a client gave an unexpected field), so there each error keeps its `type`, its `msg` and a `loc` made only of names the API defines (`secret_bodies.py`, a route class set on that router; every other route keeps FastAPI's answer). A credential's name in the path has a fixed form (a lower-case letter, then up to 63 lower-case letters, digits or underscores), so a secret pasted there by mistake is a 422 that does not repeat it, or, if it happens to have that form, a 404 that does not repeat it either. The error the route class raises does not lead back to FastAPI's original, which holds the body. A value that breaks core's rule is answered in the same shape, beside `body.value`, with the rule and never the value. The contract is `apps/api/openapi.json`: `make openapi` writes it without starting the server, and a test fails when the committed file no longer matches the routes. The dashboard's types are generated from it (`pnpm api:types` in `apps/web`), and a check in `make lint` and CI fails when they are stale.

When the workflow of a run cannot be started (Temporal unreachable within 5 seconds, or refusing), the run that was just stored is marked `failed` with the text "the analysis could not be handed to a worker", and the request is answered 503 with the code `analysis_not_started` and the run's id in the message. The failed run does not block the project: the client starts a new one. The order is fixed in `request_analysis` (`repository_analysis/request.py`): the run is committed first, so the worker finds the row; then the workflow is started. A workflow that already exists for the run counts as started.

What the API does not do yet:

- **The lists of projects and of runs sort every row of the workspace or of the project to return one page.** `project` is indexed on `workspace_id` and `analysis_run` on `project_id`, neither on the creation time, so a page costs a read of all the workspace's projects, or all the project's runs, and a top-N sort. That is nothing at the sizes of a single-user installation; an index on `(workspace_id, created_at DESC, id DESC)` and one on `(project_id, created_at DESC, id DESC)` would make a page cost a page, and they need a migration that has not been written. The list of versions reads only its page, backwards through the unique index on `(project_id, version)`.
- **A list has no total and no filter.** A client learns that more follows, not how much; runs cannot be filtered by status.
- **There is no login.** The user is whoever is at this machine: a request is served only if it comes from a loopback address, carries exactly one `Host` header that is `localhost`, `127.0.0.1` or `[::1]` with an optional numeric port, and, when a browser sent an `Origin`, every such header is `http://` or `https://` followed by one of those. Both headers are matched whole, not parsed: a missing, repeated or malformed `Host` (`localhost@evil.example`, `localhost#.evil.example`) and a malformed `Origin` are refused. Everything else gets 403. The server binds to `127.0.0.1`. Do not put it behind a proxy or bind it to another address: a proxy on the same machine makes every request look local. Approvals are recorded under one fixed identifier for the local user (`LOCAL_USER_ID` in `identity.py`); it never comes from the request. The credential routes raise the stakes of this: any process on this machine can `PUT` or `DELETE` a credential on `127.0.0.1:8000` directly, a replaced model key routes every later analysis's repository content through another account, and who stored a value is recorded as the same fixed user (see [Stored credentials](#stored-credentials)).
- **A run cannot be cancelled through the API**, and nothing times out a run whose workflow is lost; the cases are listed under [The worker](#the-worker).
- **A start can be answered 503 although a workflow was started.** If Temporal starts the workflow but its answer does not arrive within 10 seconds, the run is marked failed; the worker then finds a finished run and does not analyse it.
- **Any https host is cloned from**, including hosts on the local network. That is acceptable while only the local user can call the API and has to be decided before it is exposed.
- **A browser on another origin is not served.** There is no CORS configuration; the dashboard calls the API through its own server (see [The dashboard](#the-dashboard)).

How it is put together:

- **Types come from the contract.** `pnpm api:types` writes `src/lib/api/schema.d.ts` from `apps/api/openapi.json` (`make openapi` runs it too), and `pnpm api:types:check`, part of `make lint` and of the web job in CI, fails when the file is stale. `src/lib/api/types.ts` only gives the generated schemas short names. Requests go through `openapi-fetch` and TanStack Query hooks in `src/lib/api/`; the three lists are infinite queries that ask for 20 items at a time and merge the pages, showing an item once if a new arrival moved it onto the next page.
- **The parts around a screen read their own copies.** The sidebar and the project's frame are on the page before the screen inside them, and a streamed screen hydrates later. If they shared the screen's query keys, the screen would hydrate from data they had already fetched and not match the server's HTML, which React reports as a hydration error and repairs by rendering again (this happened on the Approvals screen before, between the frame's count of waiting proposals and the screen's list). They read the project, the newest page of proposals and the newest page of chats under keys of their own, below the keys of what they show (`queryKeys.shellProject`, `queryKeys.shellWaitingProposals`, `queryKeys.shellChats`), so invalidating the project, its proposals or its chats refreshes them too. The cost is a second request for the project and for the page of proposals when a screen reads them as well.
- **A sent message outlives the screen that sent it.** `useSendChatMessage` is a mutation under one key per project, so the new-chat screen can send the first message and move to the chat, and the chat finds the message in the mutation cache (`useSubmission`) to show it as sent, or as failed. The mutation ends only once the stored exchange has been read back, so the message does not disappear between the answer and the refreshed list.
- **What waits for a person is told wherever they are.** The frame of every screen carries a bell at its top right with how many proposals wait (built with the notifications). It reads `listWaitingProposals` once and then follows `streamWorkspaceEvents`, the workspace's own stream of every run event, through the proxy: a `proposal_waiting`, `proposal_decided` or `proposal_expired` event refreshes the count at once, so it appears and disappears in the moment, on any screen; after every (re)connect the list is read again, which is what catches a proposal stored while no stream was open. Nothing is polled. Each entry links to its project's Approvals screen, where the decision is made — or to the run's card in a chat, which decides it there (the Chat row above). The bell is the dashboard's notification surface in its first form: one kind of notification, built so that others can be added the same way (`useWorkspaceEvents` hands every event to the surface; `refreshedByWorkspaceEvent` says what each kind refreshes).
- **The browser never calls the API.** It calls the dashboard's own route handler, `src/app/api/v1/[...path]/route.ts`, which forwards to the API from the server (`OPENMARKETER_API_URL`, default `http://127.0.0.1:8000`). The rules are in `src/lib/server/api-proxy.ts`:
  - the `Host` header must name this machine, so a foreign name pointed at 127.0.0.1 is refused;
  - `Sec-Fetch-Site`, when the browser sends it, must be `same-origin` (or `none` for a read);
  - `Origin`, when present, must be the dashboard's own origin, and every request that is not a `GET` (a `POST`, a `PUT`, a `DELETE`) must carry it. This replaces the API's own `Origin` check, which a server-side proxy hides from the API: a page of another site that posts to `/api/v1/projects/{id}/profile/versions/{n}/approval` is answered 403 here and nothing is forwarded;
  - only the forty-one method-and-path pairs the dashboard uses are forwarded (twenty-two reads, nineteen writes: nine `POST`, five `PUT`, five `DELETE`; counted in `ALLOWED_ROUTES` on 2026-10-18, while the notifications were being built), matched whole with a UUID for each identifier, digits for the version, and the fixed form of a credential's name and of a tier's and a role's name; `getDraftProfile` and `getApprovedProfile` are not among them, because the dashboard no longer uses them;
  - the nine lists take `limit` (1 to 100) and `cursor` (up to 200 URL-safe characters), each once, and each event stream takes `after`, once, as an event id. Any other query parameter, a value outside those forms, and any query on another route is refused with 400 rather than dropped, so a caller learns it had no effect. A cursor of the right form that the API did not issue is the API's 422;
  - the upstream address is built from the configured origin, the matched path and the validated parameters, never from the incoming URL, and no cookie or browser header travels upstream, except `Last-Event-ID` on an event stream, checked to be an event id;
  - an event stream's answer is passed through as it arrives, not read whole, and the upstream request ends when the browser leaves;
  - a body must be `application/json` and at most 1 MB, and a `DELETE` that carries one is refused with 400. A body can hold a secret (a credential being stored): it is passed on to the API and nowhere else, and the proxy neither logs it nor puts it in an answer.
- **A typed secret does not stay in the query cache.** TanStack Query keeps the variables of a mutation for as long as it keeps the mutation. `setCredential` is therefore given a `OneTimeValue` (`src/lib/api/one-time-value.ts`), a holder the request empties, and the finished mutation is dropped at once (`gcTime: 0`); the field is cleared after a save. It is not encryption, and the value is in the page's memory while it is being typed. The field is marked for password managers to leave alone; whether they do was not tried.
- **The dashboard listens on 127.0.0.1 only** (`next dev` and `next start` default to all interfaces; the scripts pass `--hostname 127.0.0.1`), and every page is sent with `frame-ancestors 'none'`, so another site cannot put the approve button in a frame.
- **Profile text is shown as text.** Nothing from a profile, a project or a run is rendered as HTML or Markdown or turned into a link automatically. A repository URL is a link only when it is `https://`; anything else, such as the `file://` address of a project stored by the command line, is text. An evidence reference becomes a link only for a repository on github.com, gitlab.com or bitbucket.org, built from a fixed origin and encoded path segments (`src/lib/profile/evidence-link.ts`). With the version's `commit_sha` it is a permalink to the file at the analysed commit; the value is used only if it is a full hexadecimal commit id. Without one the link points at the default branch as it is today, and the screen says which of the two applies. A palette colour reaches a style only if it is a six-digit hex colour. The one text drawn as markup is a chat message's own words, as markdown, with the rules in the Chat row of the screens above.
- **Design tokens are in one file**, `src/app/globals.css`: colour (light and dark, following the system setting), type scale, radius, layout measures and motion, as Tailwind 4 theme variables.

What the dashboard does not do:

- **The comparison between versions is a list, not a diff.** For a version that was edited from another, the screen names what differs from that parent: the values the dashboard can edit by name ("Status of sync", "Product name"), anything else by its part ("Measurement", "Evidence or confidence of sync"), and features added or removed. It does not show the old and the new text, and it compares with the parent only, not any two versions.
- **"Needs your attention" is a reading aid, decided in the browser.** A part is listed when a feature's status is `unknown`, when it cites no evidence, or when its confidence is below 0.6 (`src/lib/profile/confidence.ts`). Nothing is blocked or allowed by it. If the product defines what needs review, the API should say so and the dashboard should display it. The same holds for "a draft awaits review", which the dashboard takes to mean a draft newer than the approved version.
- **Editing covers part of the profile.** The product name, a feature's description and status, the brand voice, the primary audience and the business model type can be changed. Lists (platforms, pains, palette), evidence, confidence, and adding or removing a feature cannot.
- **A list is refreshed when something is done, not by itself.** Only an unfinished run is polled. A project created, a run started or a version approved somewhere else appears on the next visit, when the window is focused again, or on reload — a proposal that waits is the exception, which the notification bell hears about as it is stored (above). The sidebar names no project; another project is chosen from the projects page.
- **The chat waits for the whole answer.** The text of an answer is not streamed: the API answers `sendChatMessage` when the turn ends, and what is shown live meanwhile are the turn's steps, not its words. The chat cannot be renamed or deleted, and the sidebar lists the newest page of chats only, with no "all chats" page. A message that failed is kept in the tab that sent it, not across a reload.
- **An earlier version of the dashboard kept a list in the browser's local storage** (key `openmarketer.dashboard.remembered.v1`). Nothing reads or removes it now; it is inert.
- **No light/dark switch** (it follows the system), no sign-in, no cancelling of a run, no project renaming, no search or filter in a list (the Approvals screen splits what it has loaded by status, in the browser, because the proxy forwards no `status` filter).

### Analysis runs

The design runs an analysis in a Temporal workflow that the API starts. `db/analysis_runs.py` and the `analysis_run` table hold the state of such a run, so the API and the worker share it and it survives a restart of either. The API requests a run and reads its status; the worker reports to it.

- `request_analysis_run` adds a `queued` run for a project. A project has at most one unfinished run (a partial unique index); a second request raises `AnalysisAlreadyRunning`, so a repeated request does not pay for the model twice.
- `mark_run_started`, `mark_run_succeeded` and `mark_run_failed` are what the worker reports. A run only moves forwards: `queued` to `running` to `succeeded`, or `queued` or `running` to `failed`. A report that repeats what is already recorded changes nothing, because Temporal can deliver an activity twice. A finished run is never changed (`AnalysisRunFinished`), and a run that was never started cannot succeed (`AnalysisRunNotStarted`).
- `analysis_run` reads one run: status, times, the failure message, and for a succeeded run the profile version it stored and that version's snapshot.
- `run_to_execute` gives a run's project and workspace from the run id alone, or nothing. It is the one read that is not scoped by a workspace, because it is what finds the scope: the worker's graph is handed a run by its kind and id, and everything it then does with the run goes through the scoped functions with what this returns. It says nothing else of the run and changes nothing.
- `save_analysis_of_project` in the evidence store stores a run's snapshot, evidence and draft profile under a project given by id, where the command line's `save_analysis` finds or creates the project by repository URL. The worker stores the result and reports the success in one transaction.

Every other function takes the workspace, the project and the run, including those the worker calls; a run of another workspace or project is treated like one that does not exist, and a project the workspace does not have is `ProjectNotFound` from `db/projects.py`. CHECK constraints keep a row consistent: a profile version if and only if the run succeeded, an error if and only if it failed, an end time if and only if it is finished, a start time once it is running. A foreign key over both columns makes the profile version belong to the run's project.

What this does not do:

- **No workflow id is stored.** The caller derives it from the run id (`analysis_workflow_id`).
- **Nothing here times a run out.** The workflow reports the failure; the cases in which it cannot are listed under [The worker](#the-worker).
- **Runs are deleted only with their project** (see [Deleting a project](#deleting-a-project)). There is no other clean-up and no way to cancel.
- **The failure message is stored as given**, cut to 2000 characters. What may be written there is the caller's decision; the worker's is described below.
- **A finished row is protected in code only.** Unlike profile versions there is no trigger, so SQL written by hand can rewrite a finished run within what the CHECK constraints allow.
- **The snapshot's repository is not compared with the project's** when a result is stored under a project id.
- **The list sorts all runs of the project.** `list_analysis_runs` returns a page of a project's runs, newest first, with the profile version of each succeeded run from the same statement; no index covers the ordering (see [The API](#the-api)).
- **No access token.** The token for a private repository does not pass through these functions and is not part of a run's row. One stored from the dashboard is in the `credential` table, encrypted (see [Stored credentials](#stored-credentials)).

### The worker

`make worker` runs a Temporal worker (`python -m openmarketer_worker`) that executes four workflows, each on a task queue of its own: `AnalyzeRepository` on `openmarketer-analysis` (this section), `Research` on `openmarketer-research` (see [The researcher](#the-researcher)), `CreativeStudio` on `openmarketer-studio` (see [The creative studio in the worker](#the-creative-studio-in-the-worker)) and `ChatFollowUp` on `openmarketer-orchestrator` (see [Chat events and the follow-up turn](#chat-events-and-the-follow-up-turn)). It needs the dev stack, a migrated database, and in `.env`: `DATABASE_URL`, and `TEMPORAL_ADDRESS` set to `localhost:7233` or left empty (the value in `.env.example`, `temporal:7233`, is the host name inside the compose network and does not resolve from the host, like the one in `DATABASE_URL`). The worker refuses to start, with the name of the setting, when one of these is missing or wrong or Temporal cannot be reached, and when `DATABASE_URL` is not the URL of a PostgreSQL database, which the checkpoints need, or carries an option the PostgreSQL driver does not accept; the message names the problem and does not repeat the URL. It also refuses to start when the model configuration cannot be read, when `GITLAB_HOST` is not a host name, when `ENCRYPTION_KEY` is set and is not 32 bytes in base64 (the message says what to set and does not repeat the key), and when the folder for the runs' clones (below) exists and is not a folder of the user the worker runs as.

**The worker reads no credential when it starts.** Until this change it asked for the model provider's key at start-up and stopped without one, and it read the repository tokens once, then. It now starts without `OPENROUTER_API_KEY`: the key is resolved for the run's workspace when an attempt at a graph step begins, and the repository tokens each time a clone or a fetch is made, from the environment or from what was stored in the dashboard (`credentials.py` at the top level of the worker; see [Stored credentials](#stored-credentials)). A run that finds no key ends `failed` at its first step, before anything is cloned, with a sentence that says where to set one. `ENCRYPTION_KEY` is optional; without it a stored credential cannot be read, which the run that needs it is told.

What the API and the worker share is in `openmarketer_core/repository_analysis/workflow_contract.py`, which imports nothing from Temporal: the workflow name, the task queue, `analysis_workflow_id(run_id)`, the kind of run (`analysis-run`, which the analyzer's agent is declared with and a run's thread name starts with) and the workflow's input, `AnalyzeRepositoryInput` (workspace, project and run identifiers). Temporal keeps every input and result in the workflow history, readable in its UI, so nothing else travels through it: no repository URL, no token, no profile. The worker reads the repository URL from the database.

The analyzer is an agent on the [agent runtime](#agent-runtime), and `AnalyzeRepository` is that agent's workflow with two hooks of its own (`repository_analyzer/workflow.py`, 84 lines). An analysis is five activities in a row, or six when it fails. The middle three are the runtime's; what they do for an analysis is in `repository_analyzer/analysis.py`:

| Activity | What it does | One attempt may take | Attempts |
|---|---|---|---|
| `start_run` (hook `before`) | `mark_run_started`; returns the limits of a graph step, which the workflow cannot read from the environment itself | 30 s | 5, half a second apart at first. A run that is not found is tried again, because the request that created it may not have committed yet |
| `run_graph_step`, first | Takes the run's thread, reads the run's project and workspace by the run id (`run_to_execute` in `db/analysis_runs.py`) and starts the graph. Its first node, `clone`, asks for the action `clone_repository` with the run's three identifiers, and the graph pauses. Nothing is cloned and no model is called, but the attempt's chat model is made first, which resolves the model provider's key for the run's workspace: a run with no key ends here | 30 min (`ANALYSIS_TIMEOUT_MINUTES`); a heartbeat every 20 s, missed for 60 s, ends the attempt | 5 (`ANALYSIS_MAX_ATTEMPTS`), waiting 1, 2, 4 and 8 minutes between them |
| `run_action` for `clone_repository` | Reads the project's URL, resolves the repository tokens of the run's workspace if a clone is really made, clones into the run's folder on this worker's disk, scans and redacts it (intake), and returns `{"commit_sha": ...}` and nothing else | 15 min; a heartbeat every 20 s, missed for 60 s, ends the attempt | 5, waiting 1, 2, 4 and 8 minutes. These are constants declared on the action in core (`analyzer_agent/definitions.py`), not settings |
| `run_graph_step`, second | Continues the graph with the outcome of the clone: keeps the commit in the graph's state, runs the extractors and builds the repository map (`prepare`), runs the loop of model calls and tool calls until a profile is accepted, then stores the result (`save_analysis_of_project`) and marks the run succeeded in one transaction (`AnalysisWork.finish`). Returns `{"profile_id": ...}` | as the first | as the first |
| `record_failure` (hook `failed`) | `mark_run_failed` with the reason. Runs whenever anything above ends without a result, also on a timeout and on cancellation | 30 s | Until it works, for up to an hour |
| `forget_run` | Removes the run's checkpoints and then the run's clone from this worker's disk. Runs last in every case: after success, after `record_failure`, after a cancellation | 30 s | Until it works, for up to an hour; it does not fail for a database that is down |

The activity `analyse_and_store`, which did all of the middle three in one attempt, no longer exists.

**The commit is pinned for the life of a run.** The clone happens once, and the commit it read is in the graph's state, which is checkpointed. Every later attempt reads that commit, whatever the repository's branch has become since, so the analyzer's limits (`max_steps`, `max_cost_usd`, `max_submissions`) hold for the whole run and another attempt pays for at most the one model call that was in flight. The steps and the cost spent carry over; the two limits themselves are read for the workspace at each attempt (see [Workspace settings](#workspace-settings-models-and-analysis-limits)), so a limit changed in the dashboard while a run is in progress applies from its next attempt, to what the run has already spent. Before this change each attempt cloned the default branch again and an analysis started over, with its budget, when it found a new commit; that case no longer exists.

**Which limit is which.** `ANALYSIS_TIMEOUT_MINUTES` and `ANALYSIS_MAX_ATTEMPTS` limit each of the two graph steps separately, not the run: with the defaults a run can make up to five attempts of thirty minutes at the first step and five more at the second. The first step does almost nothing, so in practice the numbers bound the model's work. The clone's limits are the constants in the table. The reasons for every number are in the docstring of `repository_analyzer/policy.py` and beside the constants in `definitions.py`. The worker keeps everything of the repository analyzer in `repository_analyzer/` (and the researcher's in `researcher/`, the chat's follow-up turn in `orchestrator/`), and above it only the process (`main.py`), its own settings (`settings.py`, which hold `ENCRYPTION_KEY`), the schedule of checkpoint cleanups and what every agent shares: `agent_runtime/` and `credentials.py`, which resolves the installation's credentials for a run's workspace.

**What is tried again.** The retries are for what can pass: a worker that died or was restarted, a model provider that did not answer, timed out (HTTP 408), limited the rate (429) or failed (5xx), a database that was unreachable, and an earlier attempt at the same step that is still running (below). An unexpected error is retried too. A repository that cannot be cloned, a URL that is not `https://`, a request the model provider refuses (any other 4xx: a wrong key, no credit, an unknown model), a profile the analyzer could not produce within its limits (`AnalysisError`), a model key that is set nowhere, a stored credential that cannot be read (`CREDENTIAL_FAILURES` in `analysis.py`), a configuration error and a run that does not exist or is already finished are not tried again. A database that fails while a credential is resolved is tried again like any other failure of the database. `LLMError.may_pass` in core holds the rule for the provider. A refused repository travels a longer way than before: the clone's handler fails for good with the sentence, the runtime tells the graph a failed outcome, the `clone` node raises `AnalysisError` with those words, and the step fails for good with them.

**Where a run's clone lives** (`repository_analyzer/clones.py`, `LocalClones`). One folder per run, `<system temporary folder>/openmarketer-analysis/<run id>/`, with the repository in `repo` under it; the name comes from the run's id and from nothing a repository or a URL says, and the root and each run's folder are readable by the worker's user only (mode 0700). What is kept of a clone is intake's result, in the memory of the worker process, so the repository is still read only through `RepoFiles` after the secret scan. The disk is one worker's own:

- A step on the worker that made the clone reads it and does not clone again.
- A step on another worker, or on this one after a restart or after the folder was removed, fetches the run's commit again (`at_commit`, through intake's fetch of one commit) and reads that.
- The clone is released by the runtime's `forget_run`, which calls the analyzer's run-ended function (`release_the_clone` in `wiring.py`) after the checkpoints are forgotten, for a run that succeeded, failed or was cancelled. An attempt that finishes and finds its run recorded failed meanwhile releases it too. A clone that fails leaves nothing of the run on the disk.
- What a dead worker left is removed by a sweep when a worker starts, and only then: every entry under the root that was last written longer ago than a run can last (`longest_analysis_seconds`, about 33 hours with the defaults) is removed. There is no periodic sweep.

`longest_analysis_seconds` (`policy.py`) is the bound both the sweep and the checkpoint cleanup use. It sums what the workflow can spend: `start_run` at every attempt's limit with its waits, each of the two graph steps at every attempt's limit with the waits between them, the clone the same way, the hour `record_failure` keeps trying, the hour `forget_run` keeps trying, and a day's allowance for attempts waiting while no worker serves the queue. With the defaults that is 118,957.5 seconds, 33 hours and 3 minutes (it was 27 hours 45 minutes before the clone and the second step were counted). `test_policy.py` writes the parts out as numbers.

- **A repeated activity does not repeat its work.** A repeated first step finds the thread waiting and returns the same request. A repeated clone answers with the clone this worker holds, so with the commit the first one read. A repeated second step continues from the last checkpoint; when the graph had already finished, it stores the profile without asking the model, and when the run already has its result it stores nothing.
- **One attempt at a time works on a run's thread.** An attempt at a step takes the run's checkpoints before it does anything, with a PostgreSQL advisory lock on its own connection, and holds them until its thread returns. Temporal can give up on an attempt whose thread is still working (after the time limit, a missed heartbeat, or when the worker is asked to stop); the next attempt is then refused at once with the retried failure `AttemptStillRunning`, and analyses nothing. It is tried again after the usual wait. The database releases the lock when the holder returns, its connection is lost or its process dies. The run's transition rules remain underneath: if two attempts did both analyse, the first to finish stores its result and the second's transaction is rolled back, so there is one profile version per run. The clone has no such lock in the database; within one worker process `LocalClones` lets one thread at a time work on a run's clone.
- **The failure message** holds nothing a repository host or a model provider wrote. A clone that fails gives one of six fixed sentences (see [Cloning from an untrusted host](#cloning-from-an-untrusted-host)); a refused model call gives `the model provider answered HTTP <status>`; a timeout, a lost worker, a cancellation, a failed write and an unexpected error each have a fixed sentence. A credential that is missing or unreadable gives the sentence of its error, which names what to set and holds no value: "the model provider's API key is not set: set it in the dashboard's Settings, or with the environment variable OPENROUTER_API_KEY" (for a model configuration that names another variable, only that variable is named), or "the stored value of github_token cannot be read: set ENCRYPTION_KEY to the key it was stored with, or set the credential again". What git printed and what the provider answered go to the worker's log. Any other error of the analysis is passed on with every path under the run's folder replaced by `<clone>` (`failure_message` in `repository_analysis/failures.py`); of those, a profile that does not match the schema lists the fields that are wrong, which the model wrote. Only failures of the types the analyzer declared as worded (`WORDED_BY_THE_ACTIVITY` in `steps.py`) pass with their message; any other is recorded in a fixed sentence. The runtime's own sentences ("the action did not finish in time", "an earlier attempt at the run is still running") are turned into the analyzer's ("the analysis did not finish in time", "an earlier attempt at the analysis is still running") by `in_the_analyzers_words`. Activities attach no cause to a failure, because Temporal stores causes too.
- **What Temporal's history holds**: the three identifiers of the run (the workflow's input, `start_run`'s input and the payload of the clone request), the kind `analysis-run` with the run id in each step's input, the limits, the commit that was cloned, the id of the stored profile version, the failure message, and for a failed activity the stack trace Temporal records (file names and source lines of the worker's code, no values). Nothing else: no repository URL, no folder, no profile, nothing the analyzer read, and no credential. A credential is resolved inside the activity that uses it and is in no input, result, failure or checkpoint; a test runs an analysis with a stored key and a stored token and searches the decoded history for both.
- **Left-over checkpoints are removed by every worker** when it starts and every ten minutes after that (`checkpoint_cleanup.py` at the top level of the worker, since the checkpoint tables are shared by every graph). That module keeps the schedule and knows no rule: each agent's wiring hands it a cleanup for each kind of run that keeps checkpoints, and every round runs each of them in a transaction of its own, so one that fails does not keep the others from running. Today there is one, for analysis runs (the rule in core's `db/checkpoint_cleanup.py`, handed over by `repository_analyzer/wiring.py`). It never changes a run. A cleanup that fails is logged and tried again the next time; it stops neither the worker nor an analysis.
- **A project stored from the command line with a local folder is refused**: the worker clones `https://` URLs only.

What the worker does not do:

- **Some failures leave a run unfinished**, and an unfinished run blocks its project until the row is changed by hand:
  - the workflow is terminated (from the UI, the CLI, or by an execution timeout set by whoever started it): a terminated workflow runs no further code;
  - Temporal loses the workflow or its history (for the dev stack: `make reset`, which deletes its volume), or the API process died between committing the run and starting its workflow, or the database refused the API's attempt to mark such a run failed;
  - the database stays unreachable for the hour `record_failure` keeps trying;
  - no worker is running: the run waits, `queued` or `running`, until one is started. This is the intended behaviour and has no time limit.
- **Workflows that were in flight under the earlier `AnalyzeRepository` cannot be continued by this code.** The earlier workflow scheduled `start_run` and then `analyse_and_store`; this one schedules `start_run` and then `run_graph_step`. A worker with this code that replays the history of a run started before it meets an activity it would not have scheduled, which Temporal reports as a non-deterministic workflow, and the run hangs. There is no versioning or patch marker in the workflow. Let the queue drain, or terminate what is in flight (and mark those runs failed by hand), before deploying. This is read from the two versions of the workflow; it was not tried.
- **No cancellation of the work itself.** Cancelling the workflow marks the run failed, but the thread that is analysing or cloning cannot be stopped: it runs until the analyzer's own limits or git's time limit end it, and its result is then discarded. The same holds when a worker is stopped: the process ends only after the work in progress returns.
- **An attempt that outlives the retries fails the run.** While an attempt that was given up on is still running, the attempts after it are refused, 1, 2, 4 and 8 minutes apart. If it runs for longer than the attempts that are left wait, the run ends `failed` with "an earlier attempt at the analysis is still running", although that attempt may still produce a profile, which is then discarded.
- **A heartbeat shows that the worker process is alive, not that the analysis is making progress.** An analysis that hangs is ended by the attempt's time limit.
- **The extractors run twice in a successful analysis**: once in `prepare`, for the hints the model is given, and once when the result is stored, for the evidence rows, because what they found is not kept in the graph's state. They are deterministic and read the same commit, and cost time, not money. They run again, like `prepare` as a whole, in an attempt that continues from before `prepare` finished.
- **A clone can stay on a disk after its run ended.** `forget_run` releases the clone on the worker that happens to execute it. With more than one worker on the queue that need not be the worker that holds the clone, and a clone on another worker stays until that worker next starts and the folder is older than the bound. The same holds for the clone of a run whose workflow was terminated or lost, and for a worker that is killed: its folders stay until a worker starts on that disk after the bound. This is read from the code (`LocalClones` is per process, and Temporal gives an activity to any worker of the queue); it was not observed, since only one worker has been run.
- **The clone's time limit and retries are not exercised on a real Temporal server with a real clone.** The workflow tests check that the clone is scheduled under the limits declared on the action and how a failed outcome ends the run; a clone that actually takes too long, or a worker that dies during one, is covered for git's own time limit in core's clone tests and not through the workflow.
- **A workflow started with a real run id and another workspace's or project's identifiers has that run's thread forgotten and its clone released.** Nothing is analysed, stored or recorded for it: `start_run` and `record_failure` are scoped to the workspace and the project and find no such run. But the thread and the clone are found by the kind and the run id alone, so `forget_run` at the end of that workflow removes them, and a real run of that id that was in progress would continue from nothing. The API derives a workflow's input from the row it stored, so this needs someone who can start workflows on the Temporal server directly.
- **No progress.** An analysis says `running`; it does not say which step it is at. The analyzer declares no progress function (the researcher does, see [Agent runtime](#agent-runtime)), and the checkpoints are not read for that.
- **More code than before.** The worker's side of the analyzer is 1,235 lines in ten modules, counted with `wc -l` on 2026-10-12; it was 1,122 in nine before credentials were resolved at each attempt, and this page recorded 747 in seven before the analyzer moved onto the runtime. Most of the difference is `clones.py` (223) and `analysis.py` (294), and the workflow itself shrank from 103 lines to 84. `credentials.py` at the worker's top level adds 102. In core, `analyzer_agent/` went from 783 lines to 836. The wiring an agent must write to stand between its graph and the worker's database, disk and model is the known cost of the runtime.

### Graph checkpoints

The design stores the checkpoints of a graph in PostgreSQL so that it can resume after a failure (the report's section "Agent graphs and durable workflows"). That is built, and the repository analyzer uses it when the worker runs it. The analyzer's graph is compiled from its agent (`compile_agent`, by `AgentSteps`) with the run's checkpoint store, and core's `GraphThread` takes it step by step on a thread named for the analysis run (`analysis-run:` followed by the run's id). LangGraph's own PostgreSQL checkpointer stores a checkpoint after every node, and each is in the database before the next node starts. The command line and the benchmark do not use any of this: `analyze` runs the same graph in memory from its `prepare` node (`run_from`), with a repository the caller cloned, and an interrupted run starts again.

How an attempt at a step begins is no longer a rule of the analyzer (`resumption` in `rules.py`, with its four cases and `Analysis.resumption`, is gone). It is what `GraphThread.advance` does for every graph:

| What the thread holds | What the attempt does |
|---|---|
| Nothing | Starts the graph from the run's initial state (the run's identifiers, nothing read, nothing spent) |
| A pause at the clone, and no outcome is given | Returns the same request and runs nothing |
| A pause at the clone, and the clone's outcome | Continues from the pause with the outcome |
| Checkpoints after the clone, no accepted profile | Continues after the last finished node. Steps, cost, submissions and the conversation carry over, so `max_steps`, `max_cost_usd` and `max_submissions` count every attempt of the run |
| A finished graph | Runs no node and calls no model; `finish` stores the accepted profile, or finds it stored |

Nothing is compared before continuing: a thread that has checkpoints is continued. The commit is part of the state, so the question of "the same input" that the earlier rule asked does not arise.

The node that was running when an attempt stopped is run again. `run_tools` only reads files; a repeated `call_model` pays for one model call; a repeated `prepare` runs the extractors again; a repeated `clone` asks for the same action and is given the same outcome. So a model call that finished and whose node was recorded is not made again, and at most the one call in flight is paid for twice.

How it is put together:

- **The store is shared; each kind of run brings its own rules.** `graph_checkpoints/` is what every graph uses for checkpoints: the type a graph receives (`RunCheckpoints`, in a module that loads no database driver) and the PostgreSQL store (`postgres.py`: the connection, the attempt lock, the strict serializer). It holds no rule. The thread of a run is named by `thread_id(kind, run_id)` of `agent_runtime/threads.py`; for an analysis run that is `run_thread_id` in `db/analysis_runs.py`, with the prefix `ANALYSIS_RUN_THREADS`, and the cleanup rule of analysis runs touches only threads with that prefix. Another kind of run would name its threads with its own kind and bring its own rule. The analyzer is the only agent the product has.
- **The tables are the library's, created by a migration.** `checkpoints`, `checkpoint_blobs`, `checkpoint_writes` and `checkpoint_migrations` belong to `langgraph-checkpoint-postgres`, which defines them as a numbered list of statements and reads and writes them with its own SQL. They have no model in `db/models.py`. The fourth migration runs the library's statements 0 to 9 and records each number in `checkpoint_migrations` as the library's own `setup()` would, so `make migrate` creates them and nothing calls `setup()` when the worker runs. The range is fixed in the migration, and so is the text: the revision computes the SHA-256 of the statements exactly as it is about to send them and refuses to run when it differs from the hash recorded in the revision (taken with `langgraph-checkpoint-postgres` 3.1.2, after the statements were read), so a library version that words them differently is not run unread. The dependency is bounded below 4. The three `CREATE INDEX CONCURRENTLY` statements run without `CONCURRENTLY`, which cannot run inside the migration's transaction and makes no difference on tables created empty in it. `db/migrations/env.py` leaves the four tables out of autogenerate, which would otherwise propose dropping them. `CHECKPOINT_SCHEMA_VERSION` in `db/checkpoint_schema.py` is the last statement the migrations run; a test fails when the installed library has a later one, and another compares the migrated tables with the ones the library creates for itself. On a library upgrade, later statements go in a new revision that pins them the same way; the fourth revision and its hash are not edited.
- **What is read back is data, never something to run.** The library's serializer can rebuild an object by importing a module and calling a name that the stored bytes give, and by default does so for any name. Whoever could write to the checkpoint tables would then run code in the worker, which can read the model provider's key and the repository tokens: from its environment, and the stored ones with `ENCRYPTION_KEY`. The store is therefore built with the strict serializer (`JsonPlusSerializer(allowed_msgpack_modules=None)`), set in code and not by the environment: only the library's short list of plain value types is rebuilt, and anything else comes back as the plain data it was stored with. The analyzer's state is plain data, so nothing it stores needs more; what a node needs that is not plain data (the model client, the repository) is in the attempt's context, which is never stored. So the worker does not trust the tables for code. It does trust them for content: a conversation, a commit or a finished profile found for the run is continued or stored as it is, without a check that the worker wrote it.
- **One connection per attempt at a step** (`run_checkpoints` in `graph_checkpoints/postgres.py`), opened from `DATABASE_URL` translated to the driver's connection string and closed when the attempt ends, beside the worker's session pool. The same connection holds the attempt's advisory lock on the thread (see [The worker](#the-worker)); the lock belongs to the connection's session. An error of the driver is raised as `DatabaseError` with its first line, like any other failure of the database, and is retried by the worker.
- **A run's checkpoints are forgotten when the run ends**, by `forget_run`, the last activity of every run: after its profile is stored, after its failure is recorded, after a cancellation. A failure that will be tried again keeps them. Forgetting never fails the run: if it does not work, that is logged and the rows are left to the cleanup.
- **The cleanup removes what forgetting missed.** `remove_checkpoints_of_analysis_runs(session, longest_run=...)` (`db/checkpoint_cleanup.py`) deletes, in one statement, the rows of every thread named for an analysis run that no run needs. It considers only threads whose name starts with `analysis-run:`. Such a thread is kept only while the run it is named for is unfinished and either has not started or started less than `longest_run` ago, by the database's clock. So these go: threads of succeeded and failed runs, of runs that no longer exist, threads with the prefix followed by something that is not a run id, and threads of runs still marked `running` that started longer ago than a run can last. A thread of any other name is left alone, whatever its age. The last case is a run whose workflow was terminated or lost: its checkpoints are removed, the run itself stays `running` and still blocks its project. The bound is `longest_analysis_seconds` (see [The worker](#the-worker)), 33 hours and 3 minutes with the defaults. Workers with different `ANALYSIS_*` settings each apply their own bound. A run that outlasts it and is attempted after all starts from the beginning, with a new clone. A queued run is kept however long ago it was requested. It is maintenance across workspaces, not scoped to one, and returns only a count. The price of each rule touching only its own threads: a thread of a kind no rule knows, such as one named with a bare run id, is nobody's to remove and its rows stay.

What it does not do, and what to know before relying on it:

- **Repository content rests in these tables while a run is in flight.** A checkpoint holds the analyzer's conversation: the files it read, after intake's scan and redaction, and the drafted profile.
- **The tables have no workspace or project column.** A thread belongs to a workspace only through the run it is named for. Nothing in the database keeps one workspace's checkpoints from another: like every other table they are reachable by the one application role, with no row-level security, and here there is not even a column a policy could use. The code reaches a thread by the kind and the id of a run it was handed; the cleanup reads thread names across workspaces and no content. A consequence is listed under [The worker](#the-worker): a workflow started with a run id and the wrong workspace forgets that run's thread.
- **Rows can outlive their run by up to the cleanup interval of ten minutes**, or longer while no worker is running: a process killed between storing the profile and forgetting; an attempt that was given up on and still writes after its run was recorded failed (it forgets again when it returns). The checkpoints of a run whose workflow was terminated or lost stay much longer: until the run started longer ago than a run can last.
- **Removed is not erased.** Forgetting and the cleanup delete rows. PostgreSQL keeps the content in dead tuples until vacuum, in the write-ahead log, and in any backup taken meanwhile.
- **The worker needs a direct or session-mode connection to PostgreSQL.** The one-attempt-per-thread lock is an advisory lock of the session. A connection pooler in transaction mode hands the session to others between statements, which breaks the lock. This has not been tried against a pooler.
- **The cost a provider reports is not checked for NaN or a negative number.** `cost_usd` is taken from the reply as it is and added to the run's cost. Noticed, not tested, not fixed.
- **A thread grows with the square of the number of steps.** The library stores the whole conversation at each version. Measured by the agents who built the checkpoints, before the analyzer moved onto the runtime, on scripted runs with tool results of 5 to 40 KB per turn, as uncompressed payload of one thread: about 1.9 MB after 10 turns, 7.7 MB after 20 and 31 MB after 40, the default step limit. The rows are temporary. No live run was measured, and the measurement was not repeated on this code.
- **A deploy between two attempts of one run is not detected.** There is no version on a thread. If the new code changed the shape of the graph's state (`AnalyzerState`), a stored thread may not be continuable: a missing key raises, which the worker reports as an unexpected error and retries until the attempts are used up. The same goes for a changed graph (a node renamed or removed while a thread waits at it). Changed limits and prompts apply silently to the conversation the old code began. A thread stored by the analyzer before this change has neither the run's identifiers nor the commit in its state; see the note on workflows in flight under [The worker](#the-worker).
- **The checkpoint connection has no connect timeout of its own.** It waits as long as the driver does unless `DATABASE_URL` carries `connect_timeout`. The heartbeat does not end such a wait; the attempt's time limit does.
- **The command line stores no checkpoints.** `openmarketer analyze` runs the analyzer in memory, with or without `--save`, and an interrupted run starts again.
- **Nothing reads a checkpoint except to continue.** There is no progress report from them, no way to stop a running analysis through them, and no history kept after the run.

### Agent runtime

The design runs an agent's graph inside a Temporal activity (the report's section "Agent graphs and durable workflows"). A graph that only reads files and calls a model needs nothing more. A graph that has to clone a repository, send an e-mail, call a service or publish cannot do that inside the activity that runs it: the work needs timeouts and retries of its own, a key that makes a repeat harmless, and one place where a policy gate and an approval can stand. The agent runtime is the layer for that. A graph runs inside one activity until it finishes or asks for an *action*; the workflow runs the action as an activity of its own and gives what came of it back to the same graph thread, which continues where it paused. On top of it is a small set of decorators (below, "Writing an agent") with which an agent is declared. The repository analyzer runs on it, with one action, `clone_repository`, and the two kinds of run action (below, "The two run actions") are built and tested with a test agent; no product agent has one yet.

The code is in two places, and the dependency runs from the worker to core. Below, *core* is `packages/core/src/openmarketer_core/agent_runtime/` and *worker* is `apps/worker/src/openmarketer_worker/agent_runtime/`.

| Module | What it holds |
|---|---|
| core `actions.py`, `steps.py`, `threads.py` | Plain data and rules, no framework: `ActionRequest`, `ActionOutcome`, `ActionPolicy` (how an action is tried, within ceilings), `ActionDefinition` and `ActionCatalog` (the allowlist), and the run actions: `RunKind` (`START` or `WAIT`), `RunTarget` (the child workflow's name, its queue, how long it may take and how the payload becomes its input) and `ChildRun`, what the input builder is given; `GraphRunRef`, `StepOutcome` and the reasons a thread refuses a step (`StepError` and its kinds); `thread_id(kind, run_id)`, which gives `<kind>:<run id>` |
| core `model_input.py` | How text a model wrote is read: as strict JSON, into types that forbid unknown fields and name no file or import, with errors that name the fields at fault and never a value |
| core `agent.py`, `tools.py` | `Agent`, whose decorators (`action`, `node`, `edge`, `route`, `tool`, `progress`) only record what an agent is, as plain data, and `Agent.run_targets`, the actions that start another run; `Toolbox`, the tools an agent's model may call. No framework, so a workflow's module may load them |
| core `langgraph_steps.py`, `langgraph_agent.py` | The LangGraph side: `request_action`, which a node calls, and `GraphThread`, which takes a graph one step at a time on its thread; `compile_agent`, `AgentSteps` (the steps of an agent's runs, which the worker is handed, and which hands each node's progress to `record_progress` when one is given) and `run_from` (the same graph in memory, for a run with no workflow) |
| core `run_events.py` (beside `agent_runtime/`) | `RunEvent`, one thing a run did as the person watching it is shown it, and the kinds of the chat turn and of the researcher; plain data, bounded when it is built (see [Chat events and the follow-up turn](#chat-events-and-the-follow-up-turn)) |
| worker `vocabulary.py` | Plain data the workflow sandbox loads: activity names (`run_graph_step`, `run_action`, `prepare_run`, `forget_run`), failure types, fixed texts (a child run's failure among them), `GraphRunPolicy`, `DatabaseWritePolicy`, the bounds on what enters a history |
| worker `driver.py`, `workflow_support.py`, `workflow_dsl.py` | Workflow code: `run_graph_with_actions` (the driver), which branches on the run actions, `child_workflow_id`, `database_write` and `reason_shown`, and `agent_workflow`, which makes a class the workflow of an agent (and asks for `scope_of` when an action needs the run's project) |
| worker `activities.py`, `routes.py`, `activity_support.py`, `agent_worker.py` | For the worker process only: `RuntimeActivities` (`run_graph_step`, `run_action`, `prepare_run`, `forget_run`), the routes of an agent's actions (ordinary ones with handlers, run ones with a prepare callable), the helpers every activity needs (failure wording, heartbeats around blocking work, checkpoint access, the size of what a history would store), and `AgentWorker`, where handlers and prepare callables are declared and a registration is made |

**How a run goes.**

1. The agent's workflow, made by `agent_workflow`, refuses a run whose kind is not the agent's, calls its `before` hook, and then the driver, `run_graph_with_actions(run, actions=agent.policies, policy=...)`, with a `GraphRunRef` (the kind of run and its id: the thread is `<kind>:<run id>`).
2. The driver runs the activity `run_graph_step` with the run and, after the first step, what came of the last action. The activity refuses a run of another kind, takes the run's checkpoints for the attempt (an attempt is refused, and retried, while an earlier one still holds them) and calls the agent's `AgentGraph.advance` in a thread, with heartbeats. The graph runs until it finishes or a node calls `request_action`, which pauses it (a LangGraph interrupt). The step returns a `StepOutcome`: what the agent reports of the finished run, or the `ActionRequest` (`action_id`, `name`, `payload`) it waits for.
3. For a request, the driver refuses in the workflow a name that is not in the allowlist, and a run that has already asked for `max_actions` actions (200 unless the policy says otherwise). Either ends the run and nothing runs; the model's text never becomes the name of an activity. A request whose name is one of the agent's run targets takes the branch of "The two run actions" below. Otherwise it runs the activity `run_action` under that action's own `ActionPolicy`: attempt time limit, attempts, first wait (doubled after each) and, for an action that runs long, a heartbeat timeout.
4. `run_action` checks the request against the `ActionCatalog` of the agent's routes: the name must be in it and the payload must fit the action's model, read as strict JSON. A refusal names the action and the fields at fault and never repeats a value. The activity then calls the action's handler in a thread with the validated payload and an `ActionContext` whose `action_id` is the key of the work. The handler's result must be JSON of at most 32 KiB.
5. The driver takes the next step with the `ActionOutcome`, and `GraphThread.advance` continues the graph from where it paused, until a step says the graph finished. The workflow then calls its `after` hook, or `failed` when the run did not finish, and in every case the activity `forget_run`.

**The two run actions.** An action declared with a `RunTarget` (`@agent.action("research", run=RunTarget(...))`) starts another agent's run instead of running an activity of this worker, and the design's two kinds are built as `RunKind.START` and `RunKind.WAIT`.

- The child run's record is created by the activity `prepare_run`, through the callable the agent's wiring registered for that action (`@worker.prepare_run(Model)`, blocking, keyed by `RunContext.action_id`), which answers with the child run's id. The record-creating rule is the target's: the researcher's `research_run` gained a unique `origin_action_id` (the action's id), so the activity's at-least-once delivery finds the run it made instead of a second one. `registration` refuses at start-up a run action without a prepare callable, and a `longest_run` that does not cover what a waiting target may take.
- The child's workflow input is built in the workflow by `RunTarget.input_of` from the `ChildRun` (the parent's workspace and project, the child run's id, the action's id and payload): a plain function of a contract module, so a target whose run stores its request with its record (as a research run does) passes identifiers only.
- The child workflow's id is `child_workflow_id(run, action_id)`, derived from the parent's run and the action id, and the workflow starts the child itself by name, with the target's task queue; the engine records the start in the parent's history, so a retried workflow task replays it and a reset or a duplicate start is refused rather than making a second execution.
- `START` goes on at once with the child's run id as the outcome, `cancellation_type=ABANDON`: a later run, or a person, uses its result, and a cancelled parent leaves it running. `WAIT` waits with no graph running, for the child's small result, which is the outcome; a cancelled parent asks the child to cancel and waits for it to be over (the child's own workflow records that), and a child that fails or was cancelled independently is told to the graph in one fixed sentence (`CHILD_RUN_DID_NOT_FINISH`), never in the child's own words, which stay in the child's own record. `parent_close_policy=ABANDON` for both: a terminated parent does not take its child with it.
- The child keeps its own actions, its own approvals and its own checkpoints thread; nothing of the parent's runs inside it. A child whose engine start fails because its id is taken counts as started for `START` and is a failed outcome for `WAIT`.

**The allowlist** is the agent's declarations and nothing else. `@agent.action(name, ...)` on a payload model records the name, the model, the limits and, when `run=` is given, the target. The workflow is given `agent.policies` (the names with their limits) and the worker's routes are built from `agent.definitions`, so both sides read one list; `AgentWorker.registration` refuses to build a registration while an ordinary declared action has no handler or a run action has no prepare callable. A node asks with the payload alone, `request_action(SendEmail(...))`, and the name is the one the model's class was declared with, so a node cannot ask by a misspelt name, and a model that no agent declared is refused before anything is asked (`NotAnAction`). A run action's payload is checked against the same catalog before `prepare_run` creates anything, and a request for it never reaches `run_action`.

**A failure.** A failed action reaches the graph as an outcome with `succeeded` false and an `error` text of at most 500 characters, so the agent decides what to do. That is what happens when the action's attempts are used up, when an attempt took too long, when the worker stopped sending heartbeats, and when the handler raised a failure of a type the agent declared as worded (its message passes as it is). A failure of any other type, such as one the worker's library makes itself, is told as "the action stopped unexpectedly", and its detail is in the log only. Of the actions, only a defect of the agent ends the run: an action that is not allowed, a payload that does not fit, a result that is not JSON or is over 32 KiB, and more actions than `max_actions`; none of these is tried again. A step that fails ends the run too, after its attempts, and at once when the thread or the graph refuses the step (`StepRefused`: an outcome nobody asked for, a graph that waits for two actions at once or paused on something that is not an action request, a node that broke a rule below, a route that chose a node it was not given, a step outcome over 32 KiB).

**A step is safe to repeat; an action is repeated with a key.** An attempt at a step that died is retried with the same input. A thread that waits and is advanced without an outcome returns the same request and runs nothing; an outcome that an earlier attempt already applied is not applied again, and the graph continues, or returns the next request. The id of an action is `<thread id>:<interrupt id>`, the same each time the same step is attempted again. An action is not safe to repeat by itself: Temporal runs an activity at least once, and a thread cannot be stopped, so an attempt that timed out or was cancelled may still be running its handler when the next one starts. The handler gets the id as its idempotency key, for instance as the key of a request to the service it calls. For that reason an action is tried once unless its declaration says otherwise (`attempts=`): whether a repeat is harmless is a fact about the service behind the handler, which the runtime cannot check.

**The rules for a node**, which `request_action` states and checks:

- **One action per node.** A node that needs two is two nodes. Asking a second time in one run of a node is refused (`TwoActionsInOneNode`), and so is a graph that waits for several actions at once.
- **Nothing with a side effect before the call.** When the outcome arrives, the node runs again from its start, so anything it did before `request_action` is done twice.
- **Ask for the same thing every time.** The outcome is delivered with a digest of the request it answers, and a node that asks for something else when it runs again (a draft a model made anew, say) is refused (`RequestChangedOnResume`). Work that is not repeatable belongs in an earlier node, whose result the state keeps.
- **A tool may not ask for an action.** A tool is a function the model chose to call; it answers with text. An action is asked for by a node, from what the model submitted. A tool that calls `request_action` is refused (`ActionAskedByTool`). The check sees a tool that runs in the context of its caller; a tool that started a thread of its own would get round it.
- **A node answers with a mapping of what it changes in the state**, nothing else: the route after a node decides which node follows, and a route may choose only among the targets it was declared with.
- **Plain data.** The state of the graph, the payload (stored as JSON) and the result of an action are dicts, lists, strings, numbers, booleans and `None`, because the checkpoint store's strict serializer rebuilds nothing else. What a node needs that is not plain data comes in the agent's *context*, built for each attempt by the wiring and never stored.

**What enters the workflow history, and its bounds.** Identifiers, names and small JSON: the input of a step (the kind and id of the run, and the outcome of the last action), its result (what the agent's `finish` reports, or the request it waits for), the request of an action (its id, name and payload) and its outcome, and for a failure a type and a message that code chose, with the stack trace Temporal records (file names and source lines, no values). The activities refuse, for good, a step outcome over 32 KiB (`MAX_STEP_BYTES`: the request with its payload, or the final output) and an action outcome over 32 KiB (`MAX_RESULT_BYTES`), and what is not JSON. An error that nobody worded is logged and replaced by a fixed sentence, and a worded one leaves as a copy without the errors it was raised from, so a message written for a log never reaches the history; a test has a handler fail with a secret in its message and searches the decoded history for it. No checkpoint and no state of the graph between steps is in the history. The final state never is either: `AgentSteps` hands it to the agent's `finish`, and what `finish` returns is what is stored.

#### Writing an agent

An agent is four modules. The split is not a convention: the workflow sandbox, which loads a workflow's module and everything it imports, cannot load LangGraph or the database, so what the workflow needs of the agent (its kind and the limits of its actions) has to be in a module that imports neither. The greeter in `apps/worker/tests/agent_runtime/dsl/` is a complete agent written this way, and the tests run it on Temporal and PostgreSQL; the repository analyzer is the real one (`analyzer_agent/definitions.py` and `graph.py` in core, `repository_analyzer/workflow.py` and `wiring.py` in the worker). The outline below follows the greeter; its names (`RunCampaign`, `SendEmail`) are made up, and it was not run as written.

```python
# definitions.py: what the workflow may load. No LangGraph, no database.
agent = Agent("campaign-run", state=CampaignState, context=CampaignContext)   # context is optional

@agent.action("send_email", timeout=30, attempts=3, retry_after=2)   # attempts defaults to 1
class SendEmail(BaseModel):
    model_config = ConfigDict(extra="forbid")   # a payload that allows extra fields is refused
    to: str

# graph.py: the nodes. Importing this module is what puts them on the agent.
@agent.node(start=True)
def notify(state: CampaignState, context: CampaignContext) -> dict[str, Any]:
    outcome = request_action(SendEmail(to=state["address"]))   # the graph pauses here
    return {"sent": outcome.succeeded, "error": outcome.error}

agent.edge(notify, END)   # or @agent.route(after=notify, to=[...]) on a function that names the next node

# workflow.py: loaded by the sandbox; imports definitions.py, never graph.py or wiring.py.
@agent_workflow(agent, name="RunCampaign", graph=GraphRunPolicy(
    attempt_timeout_seconds=600, heartbeat_timeout_seconds=60, max_attempts=3, retry_after_seconds=10))
class RunCampaign:
    async def failed(self, run: GraphRunRef, reason: str) -> None:
        ...   # workflow code: call an activity that records why

# wiring.py: the worker's process only; imports graph.py, so the nodes are declared.
worker = AgentWorker(agent, task_queue="campaigns")

@worker.handler(SendEmail)
def send_email(payload: SendEmail, context: ActionContext) -> Mapping[str, Any]:
    ...   # blocking; context.action_id is the idempotency key; returns small JSON

@worker.prepare_run(Research)   # for @agent.action("research", run=RunTarget(...))
def prepare_research(payload: Research, context: RunContext) -> uuid.UUID:
    ...   # blocking; create the child run's record under context.action_id; return its id

steps = AgentSteps(agent, initial_state=..., finish=..., context=..., recursion_limit=20)
registration = worker.registration(
    checkpoints=checkpoints_in(database_url), graph=steps, workflows=[RunCampaign],
    longest_run=timedelta(hours=6), activities=[...], checkpoint_cleanups=[...])
```

- **The hooks and their order.** The class given to `agent_workflow` defines no `run`; the decorator writes it. It may define three hooks, each an `async def` given the workflow's input. `before(run)` is first, for marking the run started; it may return a `GraphRunPolicy` that replaces the default, which is how limits from the worker's settings reach a run (workflow code cannot read the environment). Then the graph runs with its actions. `after(run, output)` follows a graph that finished, with what `finish` reported. `failed(run, reason)` is called instead when `before`, the graph or `after` failed or the workflow was cancelled, with a sentence that may be shown: the message of the failure when its type is one of `worded_types`, and one of the agent's fixed `texts` otherwise. Then, in every case, `forget_run` removes the run's checkpoints and calls the function the wiring registered with `@worker.run_ended`, for what a run left outside the checkpoints. `failed` and the forgetting are waited for to their end even when the workflow is cancelled meanwhile. A workflow whose starter has an input of its own gives `input=` and `run_of=`, as the analyzer does.
- **What `finish` is for.** `AgentSteps` calls it inside the step that ends a run, with the run and the final state. It may store what the run produced, so it must be safe to repeat, and it returns the small projection that enters the history: an identifier and a summary, never the state, which holds the model's whole conversation. The analyzer stores the profile there and returns its id. `initial_state` makes the state a run starts from and is called only for a thread with no checkpoint; `context` makes, for each attempt, what the nodes take as a second parameter.
- **What is checked when the worker starts, not at the first run.** A limit of an action that is not a finite positive number or is over the ceilings (10 attempts, a day per attempt, an hour's first wait), a payload model that allows extra fields or has a field that reads text as a file path or an import name, an action or a node declared twice, a run action with an effect other than internal or with limits of an activity it does not run: when the module is loaded. An agent with no node or no start, an edge or a route to a function that is not its node, a context given for an agent that declared none (or the reverse): when `AgentSteps` is made, which compiles the graph once. A handler, prepare or estimate for a model the agent did not declare, a second one for an action, an `async def`, a handler for a run action or a prepare for an ordinary one, an estimate for an action that does not spend: at the decorator. An ordinary action with no handler, a run action with no prepare callable, an action that spends with no estimate, and a workflow class that this agent's `agent_workflow` did not make: at `registration`. A workflow class that defines `run` or `proposal_decided`, a hook that is not an `async def` of the right parameters, a class not at the top of a module, an agent with an action that publishes or spends or starts another run and no `scope_of`: at `agent_workflow`. Such an agent's registration without the database `sessions`, and one with an action that spends without the process's `environ`: at `registration`.
- **Showing a run's progress.** `@agent.progress` on a function `(node, state, update) -> list[RunEvent]` in `graph.py` (the researcher's is `research_agent/progress.py`), and `AgentSteps(..., record_progress=...)` in the wiring with a function `(run, events)` that stores them (the researcher's is `ResearchWork.record_progress`, one short transaction per node in `run_event`). Without `record_progress` nothing is computed. A run's first and last events are not a node's: the researcher's `finished` and `failed` are written by an activity of its workflow's hooks.
- **Every agent's left-over checkpoints are removed.** `registration` takes `longest_run`, the most a run of the agent can take from its first step to its end with every retry and every wait for a person, and adds core's rule for any kind (`remove_stale_checkpoints`): a thread of the agent's kind whose newest checkpoint is older than that belongs to no run in progress, and its rows go. It needs no table of runs; it reads the time the library writes into each checkpoint (`checkpoint ->> 'ts'`). A `longest_run` shorter than one of the agent's waits for a person, or than the longest a run it waits for can take (`RunTarget.longest_seconds`), is refused when the worker starts. An agent may hand over a stricter rule of its own as a `CheckpointCleanup` as well, as the analyzer does with `remove_checkpoints_of_analysis_runs`, which also removes the threads of finished runs at once.

**Why not the official plugin.** The installed temporalio (1.34.0) has `temporalio.contrib.langgraph`, which its README calls experimental. It runs the nodes of a graph as activities (each node is marked `execute_in` `activity` or `workflow`), so the history grows with the nodes, and it uses LangGraph's in-memory saver with Temporal's history as the record: its README says third-party checkpointers such as PostgreSQL are not needed. This project runs the graph in one activity between actions and keeps its PostgreSQL store, its attempt lock and its cleanup, so it deliberately did not adopt the package.

What the agent runtime does not do, and what to know before relying on it:

- **The policy gate is a small one.** It holds every action that publishes for a person, weighs every action that spends against the creative budget (it runs, waits for a person, or is refused), and lets every other one run; see [Policy gate](#policy-gate) for what it does not weigh yet.
- **One `Worker` per agent.** `main.agents` lists every agent the process serves, each set up by its own wiring: the repository analyzer, the researcher, and the chat's follow-up turn, which is not an agent on the runtime but registers its workflow and activity the same way (`orchestrator/wiring.py`). `build_workers` gives each a `Worker` on its own task queue, because the runtime's activities have the same names for every agent and one `Worker` refuses two of a name, and refuses two agents on one queue when the process starts; `serve_until` serves them together and stops them together. `WORKER_MAX_CONCURRENT_ACTIVITIES` is the limit of each `Worker`, so of each agent. Two agents served in one process were checked with the test agents (`agent_runtime/test_serving_agents.py`), not with two product agents.
- **A thread of a kind no agent serves stays.** Every served kind has the rule above; a kind whose agent was removed, or whose name was changed, is nobody's, and its rows stay until they are removed by hand.
- **No Continue-As-New.** A run that asks for more than `max_actions` actions ends, where it could continue in a new workflow. A run of 200 actions was not produced, and neither the size of such a history nor how near it is to a limit of Temporal's was measured.
- **Progress is per node, and only where an agent declares it.** An agent may declare one progress function (`@agent.progress`): a pure function of a node's name, the state the node ran on and the changes it answered with, which gives that step's events (`RunEvent`, `run_events.py`). `AgentSteps` calls it as each node ends, inside `run_graph_step`, and hands the events to the wiring's `record_progress`, which stores them. Nothing of it enters the workflow history or the step's outcome. A progress function or a recorder that raises is logged and the step goes on, so progress never fails a run. A node that runs again (a step repeated after an attempt died before its checkpoint) records its events again, so an event may be shown twice. The outcome of an action needs no function of its own: the node that asked runs again with it, and its changes then are what came of the action. The researcher is the only agent that declares one (see [The researcher](#the-researcher)); the analyzer and the test agents declare none. Heartbeats still carry no details, and nothing reads a checkpoint to say where a run is.
- **Cancellation reaches the work late or not at all.** A thread cannot be stopped: a step or an action that is cancelled runs until it returns, and what it returns is dropped. An action is told of the cancellation only at a heartbeat, so one whose declaration has no heartbeat timeout is never told. The next attempt may therefore start while an earlier one is still running its handler, which is what the key is for. For a step the thread is held by the earlier attempt, and the next one is refused and retried.
- **One action at a time.** A node asks for one action and the graph waits for one, so actions cannot run in parallel.
- **A failure's message is not bounded by the runtime.** What the graph is told of a failed action is cut to 500 characters, and a step's and an action's results are bounded; the message of a failure that an agent's own code worded enters the history as long as it is. (The analysis run's record cuts it to 2000 characters.)
- **`GraphThread` reads the whole history of a thread** when it is given an outcome that is not for the action pending, to tell an action asked earlier (an outcome an earlier attempt already applied) from one nobody asked for. It does so only then. A thread grows with the square of its steps (see [Graph checkpoints](#graph-checkpoints)), and this read grows with it.
- **A deploy while runs are in flight is not handled.** There is no workflow versioning and no version on a thread; see the notes under [The worker](#the-worker) and [Graph checkpoints](#graph-checkpoints).
- **The wiring is the cost.** What stands between an agent's graph and the worker's database, disk and services (`initial_state`, `context`, `finish`, the handlers, the run-ended function, the wording of failures) is the agent's to write; for the analyzer that is `analysis.py`, `clones.py` and `wiring.py`, 714 lines (656 before credentials were resolved at each attempt).
- **The dev Temporal server waits at least a second before a retry**, whatever interval is asked for. Measured on 2026-10-11 against the dev stack, with a one-off workflow: retry intervals of 0.1 s and of 0.5 s both gave about one second between attempts. So `START_RUN`'s half second of the analyzer, and any `retry_after` below one in the tests, behave as one second there. Whether another server does the same is not known.

### Policy gate

The design's policy gate (the report's section "Safety: Approvals, Budgets and Autonomy") stands where an action is started: in the driver of the agent runtime, which every action passes, so no node can skip it and no model can avoid it. It is built in its first form: **every action that publishes waits for a person; every action that spends is reserved in the creative budget's ledger, which lets a small one run, holds a larger one for a person and refuses one past the month's cap; every other action runs.** Nothing else is weighed yet.

How it works:

1. **An action says what it does.** `@agent.action(name, effect=ActionEffect.PUBLISHES, approval_wait=...)`. The effect is `internal` by default (the clone is), `publishes` or `spends`; it is declared in code with the action and never read from a request, which a model may have shaped. `approval_wait` is how long a person has, three days by default and a month at most. An agent with such an action gives its workflow `scope_of` (which workspace and project a run works for) and its registration the database sessions; both are refused when the worker starts if missing.
2. **The gate decides** (`agent_runtime/gate.py`, `verdict_for`): `internal` runs; `publishes` asks a person; `spends` takes the ledger's decision on its estimate (step 7), which is `RUN`, `ASK_A_PERSON` or `REFUSE`. `may_wait_for_a_person` says from the declaration alone which actions can be held, which is what `scope_of` and the sessions are required for.
3. **The run proposes and waits** (`approval_wait.py`). The activity `propose_action` stores the action as a row of `proposal`, keyed by the action's idempotency key so that a retry finds the same row, with the payload, the run, its workflow and a deadline, and records the run's `proposal_waiting` event in the same transaction, so the screens watching the run see it ask. The workflow then waits with no activity running, for the signal `proposal_decided`, for the deadline, or for 15 minutes, whichever comes first, and reads the proposal back each time with `settle_proposal`, which expires it once the deadline passed (recording `proposal_expired`). The decision is always read from the database: the signal carries a proposal id and approves nothing, since anyone who reaches the workflow server can send one. A run cancelled while it waits expires its proposal.
4. **A person decides** through the API (`approveProposal`, `rejectProposal`), as the current user: `approvals/decision.py` stores the decision and records the run's `proposal_decided` event, then signals the run. A run that cannot be signalled reads the decision at its next check, within 15 minutes; a decision after the deadline is refused (409).
5. **The action runs, or the graph is told why not.** Approved, the driver runs it as any action. Rejected or expired, it does not run, and the graph gets a failed outcome ("a person rejected the action", "nobody approved the action before its deadline"), so the agent can revise what it asked for or give up.
6. **`run_action` checks again.** Before the handler of an action that publishes runs, the activity checks that a person approved that very action (`proposal_status_of_action`), and ends the run otherwise (`ActionNotApproved`). Before the handler of one that spends runs, it checks that the ledger holds an unsettled reservation of it (`held_decision_of_action`) made to run on its own, or one a person approved, with the same failure. That holds when a workflow did not go through the gate, for instance one started by hand on the workflow server.
7. **An action that spends is weighed by the creative budget** (`spend_activities.py`, `_spend` in `driver.py`). Its worker declares how its cost is estimated: `@worker.estimate(Payload)` on a blocking function `(payload, SpendContext) -> Decimal` (the context holds the action's id and the run's workspace and project), which may read the database or a price list; every action declared `effect=ActionEffect.SPENDS` must have one, and its registration is given the sessions and the process's `environ`. The activity `reserve_spend` runs the estimate, resolves the workspace's caps for that attempt (core's `creative_caps`: `MEDIA_MONTHLY_CAP_USD` and `MEDIA_AUTO_APPROVE_USD` in the environment win, then the workspace's stored choice, then the defaults) and reserves it with core's `reserve_spend`, keyed by the action's id, so a retried attempt finds the same reservation with the decision and amount it was made with. Within the amount one action may spend on its own, the action runs at once. Above it, the run proposes it as in step 3, with `proposal.estimate_usd` holding the estimate for the person (a new nullable column), while the ledger holds the amount; a rejection, an expiry or a cancelled run releases it. Past the month's cap nothing is reserved, nothing runs, and the graph is told "the creative budget for this month would be exceeded". Once the action ran, `settle_spend` commits what the handler's result says it spent in `cost_usd` (a number or its text in US dollars; the estimate when it says nothing or something that is not an amount). When the action failed for good its hold is released if the failure was one its handler worded or a refusal before the handler ran; after a timeout, a worker that stopped, a cancellation, an error nobody worded or a result the runtime refused, the estimate is committed instead, since the service may have charged. Settling is waited for to its end even when the run is cancelled, and one that cannot be written is logged and leaves the amount held, counting against the cap. The history holds the reservation's decision and amounts as text, and the action's id and scope: nothing else.

A proposal moves once: `pending` to `approved` or `rejected` by a person, or to `expired` by its run; the database holds the decider and the time with checks of its own. Spending was checked with a test agent that buys an image (`apps/worker/tests/agent_runtime/buyer/`), on the dev stack's Temporal and PostgreSQL, with caps of $1 a month and $0.25 per action: a small spend running without a proposal and committed at the reported cost or at its estimate; a larger one proposed with its estimate, approved and committed, rejected and released, and released when its run is cancelled while it waits; one past the cap refused with nothing reserved; a handler that failed for good released, and one that stopped on an error nobody worded committed at its estimate; a reservation whose first attempt lost its answer found again, not reserved twice; the workspace's stored caps used when the environment sets none; the history's exchanges of the two activities, which are identifiers and amounts only; the activities as plain functions, `run_action` refusing a spend that holds no reservation or waits for a person; and the start-up refusals. Publishing was checked with a test agent that publishes an announcement (`apps/worker/tests/agent_runtime/announcer/`), on the dev stack's Temporal and PostgreSQL: approved and run once, rejected, expired at its deadline, a signal with no decision behind it approving nothing, a cancelled run expiring its proposal (also when the cancellation arrives while the proposal is being stored), and `run_action` refusing an action nobody approved; and with tests of the store and the routes.

What the gate does not do yet, from the design:

- **A budget for generated media only, no content filter, no banned content.** The creative budget weighs actions that spend; there is no budget for publishing (a post's reach, an ad's spend on a platform), no per-run or per-project cap, and the text of a payload is not filtered. The order of the design's checks (banned, budget, content filter, then risk) is where the others go, in `verdict_for` and around it, before a person is asked. The API's proposal routes and the Approvals screen do not show `estimate_usd` yet.
- **A spend is settled once, by the last attempt's outcome.** An action retried after a timeout and then failing with a worded error is released, although the first attempt may have charged; the handler's idempotency key is what keeps a service from charging twice, and a handler that cannot be sure reports `cost_usd` or raises an error it did not word.
- **Replaying runs in flight.** The driver schedules `reserve_spend` and `settle_spend` only for an action that spends, and no product agent has one, so no run in flight schedules a different activity after this change; an agent that adds a spending action to a workflow with runs in flight breaks their replay (there is no versioning).
- **No risk levels and no autonomy.** Every held action is treated as the design's L1 (an approval queue); nothing is L0 (automatic) or L2 (human only), and the project's `autonomy_level` column is not read. There is no dry-run mode and no kill switch.
- **No policy file.** There are no YAML rules and no CEL; the one rule is in code.
- **A proposal cannot be edited**, only approved or rejected. The design's "approve, edit or reject" needs an edited payload to pass the gate again.
- **No audit log, no rationale or evidence on a proposal, no reminders.** A proposal holds the payload and not the agent's reasons, the evidence or the profile version it used. The dashboard tells the person that something waits, wherever they are and the moment it is stored (the notifications, see [The dashboard](#the-dashboard)), and the run's own screens show the `proposal_waiting` event; nothing reaches outside the dashboard — no e-mail, no push — and a deadline that is about to pass is not escalated.
- **The creative studio is its first product user.** Its paid images (`generate_image`, `edit_image`) are spending actions weighed by the ledger; the analyzer's and the researcher's actions are internal, and no agent publishes yet.

### The orchestrator chat

The design's orchestrator console (the report's section "Orchestrator Console") has two halves: the *chat turn*, which answers one message, and the *task*, which carries a request that needs several agents to its end. The chat turn is built in its first form: in memory, with read tools and one request action. The code is `packages/core/src/openmarketer_core/orchestrator/`: `reads.py` (what a turn may read: the `ChatReads` port and the frozen records it is answered with), `reads_postgres.py` (the port answered from PostgreSQL; one adapter is built for one turn from a session and the workspace and project the turn is about), `requests.py` (what a request action may ask of the turn's caller: the `ChatRequests` port and `ResearchNotStarted`; the adapter is the API's, `openmarketer_api/chat_requests.py`), and `chat_agent/` (`definitions.py` declares the agent, its state and its context, `rules.py` the prompt, the limits and the checks, `tools.py` the eight read tools and the one request action, and `graph.py` the nodes and `answer_message`); `ask.py` is the use case of one stored chat's turn — it starts the turn, reads the chat's history, runs the turn and stores the exchange, and stores no message when the turn failed. `events.py`, `events_postgres.py`, `turn_lifecycle.py` and `follow_up.py` are the turn's rows, its events and the follow-up turn, described in [Chat events and the follow-up turn](#chat-events-and-the-follow-up-turn).

**A turn.** One turn is the answer to one message from the operator about one project. The graph is a loop like the analyzer's — `call_model` ↔ `run_tools` — and it ends when the model submits the answer with `submit_answer`, or when a limit ends it. `submit_answer`'s one argument is read strictly (`extra="forbid"`, a non-empty string): a submission that does not fit is told what to fix while model calls remain, and on the last chance ends the turn with `ChatTurnError`. A reply with no tool calls is nudged back to the tools; a tool failure is told to the model as text it can correct from, and never repeats what it sent.

**Its limits.** `ChatLimits` (`max_model_calls=8`, `max_tool_calls=8`, `max_cost_usd=0.50`) bound one turn, as the analyzer's do one run. When the last two model calls start, or three quarters of the reading budget or seven tenths of the cost limit are used, the turn wraps up: the read tools are withdrawn and only the request actions and `submit_answer` are offered, and the model is told to start any run the operator asked for, then answer. The reading budget counts reads: a request action is not one, so `start_research` does not spend the budget and is not taken away by it — a turn whose operator asked for research still starts it before it answers — while a turn that gives no answer within the limits fails as before. The graph's recursion limit is `2 * max_model_calls + 6`, the analyzer's shape. The model call goes through the role `orchestrator` of `config/models.yaml`, the role the design gives the console.

**What it may read.** Eight tools, all read-only: `get_project_status` (where the project stands: its review state, its latest run, and how many proposals wait), `read_profile(section?)` (one section of the latest approved profile, or of the latest draft while nothing is approved; without a section it lists the sections), `list_pending_proposals`, `explain_proposal(proposal_id)`, `get_analysis_run(run_id)`, `list_analysis_runs(limit)`, `list_research_runs(limit)` and `read_research_report(run_id?)`. Every answer is bounded JSON (6000 characters, then truncated). The vocabulary is fixed where a person could not have typed it: the profile's sections are `PROFILE_SECTIONS`, and no list returns more than `MAX_LISTED_RECORDS` (20) records. The port keeps a turn inside its project: the adapter holds the workspace and the project, so the graph never names either and cannot read beyond them; a reading that does not exist is `None`, and a section or an identifier that does not exist is refused with a message that never repeats the value.

**What was added for it.** `db/proposals.py` gained `pending_proposals_summary` (how many of a project's proposals wait, and the nearest deadline; a missing or foreign project is `ProjectNotFound`), and the `StoredProject` of `db/projects.py` gained `status`, `autonomy_level` and `product_url`, which the status reading carries.

**It runs in memory.** `graph.answer_message(reads, model, history, *, limits=None, requests=None, events=None)` builds the context of one turn (the model, the reads, the limits, the request port and where its events go) and runs the graph in memory with `run_from`. There is no workflow and no checkpoint, so a turn that is lost — a process that died — is started again by sending the message again (its row is given up after 15 minutes; see [Chat events and the follow-up turn](#chat-events-and-the-follow-up-turn)); `history` is the conversation up to and including the operator's latest message (plain `user` and `assistant` texts; anything else is left out). A history longer than `MAX_HISTORY_CHARS` (24,000 characters) is shortened before the turn answers: everything but the newest `KEEP_RECENT_MESSAGES` (12) messages becomes one summary the model writes in a call of its own, whose cost counts against the turn (`rules.compact_history`). A turn that gave no answer stores no message.

**`start_research` is offered only when it can be answered.** A turn whose caller gives a `ChatRequests` port (the API's `sendChatMessage`) is offered the request action with the read tools; a turn without one (the worker's follow-up turn, and any caller with no workflow server, such as a test) is not told of it at all (`rules.tool_schemas(agent, offer_requests=...)`), and if a model calls it all the same it answers that starting runs is not available and starts nothing. Before this change every turn was offered it.

**Served and stored.** A chat is one named conversation of a project — a project can have several — and it is stored. `db/chat.py` writes and reads the tables `chat_thread` (the thread's name, when it last gained a message and how far the operator has read it; migration `efedf4ded27e`) and `chat_message` (the operator's and the assistant's messages of one thread; migration `e8950d3043f2`; a message is never changed, and the model and the cost of its turn are returned to the caller and not stored). A thread still named `New chat` takes its name from the first line of the operator's first message, cut at a word boundary. The API's `routes/chat.py` serves six routes under `/v1/projects/{project_id}/chats`: open a chat, list a project's chats most recently active first, read one, list its messages newest first, send one message (a chat turn: 201 with the stored question and answer, the model that answered and the turn's cost) and mark a chat read, which is the unread marker. A chat turn runs in the API's process, so the route resolves the turn's model itself: the workspace's choice of the `orchestrator` role (`model_choices`) and the provider's key (`credentials.resolution.model_key`, the rule the worker reads through `WorkspaceCredentials`). Two more routes read a chat's events (see [The API](#the-api)). The dashboard's proxy forwards the routes, and the dashboard's chat screens use them (see [The dashboard](#the-dashboard)).

What the chat turn does not do, from the design:

- **One request action, in its first form.** `start_research` starts a research run of the project (`orchestrator/requests.py`): the tool reads its arguments strictly into `ResearchRequest` and asks the turn's caller to create the run and start its workflow, then answers with the run's id and status. It writes nothing itself, and a turn whose caller gave no port is not offered it (above). Storing a directive, starting a task, and starting any other kind of run are not built; an action is held for a person only through the workflow gate, which a chat turn has none of, so nothing a turn does waits for an approval (the run it starts has its own, like any run). The task half comes later.
- **The thread is stored; attribution only in part.** A project's chats and their messages are stored, and a run the turn started records that the orchestrator asked for it (`requested_by`) and in which chat (`research_run.chat_thread_id`); a turn's `run_started` event names the run, and each message names the turn that wrote it. Nothing records which message caused which run as a link of the message itself (the design's one line on each created record).
- **The answer's text is not streamed; no proactive mode, no memory, no metrics.** The design streams answers into the dashboard thread, lets the console speak first, and assembles context from project memory, metrics and the audit log. A turn's steps are streamed as events, and the follow-up turn after a research run is the console's only turn that the operator did not ask for; a long conversation is summarised (above), but a turn otherwise reads only what its eight tools reach.
- **One project, no workspace thread.** A turn is about one project; the design's workspace-level thread is not built.

### Chat events and the follow-up turn

Three things were added to the chat together: a turn records what it does as it goes, so the open chat can show it; a research run started from a chat records its progress there too; and when that run has ended, the orchestrator speaks again in the chat on its own, in one *follow-up turn* that reads the run's report and explains it. The operator's own turns still run in the API's process, and `sendChatMessage` still answers only when the turn has ended; only the follow-up runs in the worker. The design and where this differs from it are in [Differences from the design report](#differences-from-the-design-report).

**The rows** (migration `4897ea1d143f`; the new columns are nullable and nothing stored before is filled in):

- `chat_turn`: one row per turn of the orchestrator in a chat, from its start to its outcome (`db/chat_turns.py`). Its `trigger` is `message` (the operator wrote) or `research_finished` (a follow-up), with `research_run_id`, the run it is about, set exactly for the second; its `status` is `running`, `answered` or `failed`, with `error` (a sentence for the operator, at most 2,000 characters) exactly when it failed and `finished_at` exactly when it is not running, each a CHECK constraint. A partial unique index on `thread_id` where the status is `running` keeps one running turn per chat; `start_turn` takes the workspace lock first, so two starts run one after the other, and a start that still loses to the index is `ChatBusy` too. A turn moves forwards only, and recording the same outcome again changes nothing.
- A turn left `running` by a process that stopped does not block its chat for ever: one started more than 15 minutes ago (`TURN_ABANDONED_AFTER` in `db/chat.py`) no longer makes the chat busy, and the next `start_turn` of the chat marks it failed with "This turn stopped before it could answer. Please ask again." No `turn_failed` event is recorded for it, so its events end without an outcome; the chat's `busy` is what tells a screen it has ended.
- `chat_message.turn_id`: the turn that wrote a message, a turn of the same chat; null for a message stored before turns were. A follow-up's answer is stored with `append_answer`: an `assistant` message with no question before it, which makes the chat unread.
- `research_run.chat_thread_id`: the chat whose turn asked for the run, a chat of the same project (`request_research_run` refuses another with `ChatNotFound`); null for a run started anywhere else. `PostgresChatRequests` (the API's) passes the turn's chat. `requested_by` is still `orchestrator` for such a run.
- `run_event`: the events of every kind of run (`db/run_events.py`), named by `run_kind` and `run_id` without a foreign key, as a proposal names its run, with `project_id`, `kind`, `detail` (JSONB) and `created_at`. Its `id` is a `BIGINT` identity, the cursor a reader continues from; it is indexed on `(run_kind, run_id, id)`. A chat's events are those of its turns (kind `orchestrator-chat`) and of the research runs whose `chat_thread_id` is the chat (kind `research-run`), ordered by `id` (`events_of_chat` oldest first after a cursor, `latest_events_of_chat` newest first in pages). Appending takes the workspace lock, so the events of one workspace are numbered and committed one transaction after another and become visible in the order of their ids: a reader that continues after the last id it got never finds a smaller id committed later. Events are never changed; they are deleted with their project.

**What an event holds** (`run_events.py`, plain data). `RunEvent(kind, detail)` bounds what it holds when it is built: a text value is cut at 300 characters, a list keeps its first 10 items, a detail has at most 8 keys, each a lower-case name, and a value is a string, a finite number, a boolean, null or a list of those; a nested mapping or anything else is refused (`InvalidRunEvent`). The kinds:

| Run | Kind | Detail | Written by |
|---|---|---|---|
| Chat turn | `turn_started` | `trigger` | `turn_lifecycle.py`, in the transaction that starts the turn |
| | `tool_called`, `tool_answered` | `tool` and `label`; `tool` and `ok` | `rules.run_tool_calls`, before and after each tool; the submission of the answer records none. The labels are fixed English lines per tool (`TOOL_LABELS`, such as "Reading the research report"; "Calling a tool" for a name it does not know) |
| | `run_started` | `run_kind`, `run_id` | `start_research`, after the run was started |
| | `turn_answered` | `message_id` | `turn_lifecycle.py`, in the transaction that stores the answer |
| | `turn_failed` | `reason` | `turn_lifecycle.py`: one of three fixed sentences (`rules.failure_reason`: no answer within the limits, the model could not answer, an unexpected error), never what a model or a provider wrote |
| Research run | `planned` | `round`, `queries` (the round's new ones), `categories` | node `plan` |
| | `searched` | `query`, `results` (how many it added), `ok` | node `search` |
| | `screened` | `kept`, `dropped` | node `screen` |
| | `fetched`, `fetch_failed` | `url` and `title`; `url` and `reason` (the handler's sentence) | node `fetch` |
| | `read` | `pages` (read so far), `ok` | node `read` |
| | `synthesized` | `findings` (checked findings the run has after the round), `round` | node `check`; `synthesize` and `report` record nothing |
| | `finished`, `failed` | `findings`; `reason` (as recorded on the run) | the `Research` workflow's activity `record_end` |
| Any run | `proposal_waiting` | `proposal_id`, `action_name`, `effect` | `db/proposals.py` (`propose_action`), in the transaction that stores the proposal |
| | `proposal_decided` | `proposal_id`, `approved` | `db/proposals.py` (`decide_proposal`), in the transaction that stores the person's decision |
| | `proposal_expired` | `proposal_id` | `db/proposals.py` (`settle_proposal`), in the transaction that expires it |

The research events come from `research_agent/progress.py`, the researcher's progress function (see [Agent runtime](#agent-runtime)), stored by `ResearchWork.record_progress` in a short transaction per node. Events hold names, counts, identifiers, the queries a model wrote, and a page's address and title, cut short. No page text, snippet or quote goes into one. A title is what a web page says of itself: it is shown as plain text and never read by a model. Events are for the person's screen: no event is given to a model, the follow-up turn included, which reads the run through its read tools.

The three proposal kinds are not written by a progress function or a graph: the one record of a held action is its `proposal` row, and every transition of the row is recorded on the run that asked, in the same transaction that makes the change, so the crash between the two can never leave a decision without its event. A call that changes nothing — a retried `propose_action` that finds the proposal stored — records nothing. The run's screens fold them into where the action stands (`ResearchRunView.proposal` in the dashboard), and the workspace's stream carries them to the notifications the same way; `propose_action` is a worker activity and `decide_proposal` runs in the API, so the three kinds are the first ones an API request can record.

**A turn from start to end** (`turn_lifecycle.take_turn`, shared by `ask.py` and `follow_up.py`):

1. One transaction starts the turn (`ChatBusy`, the API's 409 `chat_busy`, while another runs), reads the chat's conversation and records `turn_started`. It commits before the model is called, so a reader on another connection sees the turn and the chat busy.
2. The agent answers, recording its events through `PostgresTurnEvents`, one short transaction each. An event that cannot be stored (a `DatabaseError`) is logged and dropped; the turn goes on.
3. One transaction marks the turn answered first, stores what the turn's kind stores (the exchange, or the follow-up's answer) and records `turn_answered`. A turn that was given up meanwhile (marked failed by a later start) stores nothing and fails with `ChatTurnError`.
4. A turn that fails in 2 or 3 is marked failed with its sentence, records `turn_failed` and raises its error again; no message is stored. When even that cannot be written, it is logged and the row stays `running` until the next turn of the chat gives it up.

`turn_lifecycle.py`'s own writes hold no transaction open while the model is called. The reads of a turn do: they go through a session the caller opens around the turn (the API's request transaction for `sendChatMessage`, one transaction in the follow-up's activity), which stays open, idle, for the length of the turn. Noticed while writing this page; not measured.

**How a research run reports back.** `Research` gained an `after` hook and its `failed` hook a second part. After the run has stored its report, or after its failure is recorded, the activity `record_end` reads the run and stores its last event (`finished` with how many findings the report holds, which `finish` now returns beside the report's id; `failed` with the reason recorded on the run) in one transaction, and answers with the run's chat, if it has one. The workflow then starts `ChatFollowUp` as a child with the id `chat-follow-up-<run kind>-<run id>` on the task queue `openmarketer-orchestrator`, abandons it (`ParentClosePolicy.ABANDON` and `ChildWorkflowCancellationType.ABANDON`: it outlives the run and is not cancelled with it) and does not wait for it; a start refused because that id was used (`REJECT_DUPLICATE`) counts as done, so a run told twice follows up once. `record_end` is tried for up to ten minutes (30 seconds an attempt, a first wait of a second, waits up to a minute; `policy.RECORD_END`), and a failure of it or of the start is logged and changes nothing about how the run ended. A run whose failure could not be recorded tells no chat. A cancellation that arrives after the report was stored waits for the chat to be told and does not turn the run into a failed one. A run started through the API (`startResearch`) has no chat, records `finished` or `failed` all the same, and starts no follow-up. The names and the input of the follow-up are in the worker (`orchestrator/contract.py`), since only the `Research` workflow starts it.

**The follow-up turn** (`orchestrator/follow_up.py`, `follow_up_on_research`). It does nothing when a turn of the chat has already answered about the run, since the activity may run twice. Otherwise it takes a turn with the trigger `research_finished`: the chat agent is given the chat's stored conversation and, in the operator's place, an instruction code writes from the run's record (`rules.follow_up_instruction`): marked as written by OpenMarketer and not by the operator, it names the run and its status, asks the agent to read it with `list_research_runs` and the report with `read_research_report`, to give each finding with its confidence and sources, or, for a run that failed or has no report, why and what the operator can do, and says that no other run can be started in the turn. The instruction is not stored; only the answer is. The turn has the same read tools and limits as any turn (`ChatLimits`), and no `ChatRequests`, so it is not offered `start_research`. A follow-up whose turn failed is taken again when it is asked again.

**The worker's side** (`apps/worker/src/openmarketer_worker/orchestrator/`). `ChatFollowUp` (`workflow.py`) is one activity, `follow_up_on_run` (`activities.py`), registered in `main.py` beside the agents on its own task queue; it is not an agent on the runtime and keeps no checkpoints. Each attempt makes the chat model for the chat's workspace: the `orchestrator` role with the workspace's model choices laid over `config/models.yaml`, and the model provider's key the workspace has at that moment (`wiring.py`), traced when [tracing](#tracing-to-langfuse) is on; the turn runs in a thread while the activity sends heartbeats. The limits (`policy.py`):

| What | Limit |
|---|---|
| One attempt | 10 minutes, below the 15 minutes after which a running turn is taken for abandoned (a test holds the two together); a heartbeat within 60 seconds |
| Between attempts | 2 seconds at first, doubled each time up to 2 minutes |
| All attempts | 30 minutes from the first schedule (`schedule_to_close`) |
| Tried again | a busy chat (`ChatBusy`), a database that could not be reached, and a model provider that failed in a way that may pass (`LLMError.may_pass`), the last for 3 attempts in all (`MODEL_ATTEMPTS`), since each is a failed turn the chat shows |
| Not tried again | a request the provider refuses, no answer within the turn's limits, a model key set nowhere, a stored credential that does not open, a stored model choice that breaks a rule, a configuration error, a project, chat or run that is not there to follow up on, and an error nobody worded |

A follow-up that ends without an answer has its turn recorded failed in the chat at each attempt, and the workflow then completes without failing, after logging why in a sentence that may be shown. The follow-up's history holds its four identifiers (workspace, project, chat, run) and short sentences; the `Research` workflow's history now also holds a number of findings and the chat's id.

What this does not do:

- **The API reads the table; nothing pushes.** An open stream reads `run_event` about once a second; there is no `LISTEN`/`NOTIFY`. Each open chat costs a read a second (three statements: the project, the chat, the events).
- **The answer's text is not streamed.** A turn's answer is submitted through a tool (`submit_answer`) and arrives whole; what is streamed are its steps.
- **An event may be shown twice.** A research step that is repeated after an attempt died before its checkpoint runs its nodes again and records their events again. A turn's events are not repeated: a follow-up taken again is a new turn, with its own row and events.
- **A follow-up can give up in silence.** A chat that stays busy for the follow-up's 30 minutes, or a worker that serves no `openmarketer-orchestrator` queue for that long, leaves the run's card with its `finished` or `failed` event and no follow-up answer; nothing tells the operator that none will come.
- **Only research runs report back.** An analysis records no events and starts no follow-up; no other kind of run is shown in a chat.
- **Events are kept as long as their project.** No retention removes them; a stored title is a web page's own text, kept until the project is deleted (which, with research runs, fails today: see [Deleting a project](#deleting-a-project)).
- **The follow-up's contract is the worker's.** The API never starts a follow-up and does not know the workflow's name.

### Tracing to Langfuse

Runs of an agent can be traced to Langfuse, so that what happens inside a graph can be seen: every node, with the state it read and what it changed, and every model call it made, with its messages and tools, the reply, the model, its tokens and its cost. A chat turn of the API is traced the same way. It is off unless the environment gives a Langfuse project's keys, for the worker, the command line and the API alike:

```bash
LANGFUSE_PUBLIC_KEY=pk-lf-...
LANGFUSE_SECRET_KEY=sk-lf-...
LANGFUSE_BASE_URL=https://...    # optional: a self-hosted Langfuse; Langfuse Cloud otherwise
```

How it is put together (`packages/core/src/openmarketer_core/tracing.py`, the only module that imports `langfuse`, which a test holds it to). Langfuse's SDK is built on OpenTelemetry: each traced thing is a span, exported in batches.

- **Graphs and nodes.** Langfuse's LangChain handler is attached to every LangChain run of the process through LangChain's configure hook (a context variable that `start_tracing` sets), so LangGraph reports every node without the graph adapters importing Langfuse. Each step of a workflow's run is a graph run named after the run's kind (`analysis-run`), with the run's thread (`analysis-run:<run id>`) as its Langfuse session, so the steps of one run, which are separate graph runs between actions, are one session (`langgraph_steps.py`). A run of the command line is named after its agent's kind (`langgraph_agent.run_from`). Work that may not descend from the context `start_tracing` ran in is run under `Tracing.traced` instead, which sets the same handler for the work's own context; the API's chat turns run that way, because a turn runs in a worker thread of the API's server, whose context the handler does not reach.
- **Model calls** do not go through LangChain, so LangGraph cannot see them. `Tracing.model` wraps a `ChatModel` so that each call is a *generation* under the node that made it, named after its role, with its model, its tokens and the cost OpenRouter reported. A failed call is a generation of level `ERROR` whose message names the status and never what the provider wrote. `Tracing.decisions` does the same for a `DecisionModel` (see [Decision calls](#decision-calls-and-the-screening-of-search-results)): each call is a generation named after its role (`screener`), with the texts and the questions it was sent as its input, the probability of each answer as its output, the model and the cost; the endpoint reports no tokens. The worker wraps the decision model of each research attempt as it does the chat model (`researcher/wiring.py`). The worker wraps the model of each attempt (`repository_analyzer/wiring.py`, `researcher/wiring.py`, and `orchestrator/wiring.py` for a follow-up turn, which runs under `Tracing.traced` like the API's turns), the command line its models, and the API the model of each chat turn (`routes/chat.py`); with tracing off the model is used as it is.
- **Start and stop.** The worker, the command line and the API read the settings first, say in their log whether runs are traced and where, and refuse to start with one key and not the other. Tracing is started in the task that then starts everything else, so the graphs in the worker's activity threads are traced as well (checked through Temporal in `test_worker.py`), and stopped last, which sends what is still queued. The API starts tracing the same way in `app_from_env` and never stops it by hand: the handler was set in the factory's context, which the server's own tasks do not share, so `Tracing.stop` could not unset it; Langfuse's own `atexit` sends what is still queued when the process ends.
- **Its own tracer provider.** The spans are made with a tracer provider of `tracing.py`'s own, never the process's global one.

**A Langfuse in the dev stack.** `make up tracing=1` starts the dev stack with its compose profile `tracing`, which adds a self-hosted Langfuse (`langfuse/langfuse:4` and `langfuse/langfuse-worker:4`) on `http://localhost:3001`, as the dashboard has 3000; plain `make up` leaves it out. Langfuse keeps its data in a database `langfuse` of the stack's PostgreSQL and a bucket `langfuse` of its MinIO, which two one-shot containers create, also on volumes made before the profile existed, and in a ClickHouse and a Redis of its own, which are published on no port of the host. On a new database it creates a project whose keys are the ones `.env.example` gives for it (`pk-lf-openmarketer-dev`, `sk-lf-openmarketer-dev`, with `LANGFUSE_BASE_URL=http://localhost:3001`), and a user to sign in with (`dev@openmarketer.local`, password `openmarketer-dev`). Setting those three in `.env` traces `make worker`, `make analyze` and `make api` to it. `make down`, `make reset`, `make ps` and `make logs` include the profile's containers; `make reset` deletes their data with the rest. Its telemetry to Langfuse's makers is off. Like every credential of the dev stack, its keys and passwords are development defaults.

What is sent, and what is not:

- **Sent:** the graph's state and every prompt and reply, which hold repository content after intake blanked out the secrets it found, and the texts and answers of every decision call (a research run's questions and search results), to Langfuse Cloud unless `LANGFUSE_BASE_URL` names a self-hosted Langfuse. That is why it is off by default; a self-hosted Langfuse keeps them on the installation's own machines.
- **Not sent:** the model provider's key and Langfuse's secret key. A call's inputs are built from the role, the messages and the tools, never from the wrapped model, and a run's context (which holds the model) is given to the nodes and is not part of what LangGraph traces. The tests read every span that would be exported and find neither key in it.
- **Langfuse's keys** are read from the environment when the process starts. They are the operator's, not a workspace's, and are not among the credentials the dashboard stores, unlike the rule for those (resolved at each attempt).

What it does not do:

- **A run is not one trace.** A run of the worker is several graph runs, one per step between actions, each a trace of its own in one session; the waits between them (an action, a person's decision) are not traced, and nor are the workflow and its activities. A chat turn is one graph run, one trace.
- **No other OpenTelemetry traces.** The design's "standard traces" of the rest of the system are not built; `OTEL_EXPORTER_OTLP_ENDPOINT` is read by nothing.
- **No sampling and no redaction of its own.** Every run is traced in full while tracing is on.
- **The tests do not use a Langfuse server**: they read the spans they keep in memory. A server was tried by hand only (below).

### Stored credentials

The installation has three credentials, the secrets the code uses: the model provider's API key (`openrouter_api_key`, environment variable `OPENROUTER_API_KEY`) and the access tokens of the two repository hosts (`github_token`, `GITHUB_TOKEN`; `gitlab_token`, `GITLAB_TOKEN`). Each could only be set in the environment. Each can now also be stored for a workspace from the dashboard's Settings, and is then kept encrypted in the table `credential` (migration `e96ec2276ea4`), one row per workspace and name.

The code is in core's `credentials/`: `catalog.py` is the list of the three and the rule for an acceptable value, `cipher.py` seals and opens a value, and `resolution.py` says which value a credential has, where each comes from, and sets or removes a stored one. The rows are read and written by `db/credentials.py`. The API's routes are listed under [The API](#the-api), the screen under [The dashboard](#the-dashboard), and the worker's side is `credentials.py` at the top level of the worker (`WorkspaceCredentials`), with the analyzer's `repository_analyzer/repository_tokens.py`.

- **The environment wins.** A credential whose environment variable is not empty has that value, and a value stored for it is ignored. Storing one while the variable is set is refused (`CredentialSetByEnvironment`, the API's 409), because it would have no effect. A value stored earlier is kept, and its status still says it is stored, so the screen can say it is being ignored. Removing a stored value is always allowed and never touches the environment. A variable that is empty or holds only whitespace sets nothing, and a value from the environment is used without the whitespace around it; the model router and `RepositoryTokens` read their variables the same way, so this holds for the command line too.
- **A value is write-only.** It enters in the body of `setCredential` and nothing returns it or anything derived from it. A status is where the value in use comes from (`environment`, `stored`, `not_set`), the variable that would set it, and who stored a value and when. The query behind a status selects the name, the time and the user and never the nonce or the ciphertext; two tests read the SQL that was sent. Only `sealed_credential` reads those two columns, and what it returns is still encrypted. The one function that decrypts is `credential_value`, and its callers are the worker (each value it resolves at an attempt, a follow-up turn's model key among them) and the API's chat route (a turn's model key, through the shared `model_key`). The API's request model holds the value as a `SecretStr`, and a refused request is not quoted back (see [The API](#the-api)).
- **A stored value is bound to its workspace and its name.** It is sealed with AES-256-GCM under the installation's `ENCRYPTION_KEY` (32 random bytes in base64; `openssl rand -base64 32` makes one), with a fresh random 96-bit nonce for every value. The workspace's id and the credential's name are the associated data, so a row copied to another workspace or under another name does not open. A value that does not open is not told apart: a wrong key, a changed row and a moved row read the same, and neither the key nor a value appears in an error or in `repr`. `cipher.py` is the only module of core that imports `cryptography`; a test holds it to that.
- **What a value may be.** Whitespace around it is dropped, since a pasted key often ends with a line break; what is left must be 1 to 4096 printable ASCII characters with no space. A refusal names the rule and never repeats the value or a part of it. The rule is applied when a value is stored, not to a value from the environment. A name the catalog does not have is not repeated either ("there is no such credential"), since it may be a secret written in the wrong place.
- **Resolved at each attempt, so nothing is restarted.** The worker keeps no credential. It asks for the model provider's key when an attempt at a graph step begins, and for the two repository tokens each time a clone or a fetch of the run's commit is really made, with the workspace of the run. A key stored, replaced or removed in the dashboard is what the next attempt finds; a test stores a key after the worker's parts were built and another replaces one between two steps of a run. The API keeps none either: the model provider's key of a chat turn is resolved in the API's process, per message (see [The orchestrator chat](#the-orchestrator-chat)). 
- **The stored model key is OpenRouter's and goes to no other provider.** The model configuration names the variable of its provider's key (`provider.api_key_env` in `config/models.yaml`), and the worker looks at that variable first. Only when it is `OPENROUTER_API_KEY`, as shipped, is the stored value used when the variable is not set. A configuration that names another variable is another provider's: its key comes from that variable alone, neither `OPENROUTER_API_KEY` nor the stored value is sent to its endpoint, and a run without it fails with "the model provider's API key is not set: set the environment variable" and the variable's name, without pointing at Settings.
- **A credential that cannot be resolved ends the run, not the worker.** A model key set nowhere (`ModelKeyNotSet`) and a stored value that cannot be read, because the worker has no `ENCRYPTION_KEY` or another one (`CredentialUnreadable`), end the analysis with a sentence that names what to set and holds no value. Neither is tried again. A stored value that cannot be read does not matter while the environment sets that credential.
- **A credential is in no history and no checkpoint.** It is not in the graph's state, not in a workflow or activity input or result, and not in a failure; see [The worker](#the-worker).
- **`ENCRYPTION_KEY` is needed only for stored values, by both processes.** Without it the API answers `can_store: false` and refuses a `PUT` with 409 `encryption_key_missing`, and the worker cannot read what is stored. A key that is set and is not 32 bytes in base64 stops either process when it starts. The API and the worker must be given the same key. Credentials set in the environment work without it.
- **Who stored a value is the current user**, never a field of the request; in local mode that is the one fixed local user (`LOCAL_USER_ID`). Storing again replaces the value, the user and the time, which is the database's.

The model router gained what this needs and nothing else: `ModelRouter.headers(api_key=None)` takes the key to use, and `RouterChatModel.api_key` carries it, left out of `repr`. Without a key handed in, both read the environment as before, which is all the command line and the benchmark do.

What this does not do:

- **No key rotation.** Nothing re-encrypts. After `ENCRYPTION_KEY` is changed, every stored value is unreadable and has to be set again.
- **A status does not say whether a stored value can still be opened.** The list decrypts nothing, so a value sealed under another key is shown as "Set here" until a run fails on it.
- **The API and the worker each decide "the environment wins" from their own environment**, and the API reports `source` and `can_store` from its own. With a variable set for the worker only, the API stores a value and shows it as in use ("Set here") while the worker uses its environment's. With one set for the API only, the screen says "Set by the environment" and the worker finds no value. With no `ENCRYPTION_KEY` on the worker, or another one, the API reports that values can be stored, and every run that needs a stored one fails with the unreadable-credential sentence. Nothing compares the two processes. A model configuration that names another variable for the key is not read by the API either: the screen still offers the OpenRouter key, which that configuration never uses, and a chat turn resolves the same configuration it was started with. A key set for the API only answers the operator's chat turns and leaves the follow-up turns of the worker without one; a key set for the worker only does the reverse.
- **A value from the environment is not checked** against the rule for a stored one; apart from the whitespace around it, it is used as it is.
- **Whether a value is one its provider accepts is not checked**, when it is stored or later. There is no "test" button; a wrong key shows as a failed analysis ("the model provider answered HTTP 401").
- **Both repository tokens are resolved for every clone.** A stored GitLab token that cannot be read ends the analysis of a repository on GitHub too, and the reverse.
- **There is no login, and these routes raise what that costs.** Any process on this machine can store, replace and remove a credential by calling the API on `127.0.0.1:8000` directly; the dashboard's proxy stops another web site, not a local program. Whoever replaces the model provider's key with one of their own has every later analysis send the repository's content through an account they control. `set_by` is always the fixed local user, so nothing records who did it. See "There is no login" under [The API](#the-api).
- **"Not kept in this browser" is true of the dashboard's own code only.** The field is a password field, marked for password managers to leave alone, and a browser's password manager may still offer to save what is typed. This was not tried in a browser.
- **A secret pasted as the name in the path is not answered back, but it is logged.** The 422 and the 404 do not repeat it; the request path is still in uvicorn's access log.
- **No history of changes.** Replacing overwrites who stored a value and when, and a removal leaves no trace. There is no audit log.
- **Nothing erases a value from memory.** The API holds a submitted value for the request, and the worker holds the model key in the attempt's chat model for as long as the attempt runs, so a key replaced during a step is used from the next attempt on. A removed row is deleted, not erased from the database's files (as for [checkpoints](#graph-checkpoints)).
- **`GITLAB_HOST` is the environment's only.** It is not a credential, is read when the worker starts, and changing it needs a restart.
- **The command line and the benchmark do not read stored credentials.** `make analyze` and `make evaluate` take the key and the tokens from the environment, as before.
- **Downgrading the migration drops the table, and the stored values with it.**
- **Only these three credentials exist.** The other keys in `.env.example` (media providers, platform and advertising clients, OIDC, tracing) are read by no code. The table does not check a name: a row under a name the code no longer knows is never read, and nothing removes it.
- **No workspace isolation in the database**, as for every table: the scoping is in the queries, and beyond that in the binding of a sealed value to its workspace.
- **The value travels in clear on this machine**: from the browser to the dashboard on `localhost:3000` and from there to the API on `127.0.0.1:8000`, over plain HTTP on the loopback interface.

### Workspace settings: models and analysis limits

Two things that could only be changed in a file can now be chosen for a workspace in the dashboard's Settings: which models the roles call, and how far an analysis may go. Both are rows of the table `workspace_setting` (migration `bbcf991fe9b4`): one per workspace and name, each a JSON object, with who stored it and when. The names are `model.tier.<tier>`, `model.role.<role>`, `model.rejected_parameters.<model>` and `analysis.limits`.

The code is in core's `workspace_settings/`: `model_choices.py` and `analysis_limits.py` are what can be chosen and the rule of a valid choice, without a database; `model_settings.py` and `analysis_settings.py` store, remove and resolve them. The rows are read and written by `db/workspace_settings.py`. The routes are listed under [The API](#the-api), the screens under [The dashboard](#the-dashboard), and the worker's side is `workspace_settings.py` at the top level of the worker (`WorkspaceSettings`).

- **Models: a layer over the file, and the environment still wins.** The router's order is unchanged and its workspace layer is now filled: a role's model comes from `LLM_MODEL__<ROLE>`, then the workspace's choice for the role, then the role's `model` in the file, then its tier, then the file's default. A tier's model comes from `LLM_MODEL_<TIER>`, then the workspace's choice for the tier (new in the router), then the file. A role's other parts (fallbacks, temperature, length limit, reasoning effort) come from the workspace's choice, then the role, then the file's defaults. A choice the environment would override is refused (`model_set_by_environment`); a role's parameters can be chosen while the environment sets its model. The router's project layer is still passed by no code.
- **Rejected parameters are added to the file's.** A model marked in the dashboard as rejecting the temperature is sent none, like one listed under `unsupported_parameters` in `config/models.yaml`. The mark applies to a request's first model: the fallbacks receive the same request.
- **Limits of an analysis.** `max_steps` (5 to 200, default 40) and `max_cost_usd` (0.01 to 20, default 0.50) can be chosen; a limit not chosen keeps the analyzer's default. Why the bounds are what they are is in `analysis_limits.py`. `max_submissions` stays the analyzer's. The graph's own step limit, which stops a run as a defect, is set once when the worker starts, from the largest step limit a workspace may choose.
- **Read at each attempt, so nothing is restarted.** The worker reads a workspace's model choices when it makes the chat model of an attempt and its limits when an attempt begins, as it resolves the credentials. A choice made while a run is in progress is taken by the run's next attempt; the steps and cost the run already spent carry over. Tests store a choice after the worker's parts were built and between two steps of a run.
- **A stored choice is checked again when it is read.** One that breaks a rule (the rules became stricter, or the row was changed by hand) ends a run with a sentence that names what to reset in Settings, and is not tried again; the screens list it as unreadable and offer to reset it, so they still open. A choice for a tier or a role the configuration no longer has is ignored.
- **The catalogue.** The API reads the provider's list of models (`GET <base_url>/models`, sent without a key) through `llm_catalog.py`, keeps it for ten minutes, and does not try again for a minute after a failure. An entry is kept only when its id is a model slug, and only the parts that have the expected shape. The dashboard suggests its models in every model field and shows what the check found for each role. It replaces `fetch_catalog`, which nothing called. A role of kind `decisions` is not checked: its models are not in the catalogue (see [Decision calls](#decision-calls-and-the-screening-of-search-results)).

What this does not do:

- **The command line and the benchmark do not read these choices.** `make analyze` and `make evaluate` take the models from `config/models.yaml` and the environment, and the analyzer's default limits.
- **The API and the worker each read their own environment and their own copy of the configuration.** With `LLM_MODEL_FAST` set for the worker only, the screen shows the workspace's choice as in use while the worker uses the variable. Nothing compares the two processes.
- **The check is the catalogue's word, not a test.** It does not call a model; a model that the catalogue lists with tools may still fail on a request. There is no test button and no cost estimate. When the catalogue cannot be read (no network, a provider without one), nothing is checked or suggested and any `provider/model` is accepted.
- **No history of changes.** Choosing again overwrites who made the choice and when; there is no audit log. Who made it is the one fixed local user, and any process on this machine can change a choice through the API (see "There is no login" under [The API](#the-api)): whoever chooses another model sends every later analysis's repository content to it.
- **The provider's address and `GITLAB_HOST` stay in the environment.** Either would decide where a stored key or token is sent, so neither can be set from the dashboard.
- **Per-project choices do not exist.** The router has a project layer above the workspace's; nothing stores one.
- **Process settings stay in the environment**: the database, Temporal, `ENCRYPTION_KEY`, `ANALYSIS_TIMEOUT_MINUTES`, `ANALYSIS_MAX_ATTEMPTS` and `WORKER_MAX_CONCURRENT_ACTIVITIES`. The last three set how long the cleanup waits before it treats a run as lost, which has to be known when the worker starts.

### The researcher

The design's researcher (the report's section "Researcher: Sourced Findings from Public Sources", figure `fig_researcher`) answers questions from public web pages and returns *findings*: short statements, each with the pages it rests on. It is built in its first form and runs in the worker as a Temporal workflow on the [agent runtime](#agent-runtime), started through the API or by the chat's `start_research` (see [The orchestrator chat](#the-orchestrator-chat)). It publishes nothing and spends nothing but its model calls and, for now, its searches: `search_web` is temporarily declared as spending, so the policy gate holds every search for a person — the temporary exception under [Policy gate](#policy-gate), until the approval surface has been tried, when it goes back to an internal action.

The code is `packages/core/src/openmarketer_core/research/`: `questions.py` (the request, `ResearchRequest`), `request.py` (the use case `request_research`: store the run, then start its workflow, and mark the run failed with `ResearchNotStarted` when the start fails; who asked is `person`, `orchestrator` or `run`), `workflow_contract.py` (the workflow `Research`, its queue `openmarketer-research`, its id `research-<run id>` and its input, which names the run's three identifiers and nothing else), `failures.py` (what a run that ends without a report raises), `web_search.py` (a client of an installation's SearXNG instance), `page_fetch.py` (fetching one public page), `page_render.py` (rendering a script shell with a headless browser over the Chrome DevTools Protocol), `page_text.py` (the text of a stored page as a model is shown it), `page_store.py` (the pages in S3-compatible object storage), and `research_agent/` (`definitions.py`: the agent, its state, its context and its two actions; `rules.py`: the limits, the prompts, the schemas of what a model submits, the screening's texts and the check of findings; `graph.py`: the nodes and the routes). The rows are in `db/research_runs.py`, `db/research_pages.py` and `db/research_store.py` (tables `research_run`, `research_page` and `research_report`; migrations `c5f38eddbf72` and `4f6e5ca41a1a`). The worker's side is `apps/worker/src/openmarketer_worker/researcher/`.

**The request.** One to five questions of at most 300 characters each; at most five topics and five competitors of at most 60 characters each; a time window of at most 40 characters; and `max_sources`, how many pages the run fetches at most, from 1 to 12, 8 by default (`questions.py`). It is read strictly (`extra="forbid"`) and stored with the run, and it is read again from the database whenever the run is executed: a stored request that no longer fits ends the run (`StoredResearchRequestInvalid`). A project may have several research runs at once, unlike analyses.

**The graph** (`research_agent/graph.py`):

```
plan -> search -> ... -> search -> screen -> fetch -> ... -> fetch -> read -> ... -> read
  ^                                                                                  |
  |                                                  synthesize -> check <----------+
  |                                                                    |
  +-------------------------- one more round ------------------------->| (unanswered)
                                                                       v
                                                                    report -> END
```

- `plan` asks the `researcher` role for the round's queries with the forced tool `submit_queries` (`QueryPlan`): at most six, at most 300 characters each, and the SearXNG categories to search, of which only `general`, `news` and `science` are kept, each once (`general` when none is). `it` is no longer offered or kept: in a real run about exam-prep apps about half the results came from it (container images, developer documentation) and none bore on the questions. A plan may still name up to six categories, so a model that names `it` is searched without it rather than rejected; a thread stored while `it` was allowed keeps it for the searches of its current round, which must ask for what they asked before (an action's request is compared when it is resumed), and `search_web` accepts up to six categories for that reason. A query already searched in an earlier round is dropped; a round with no new query ends the run. From the second round on, the prompt names the questions still without a finding and the queries already searched.
- `search` asks for the action `search_web`, one query at a time; its results join the candidates with the query that found them. A search that fails after its attempts is a note, and the run goes on.
- `screen` drops the candidates whose address, title and snippet show a page that is not about the request, before anything is fetched; see [Decision calls and the screening of search results](#decision-calls-and-the-screening-of-search-results).
- `fetch` asks for the action `fetch_page`, one candidate at a time, until the run holds `min(max_sources, 12)` pages or no candidate is left; a fetch that fails is a note. The graph keeps the page's id, its address after redirects, its title and its injection flags, never its text.
- `read` has the reader read one stored page (below).
- `synthesize` asks the `researcher` role for findings with the forced tool `submit_findings` (`DraftFindings`: at most 12, each with a question's index, a statement of at most 500 characters, a confidence from 0 to 1 and one to five cited pages with quotes). It is given the questions and the readings as JSON, never a page: at most 4,000 characters of each reading and 40,000 in all, the readings of earlier rounds included. `findings` has no default: nothing found is an explicit `{"findings": []}`, which the prompt asks for, and a submission without the field (`{}`, which `deepseek/deepseek-v4.1-flash` sent in a real run) is rejected and asked for once more, instead of being read as nothing found. Both answers of that run were cut off at the role's length limit, then the 4096-token default, all of it spent on the model's thinking, which OpenRouter counts in the answer: the first held no tool call and the second the `{}`. The role's `max_tokens` is 16384 since 2026-10-17, and an answer cut off (`finish_reason` `length`) is now told so when asked again and named in the error that ends a run cut off twice. With no reading it submits nothing. When the second answer is not readable either, the run ends in the first round; in a later round the findings earlier rounds checked are kept, with a note, and the run goes on to `check`.
- `check` is code (below), and merges the round's checked findings into the run's (`rules.merged_findings`): they replace the earlier rounds' findings only for the questions they answer, and earlier findings of the questions the round did not answer stay, so a later round that finds nothing no longer empties the report (as it did in a real run whose second round answered `{}`). Findings tied to no question (`-1`) are treated as one question in this. The gaps the next round plans for are the questions the merged findings leave unanswered (`rules.unanswered_questions`). The state's shape is unchanged: a thread stored before this keeps its latest check's findings in `findings`, which the next check merges into. The route after it is the design's `decide`: back to `plan` while questions are left without a finding, fewer than `max_rounds` rounds were made and the cost is under its limit; otherwise `report`.
- `report` does nothing: the state is the report, and the worker's `finish` stores it.

A submission that does not fit is told what to fix and asked once more inside the same node (`SUBMISSION_ATTEMPTS = 2`), and an answer the model's length limit cut off is told that as well; a second one ends the run with `ResearchError`, which says the last answer was cut off when it was. `ChatReply` keeps the provider's `finish_reason` for this (`llm.py`): a thinking model can spend its whole `max_tokens` on reasoning and submit nothing, and that was previously indistinguishable from a refusal (see the run below). The limits are `Limits` in `rules.py`: six queries a round, two rounds, 12 pages, $0.75. They are constants: no environment variable or dashboard setting changes them, and the analysis limits of [Workspace settings](#workspace-settings-models-and-analysis-limits) do not apply to research. The cost limit is checked before every node that calls a model.

**The two actions** (`research_agent/definitions.py`), both declared `ActionEffect.INTERNAL`, so the [policy gate](#policy-gate) lets them run without a person:

| Action | Payload | Answer | Attempts |
|---|---|---|---|
| `search_web` | the run's identifiers, a query (2 to 300 characters), categories | at most 5 results (`web_search.MAX_RESULTS`), each `https` only, its title cut at 200 characters and its snippet at 300 | 30 seconds each, 3 attempts, 5 seconds apart |
| `fetch_page` | the run's identifiers, a URL (8 to 2,048 characters) | the page's id, its address after redirects, its injection flags | 120 seconds each, 2 attempts, 10 seconds apart, a heartbeat every 30 seconds |

The handlers are the worker's (`researcher/research.py`). The search asks SearXNG's JSON API at `SEARXNG_URL`; it needs no key. A fetch goes through `PublicPageFetcher` (`page_fetch.py`): only `https`; a host that resolves to a private, loopback, link-local, reserved or multicast address is refused; `robots.txt` of every host is read first and honoured for the crawler's user agent; only `text/html`, `application/xhtml+xml` and `text/plain` are taken, and a body over 2 MiB is refused while it is read; at most three redirects, each vetted again. An HTML page with less than 200 characters of text and scripts is rendered by the headless browser at `LIGHTPANDA_URL` (`page_render.py`), and a failed render keeps what HTTP returned. A refusal (`FetchRefused`) is not tried again; a failure that may pass (`FetchUnavailable`) is. The page's bytes go to object storage under `pages/<workspace>/<project>/<run>/<page>.html` and its row to `research_page` (address, title, type, size, SHA-256, flags); a run fetches one address once, and a repeated fetch of a stored address answers from its row. The flags are computed when the page is fetched: `rules.INJECTION_SIGNS` are eight patterns (such as "ignore previous", "system prompt", "you are now a") searched in the page's text.

**The quarantined reader.** `read` is the one node that sees a page's text. It reads the text back from object storage through the context (`page_text_of`), as `page_text.plain_text` extracts it: scripts, styles and markup taken out, cut at 20,000 characters. It calls the role `reader` with no tools at all (the router refuses tools to a role whose `requires` does not list them, and `config/models.yaml` gives the reader none), with the page placed between markers as data, and reads the one JSON object of the answer strictly into `Reading`: a summary of at most 800 characters, which has no default so that `{}` is asked for again rather than read as a page that says nothing, at most six key points, at most five exact quotes of at most 500 characters each, the page's date, and a note per question. An answer that is not that object, or has a field the reading does not have, is told so and asked once more, and an answer the model's length limit cut off is told that as well; a second one ends the run, saying so when it was cut off. The reader's `max_tokens` is 8192 since 2026-10-17, up from 3072, which two reader answers of a real run had filled exactly, cut off mid-thought. A page whose text cannot be read is left out with a note.

**The check of findings** (`rules.check_findings`, in the node `check`). A cited page that this run did not fetch is dropped from the finding; a quote shorter than eight characters, or one that does not appear in the stored page's text (compared after Unicode NFKC normalisation, collapsed white space and case folding), is dropped; a finding left with no page is dropped. A finding whose quotes were all dropped keeps its pages, with no quotes. A finding naming a question the run does not have is kept with the index `-1`. Every finding is marked `flagged` when every page it rests on raised an injection flag. Everything dropped is a note of the report, and the questions no finding of the run answers, after the round's findings are merged in, are what the next round plans for.

**The worker's workflow** (`apps/worker/src/openmarketer_worker/researcher/`): `workflow.py` is `Research`, the researcher's agent with three hooks: `before` marks the run started and takes this worker's limits for the graph's steps from that activity, `after` tells the chat that asked for the run, if one did, that it finished, and `failed` records why on the run, in the researcher's words, and then tells that chat it failed (see [Chat events and the follow-up turn](#chat-events-and-the-follow-up-turn)). `activities.py` holds the three activities those hooks call (`start_run`, `record_failure`, `record_end`); `research.py` is what the runtime's activities do for a run: the initial state from the stored request, the context of an attempt (a chat model and a decision model made for the run's workspace at each attempt, with the workspace's key and model choices, and the stored pages' text), `record_progress`, which stores each node's events, the two handlers, and `finish`, which stores the report and marks the run succeeded in one transaction and answers with the report's id and how many findings it holds; `WordedSteps` turns a failure of a step into a type and a message that may be shown (`ModelUnavailable` is tried again, the rest of a research's failures end the run). `steps.py` has the names, the failure types and the sentences; `policy.py` the limits of the steps (`ResearchPolicy`: 30 minutes an attempt, a heartbeat within a minute, 5 attempts, a first retry after a minute) and `longest_research_seconds`, how long a run can be in progress at most, which the cleanup of left-over checkpoints of research runs uses; `settings.py` reads `RESEARCH_TIMEOUT_MINUTES`, `RESEARCH_MAX_ATTEMPTS`, `SEARXNG_URL` (`http://localhost:8888` by default), `LIGHTPANDA_URL` (`http://localhost:9222`) and `RESEARCH_PAGE_RETENTION_DAYS` (30), and stops the worker at start-up on a value that does not fit; `retention.py` is the schedule, once a day, that removes the oldest expired pages, 500 a round, their objects first and then their rows; `wiring.py` builds all of it, and `main.py` registers it beside the analyzer. The dev stack runs SearXNG (port 8888) and Lightpanda (9222, with `--obey-robots`) for it, and the pages go to its MinIO bucket `openmarketer-assets`. The chat model and the decision model of an attempt are traced when [tracing](#tracing-to-langfuse) is on.

**The API** (`apps/api/src/openmarketer_api/routes/research.py`), under `/v1/projects/{project_id}/researches`: `POST` starts a run (202 with the run; the body is a `ResearchRequest`), `GET` lists a project's runs newest first with `limit` and `cursor`, `GET /{run_id}` reads one run's status, and `GET /{run_id}/report` reads the report of a run that succeeded: its questions, its checked findings with their pages and quotes, its notes, its cost, its model and who asked. Everything is read from the database; no route asks Temporal. The errors are `project_not_found` and `research_not_found` (404), `research_report_not_found` (404 while the run has no report, unfinished or failed) and `research_not_started` (503, the run stored as failed; start another). The dashboard's error map knows the three research codes (`apps/web/src/lib/api/api-error.ts`, commit `1305403`), so the types the dashboard generates from the contract compile; the dashboard's Research screens read through them.

What the researcher does not do, from the design:

- **The dashboard shows research but does not start it.** The dashboard's proxy forwards the three read routes (`listResearches`, `getResearch`, `getResearchReport`) and the Research screens poll an unfinished run, but a run is started with the API directly or through the chat's `start_research`: the design's "By a person, from the dashboard" is not built.
- **No agent asks for research.** The design's run-and-wait action `research` of another agent is not declared by any agent; the column `research_run.origin_action_id`, which lets a repeated attempt of such an action find the run it made, exists and is tested in core, and no caller passes it.
- **No block list of domains.** The design's `scope` "drops domains on the project's block list"; there is none.
- **No search provider's official API.** The search is a self-hosted SearXNG; which engines it asks, and how, is SearXNG's configuration (`deploy/compose/searxng/settings.yml`, which keeps SearXNG's defaults).
- **The limits are constants.** A person cannot change the rounds, the queries, the pages or the cost limit of research without changing the code.
- **The number of fetches is bounded by the candidates, not by the page cap.** A fetch that fails adds no page, so a run whose fetches fail may ask for up to every candidate (five per query, six queries, two rounds). `policy.longest_research_seconds` counts 12 fetches per run (`pages_of_a_run`), so with many failed fetches a run can be in progress longer than the time after which its checkpoints are treated as left over.
- **An object can be left in storage.** A fetch whose final address (after redirects) is already a page of the run stores the bytes under a new key before `store_page` answers with the existing row; the new object has no row, so the retention schedule never removes it.
- **The address check and the connection resolve the host separately.** `page_fetch.py` checks the addresses the host resolves to, and httpx resolves it again when it connects; the connection is not pinned to the checked address. A page rendered by the headless browser is loaded by the browser itself, with its scripts, subresources and redirects, which these checks do not see.
- **The reader's answer is JSON in text, not structured output.** The `reader` role lists `structured_output` in `config/models.yaml`, and the call sends no `response_format`.
- **Runs in flight cannot be continued by a worker with the chat events.** Adding `after` and `record_end` changed which activities `Research` schedules, without versioning or a patch marker in the workflow. A worker with this code that replays the history of a run started by an earlier worker meets a command it would not have issued, which Temporal reports as a non-deterministic workflow, and the run hangs. Restart the worker with no research run in progress (let them finish, or terminate them and mark them failed by hand). This is read from the two versions of the workflow and its docstring; it was not tried.
- **A project with research runs cannot be deleted**: see [Deleting a project](#deleting-a-project).
- **No run outside the tests is recorded.** Nothing here records a research run against the dev stack's SearXNG, Lightpanda and MinIO with a real model.

### The creative studio in the worker

The studio's agent (core's `studio/studio_agent/`) runs in the worker as the `CreativeStudio` workflow on the task queue `openmarketer-studio` (`apps/worker/src/openmarketer_worker/creative_studio/`, the researcher's shape). The API and the chat's request action start it with the run's three identifiers (`studio/workflow_contract.py`).

- **Hooks.** `before` marks the run started and takes the step limits from the worker's settings (`StudioPolicy`: 20 minutes an attempt, four attempts, a first wait of a minute); `after` and `failed` tell the chat, as the researcher does: `record_end` stores the run's last event (`finished` with the asset, the version and `needs_review`; `failed` with the reason) and the workflow starts `ChatFollowUp` with `run_kind` `studio-run` as an abandoned child. `failed` records the reason with what the run's stored versions cost (`db/media_assets.cost_of_run_versions`, added for it).
- **Handlers** (`studio.py`). `generate_image` and `edit_image` call the image provider (`OpenRouterImages`, role `image_generator`, traced with `tracing.media`), fit the image to the platform's size, store its bytes under `asset_key` and its row with `add_version` keyed by the action's id, and answer `{version_id, asset_id, width, height, mime, size_bytes, cost_usd}`; a version the action stored before is answered from its row without asking the provider again, so a paid image is paid once. References are versions of this run and assets of the project (their current version); anything else fails the operation before anything is paid. `render_html` and `run_python` run in the Docker sandbox with the named versions beside them as `<version id>.png`; a program that fails, times out or leaves no accepted image fails the operation (`OperationFailed`, not retried) with a short reason the graph reads (the program's error stream, cut to 500 characters; the sandbox is given no secret). `read_text` is the sandbox's OCR. A provider or a sandbox that cannot be reached is `StudioUnavailable`; a paid image that object storage loses is `DatabaseUnavailable`, the type the creative budget commits the estimate for.
- **Spending.** The two paid actions declare an estimate (`@worker.estimate`): the image role's `estimate_usd_per_image` under the workspace's models; the gate reserves it in the ledger, runs it under `MEDIA_AUTO_APPROVE_USD`, holds a dearer one for a person, refuses one past the month's cap, and commits the `cost_usd` the handler reports. The run's limits carry the same estimate (`Limits.image_estimate_usd`), so the model is not offered an image the asset's cap cannot pay for.
- **Context.** Each attempt resolves the chat model and the image provider for the run's workspace, with the one OpenRouter key it has then; the brand kit comes from the project's latest approved profile (`brand_kit_of`), and `image_of` reads a version of the run from object storage. No key, image or brand kit is in the state, a checkpoint or the history; the history does hold the operations' payloads (a prompt, a page or a program the studio's model wrote), as the agent's declarations bound them.
- **Settings** (`settings.py`): `STUDIO_TIMEOUT_MINUTES`, `STUDIO_MAX_ITERATIONS` (rounds), `STUDIO_MAX_COST_PER_ASSET_USD`, and the sandbox's `STUDIO_SANDBOX_IMAGE`, `_TIMEOUT_S`, `_MEMORY_MB`, `_CPUS`, `_PIDS`, `_MAX_OUTPUTS`, `_INSTALL_TIMEOUT_S`, `_PROXY_NETWORK`, `_PROXY_URL`, `_RUNTIME`. A value that does not fit stops the worker at start-up, and so do sandbox limits under which a program or a render cannot finish in the time its action is given. `STUDIO_SANDBOX=none` is not read yet: the sandbox is always Docker.
- **Checkpoints.** `longest_run` is every step and operation at its limits with every paid image waiting the longest a person may take (three days each), which is weeks; core's `remove_checkpoints_of_studio_runs` is the stricter rule for runs that ended.
- **Not done.** No test runs the real sandbox or the real provider from the workflow (both are faked there; each has its own tests in core).

Changing the follow-up for the studio changed `ChatFollowUpInput` (it gained `run_kind`), its workflow id (`chat-follow-up-<run kind>-<run id>`) and its activity's name (`follow_up_on_run`): a `ChatFollowUp` or a `Research` run in flight when the worker is updated cannot be replayed by the new code (there is no versioning).

### Decision calls and the screening of search results

A *decision call* asks a model yes-or-no questions about a list of texts, and the answer is one probability per question, with no text written. It goes to OpenRouter's decisions endpoint, which is in alpha: `provider.decisions_url` in `config/models.yaml`, set by `OPENROUTER_DECISIONS_URL` and `https://openrouter.ai/api/alpha/decisions` by default. A role that makes such calls is of kind `decisions`, a third kind beside `chat` and `embeddings` (`llm_config.py`). It names its model and nothing else: the configuration refuses a decisions role with a tier, a temperature, a length limit, fallbacks, `requires`, a reasoning effort or dimensions, and the dashboard's Settings, Models refuses any part of a choice but the model. The model is resolved like any role's, so `LLM_MODEL__SCREENER` and a workspace's choice apply.

The code is `packages/core/src/openmarketer_core/decisions.py`: the port `DecisionModel` that an agent depends on, and `RouterDecisionModel`, its adapter over httpx, which posts the body `ModelRouter.build_decision_request` builds (the model, the texts and the questions) with the same key and headers as a chat call. The question is plain data in `decision_questions.py`, which imports no HTTP client, so the researcher's rules build it without loading the adapter. Only the yes-or-no question (the endpoint's `noul`) is implemented; the endpoint also knows choice, score and box questions, which nothing asks yet. The answer is read strictly: every question asked must be answered with a probability from 0 to 1, and an answer to a question not asked is refused, counted and not named, since its key is the endpoint's text. What the endpoint writes when it refuses a request is logged and not put in the error, as for a chat call.

**The one role is `screener`**, with the model `respan/span-02`. The researcher uses it in a node `screen`, which runs after a round's searches and before any fetch: each search result not fetched yet is judged by its address (cut at 200 characters, `MAX_SCREEN_URL_CHARS`), its title, its snippet and the query that found it, all labelled as web text and data only, against the run's request (its questions, topics, competitors and time window), in batches of 10 (`SCREEN_BATCH`). Each result's question asks what the page is about, not whether it shares words with the request: "Would a market researcher answering the research questions want to open search result r0? Judge what the page is about, not shared words: a container image, code repository, package or developer documentation is not about the questions' market even when a word in its name matches", yes meaning "The page is about the subject of at least one question" and no "The page is about something else, or only shares a word with the questions". The earlier question ("does it bear on any of the questions or topics?") kept Docker images such as `15971597/tekrar` at 0.94 in a real run, because "tekrar" is a word of "aralıklı tekrar"; adding the address alone did not change that. A replay of that run's results with the new wording and the address, reported by the caller of this change and not repeated here, gave every container image and documentation page 0.00 to 0.01 and every relevant result 0.91 to 0.97. A result whose probability is under 0.5 (`SCREEN_KEEP_AT`) is dropped, and so never fetched; the threshold is applied in code, not by the model. The rules and the texts sent are in `research/research_agent/rules.py`, the node in `graph.py`. After `screen` and after each fetch the graph fetches the next result, or, with nothing left to fetch, reads the next stored page, or goes on to `synthesize` when no page waits to be read; a run whose results were all dropped, or whose fetches all failed, now reaches `synthesize` instead of failing in `read`. The worker makes the decision model of each attempt for the run's workspace, with the same OpenRouter key and the same workspace's model choices as the chat model (`researcher/wiring.py`), and the run's time budget counts one more graph step per round for `screen` (`researcher/policy.py`).

What it does not do, and what is not known:

- **The screening fails open.** A batch whose call fails is kept whole, with a note in the run, and the run goes on: screening only saves fetches. A result left without an answer is kept too.
- **No provider routing is sent with a decision call.** A chat call carries `provider` with `data_collection: deny`; a decision call does not. The endpoint accepts the field without saying whether it honours it (as reported by the caller of this change, from a probe), and whether it honours it cannot be verified, so the code does not send a preference it cannot show is kept. The research questions and the titles and snippets of search results therefore reach the endpoint's provider without that preference.
- **The model is not checked against the catalogue.** `respan/span-02` is not in OpenRouter's public `/api/v1/models` list, which lists chat models, so the capability check of Settings, Models skips every decisions role; an unserved model is reported by the endpoint when it is called.

### Private repositories

The two repository tokens reach intake as `RepositoryTokens`. The CLI reads `GITHUB_TOKEN` and `GITLAB_TOKEN` from the environment. The worker resolves both for the run's workspace each time a clone or a fetch is made: the environment's value, otherwise the one stored from the dashboard (`repository_analyzer/repository_tokens.py`; see [Stored credentials](#stored-credentials)). Wherever a value came from, it is handed over under the same two names, and `repository_analysis/intake/credentials.py` alone decides which one, if any, a clone may carry.

- `GITHUB_TOKEN` is for `github.com`. `GITLAB_TOKEN` is for `gitlab.com`, or for the host named by `GITLAB_HOST` when that is set (a self-hosted GitLab; `host` or `host:port`).
- A token is offered only to an `https://` URL whose host is exactly the configured one: compared in lower case, without a trailing dot, on port 443 unless the configuration names another. There is no suffix matching (`github.com.evil.example`), and a URL with a user name, a backslash, a space or a control character gets no token.
- A repository on any other host is cloned without credentials, so public repositories work as before.
- git receives the token as a header configured for that origin only (`http.<origin>.extraHeader`). Scoping the header is not enough: after a redirect git sends its extra headers to the new host on the following requests, which is one of the two reasons no redirect is followed (next section).
- The token is not in the stored project URL (credentials in a URL are refused), not in a workflow or activity input, and not in an error message: errors of a clone are fixed sentences, and the token is removed from git's output before that is logged.

Before this, the command line sent whichever of the two tokens was set to any host a URL named.

What this does not do: a private repository has not been cloned with a real token (see below); one GitLab host can be configured, not several, and only in the environment (`GITLAB_HOST`); a token in the environment is per installation and a stored one per workspace, of which there is one, and none is per project.

### Cloning from an untrusted host

A repository URL comes from whoever can create a project, and the host behind it answers as it likes. `repository_analysis/intake/git.py` runs git so that neither can do more than be cloned:

- **git does not get the environment of the process.** Its environment is built from a list: `PATH`, `TMPDIR`, the proxy variables for HTTPS (`HTTPS_PROXY`, `https_proxy`, `NO_PROXY`, `no_proxy`) and the variables that add a certificate authority (`GIT_SSL_CAINFO`, `GIT_SSL_CAPATH`, `SSL_CERT_FILE`, `SSL_CERT_DIR`, `CURL_CA_BUNDLE`). An installation behind a proxy or with its own authority needs those; none of them switches a check off. Everything else is withheld: the model key, `DATABASE_URL` and the tokens never reach git or a program it starts, and `GIT_SSL_NO_VERIFY`, `GIT_CONFIG_*`, `GIT_TRACE*`, `GIT_ASKPASS`, `HTTP_PROXY` and `ALL_PROXY` set in the process change nothing. `HOME` is `/dev/null`, so there is no user configuration and no `~/.netrc`, and `LC_ALL=C` keeps git's messages in the language their cause is read from.
- **git asks nobody for a password.** `GIT_ASKPASS` and `SSH_ASKPASS` are set and empty, `core.askPass` and `credential.helper` are empty, and prompts are off. Before this, git inherited the environment, and a host that answered 401 made git run the askpass program of the process (the terminal of an editor sets one) and send its output to that host; a test keeps that reproduction.
- **No redirect is followed**, with or without a token (`http.followRedirects=false`). Without a token a redirect could still send the clone to an address the caller did not name, such as one inside the network the worker runs in.
- **Only HTTPS is used for a remote repository** (`protocol.allow=never`, `protocol.https.allow=always`; a local folder given on the command line allows `file` instead). If redirects were followed, a redirect to `http://` would still not be contacted.
- **What the host writes is not repeated.** git prints text from the host (`remote: ...`). It is logged, with the token removed, and the error is one of: the repository was not found or needs a token that is not configured or has no access; the URL redirects; the clone did not finish within 300 seconds; the host could not be reached; the connection could not be secured (TLS); the repository could not be cloned. The cause is read from git's own `fatal:` and `error:` lines only, with quoted text such as the URL removed, so neither the host nor the URL chooses it. Output that is not valid UTF-8 no longer stops the clone with an unexpected error.

Consequences:

- **A repository whose URL redirects cannot be analysed** until the project uses the address it redirects to. That is the case for a renamed or moved repository, and on gitlab.com for every URL that does not end in `.git` (`https://gitlab.com/group/project` redirects; `https://gitlab.com/group/project.git` does not). github.com and bitbucket.org serve both forms. The failure message says so. Projects are not changed to the new address automatically.
- **Any HTTPS host is still cloned from**, including one on the local network: redirects to such an address are closed, a URL that names one directly is not.
- **`gitleaks` still gets the environment of the process.** It is a local program that opens no connection; it has not been given a reduced environment.
- The operator of a terminal sees git's output and the provider's answer as log lines on standard error, because the command line does not configure logging.

### Golden-repository evaluation

The benchmark measures the analyzer against expected profiles. It is in `packages/evaluation/` and runs from the command line:

```bash
make evaluate                       # says what a run would make and spend, and stops
make evaluate live=1                # runs it: every case, 3 analyzer runs each
make evaluate live=1 case=excalidraw runs=1 judge=claude-code
make evaluate rescore=evals/results/<id>   # scores a stored run again, without a model call
```

- **A golden case** is a folder in `evals/cases/` with `case.yaml` (the repository, a full commit id, how the label was made, whether it lists every feature, and notes on what is weak about it) and `expected_profile.json`, checked against the schema when the case is loaded. A case names a commit, never a branch. How a label was made is one of four values, from an analyzer draft approved unchanged to written by a person, and the report prints it next to every score of the case.
- **Running** goes through the benchmark's own `analyze_repository` (`packages/evaluation/src/openmarketer_evaluation/runner.py`), with the case's commit: intake, the extractors and the analyzer's `analyze`, in memory and in one call. These are the steps the worker takes one by one in a workflow, not the worker's code path: no clone action, no checkpoints, no stored result. For this, intake can fetch one commit instead of the default branch (`run_intake(..., commit=...)`, `clone(..., commit=...)`): only a full 40-character id is accepted, that commit alone is fetched into a new repository, under the same lock-down and the same timeout as a clone, and a commit the host does not serve or that comes out different is an `IntakeError` that leaves nothing behind. The product's clone of a run is still of the default branch; the worker uses the same fetch of one commit when a later step needs the run's commit on a disk that does not hold the clone. A run that ends without a profile (a failed clone, a provider error, the step or cost limit) is recorded and scored as such, and the benchmark goes on with the next run. Runs are made one after another.
- **The judge** answers what code cannot decide: which drafted feature is which expected one, whether the lines a claim cites say what it says (at most 30 claims per run by default), and whether the free-text brand voice and audience agree. Its replies are parsed strictly; one that does not have the asked shape is recorded as malformed, and nothing is read into it. A benchmark does not start when the judge is the analyzer's model or one of its fallbacks, and a run that a fallback of the analyzer judged is marked in the report. The judge is reached in one of two ways: the `judge` role through the model router (the default, spends provider credit), or `--judge claude-code`, Claude Code's headless mode on the maintainer's subscription. The second runs with no tools, MCP servers, skills, hooks or project instructions, in an empty temporary folder, with an environment that holds no provider key, and every reply whose session report shows anything else is refused. On that route the role's temperature, length limit and structured output are not applied and the cost is not known; the report says so.
- **Scoring** is pure functions over the expected profile, the draft and the verdicts, one named function per metric in `scoring.py`: product name, type and platforms; features matched, missed and not in the label; recall, and precision only when the label says it lists every feature; drafted `live` features whose counterpart is not `live` (the costly error); agreement of statuses; claims that cite evidence and how many of them the judge found supported; the sections, business model, attribution, deep links, palette and analytics tools. The analyzer's cost, model calls and time, and the judge's calls and cost, are reported next to them.
- **Results** go to `evals/results/<benchmark id>/`: `config.json` (models of both roles, limits, the code's commit and whether it had uncommitted changes, the cases with a hash of each label), the drafts in `raw/`, the verdicts in `verdicts/`, `scores.json` and `report.md`. Scores are computed again from `raw/` and `verdicts/` alone, so a changed metric is applied to an old run without a model call; a label that changed since the run is pointed out. The cited lines shown to the judge (`excerpts/`) and replies that could not be read (`malformed_replies/`) repeat repository content and are kept out of git by a `.gitignore` the run writes into its own folder. The report gives, for every metric, the number of runs it comes from with the minimum, median and maximum, and starts with the limits of the result.

The first benchmark run is committed: `evals/results/20261010T085633Z/`, one run on Excalidraw at commit `4c00f31`, with the free analyzer model and a judge reached through Claude Code. The draft named the product and its type and platforms correctly, matched 13 of the 18 expected features (recall 0.72), marked no feature `live` whose counterpart is not, and agreed on the status of all 13 matched features. Every one of its 28 features was `live`, 15 of them not in the label, which is not exhaustive. Of 30 claims the judge was asked about, 14 were supported by the cited lines and 16 partly; 3 were not asked about. The run took 29 model calls, 169 seconds and no money; the judge made 33 calls. One run on one repository, against a label written by an AI assistant: this shows that the benchmark works end to end, not how good the analyzer is.

- The benchmark with the judge reached through the model router. The only live run used `--judge claude-code`; the default route has been run in the tests only. Fetching a pinned commit has been run against github.com only.

## Model for the analyzer

The `repo_analyzer` role uses the fast tier, and the fast tier is the free model `apodex/apodex-1.1-mini:free`. This is a design decision, described in the report's section on model configuration: analysing a repository costs nothing, and the model's output is checked in code and reviewed by a person. The first version of the design had the role on the strong tier. The quality of profiles from the free model has not been measured; `LLM_MODEL__REPO_ANALYZER` moves the role to another model.

## Model behaviour worth knowing

Weak or free models produced these failures against the analyzer; each is handled in code and covered by a test:

- Nested sections of the profile sent as JSON text instead of objects. They are decoded before validation.
- `confidence` left out, or the schema default `0` copied back. The tool schema shown to the model now requires `confidence` and shows no default, and a submission with a missing confidence, or `0` next to cited evidence, is rejected.
- The same rejected submission sent again. After three submissions, or when the run is out of steps or budget, the profile is repaired in code (bad evidence removed, unevidenced features set to `unknown`) and the corrections are reported. A submission that still does not match the schema at that point ends the run with an error.

Other things observed:

- A request names fallback models. When the primary model fails, OpenRouter serves the next one, which may be paid. The reply states which model answered and the CLI prints it. The name is kept only if it is printable text of 1 to 200 characters; otherwise the name that was asked for is used, because the name is stored with the run and a NUL character in it made every checkpoint write fail.
- Free models are rate limited upstream (HTTP 429). Runs are best started one at a time.
- Prompt caching is not used.

## What comes next

Saving results to the database is done, the API can create a project, have the worker analyse it as a workflow, and read, edit and approve its profile, and the dashboard does all of it in a browser. The dashboard reads projects, runs and profile versions from the API's list and read routes, and its Settings store the model provider's key and the repository tokens, and choose the workspace's models and the limits of an analysis, all of which the worker resolves at each attempt; no analysis has yet run on a stored key or a chosen model outside the tests. A retried analysis in the worker continues from stored checkpoints, on the commit the run first read. The layer through which a graph asks for side effects (the agent runtime) is built and the analyzer runs on it, with a first policy gate: an action that publishes or spends waits for a person's approval through the API. The dashboard decides them — the Approvals screen, a held action in a chat's research card, and the notification bell telling the person wherever they are when one waits. The next step is a few agents, tested together with the orchestrator's chat turn, whose read tools answer over their real runs and proposals. Budgets, the content filter and risk levels still come before an agent that publishes for real. The first is the writer, designed in the design report (section "Writer: From an Approved Profile to an Approved Post", figure `fig_writer`) and not built: it plans each post as structured output (angle, features, whether it needs research or an image), drafts the text from the approved profile with no tools, checks it with code rules and a critic model, asks the researcher and the creative studio for what it needs, and proposes the post through the gate, publishing in dry-run first. Its first version is text only, which needs nothing that is not built. The researcher (section "Researcher", figure `fig_researcher`) is built in its first form: it answers questions from public pages, read only by a reader node with no tools, and stores a report of sourced findings, started through the API or the chat and shown in the dashboard's Research screens (see [The researcher](#the-researcher)); no agent asks it for findings yet. The report now also defines its terms (agent, run, graph, workflow, role, action, tool, playbook) and lists the agents with the roles and actions of each. All three kinds of action it names are built: the ordinary one, an action that starts another agent's run (the design's "start a run"), and one that runs another agent as a child workflow and waits for its result ("run and wait"), the last two exercised by the test agent, with the researcher the first target they were designed for. The creative studio also needs the gate's budget ledger and automatic small spends before it can be built. The orchestrator is designed as a supervisor with two halves (section "Two halves: the chat turn and the task", figure `fig_task`). The chat turn is built in its first form: it answers one message about one project through read tools and can start a research run through its one request action, in memory, with its named chats stored, served by the API and shown in the project's sidebar and chat screens of the dashboard (see [The orchestrator chat](#the-orchestrator-chat)). The chat shows a turn's steps and a research run's progress live, and when a research run the chat started has ended, one follow-up turn in the worker explains it in the thread (see [Chat events and the follow-up turn](#chat-events-and-the-follow-up-turn)); that turn stands in for the task's `report` until the task is built. Storing a directive and starting other kinds of run come after the agents. Its chat is designed with as many threads as people start, kept until deleted (section "Chat threads", figure `fig_chat`): a task will write everything it does into the thread it started from (its plan, steps, proposals, follow-ups, questions and report), and notifications will link to those messages. The task — a durable run of its own that plans the steps of a request needing several agents, has a plan that can spend approved by a person, starts the agents' runs, reviews each result and reports at the end — is not built. It delegates and never approves; scheduled work and the dashboard start agents without it. The golden-repository evaluation runs with one command and has scored one run on one case. Next: more golden cases across stacks (mobile, CLI, library), labels reviewed by a person, and several runs per case, so that the analyzer's quality, and the free model's, can be stated. Whether a proposed strategy belongs to Phase 1 is open: the roadmap caption mentions it, the phase description does not.
