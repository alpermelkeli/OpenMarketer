1 · Brieffrom a person in the dashboard, later from the planner, the repository watcher or the orchestrator: the platform, the goal (introduce the product, announce a live feature, or an angle in a person's own words) and the number of variants
2 · Prepare code, no modelpin the approved profile version for the whole run and build the writing context from it: live features only, with their evidence; voice, audience, do-not-mention; the platform's rules. A brief that names a feature that is not live is refused here.
3 · Draft writerwrites the variants from the writing context alone, with no tools. Each variant is structured: its text, its angle, and the claims it makes, each claim naming the features it rests on.
Never in the writer's prompt
  • repository files, comments, issues
  • web pages or anyone's messages
  • features that are not live
  • credentials; it has no tools to call
4 · Check code first, then a different model
Code rules hard
  • length as the platform counts it
  • no do-not-mention term
  • every claim names a live feature of the context
  • no link, no @mention; hashtag limit
  • numbers that are not in the profile are flagged
Critic criticreads each variant against the writing context: brand voice, facts, platform fit, and risky claims (legal, medical, financial, comparisons), which block a variant. Returns a structured report per variant with severity and edit suggestions, and ranks the variants that pass.

5 · Propose action publish_posteffect publishes, so the policy gate holds it as a proposal: the best variant, the others as alternatives, its angle, its claims with their evidence, both reports and the profile version
Revise back to Draftthe writer gets the findings, or a person's note, and rewrites the failing variants. Rounds and cost are limited; at the limit the best variant that keeps every code rule and makes no risky claim is proposed, marked as not passing the critic; if there is none, the run ends failed.
