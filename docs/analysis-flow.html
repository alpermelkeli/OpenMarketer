How a repository is analysed

One analysis run, from the click in the dashboard to a draft Product Profile waiting for review. Each step names the file and the function that does it. Paths under core/ are packages/core/src/openmarketer_core/, paths under worker/ are apps/worker/src/openmarketer_worker/.

Dashboard (Next.js) API (FastAPI) Temporal workflow Worker activity Core use case Run state in PostgreSQL: queued running succeeded failed

1 · The request — dashboard and API; nothing is cloned and no model is called here

1

A person starts the analysis

  • apps/web/src/components/analyses/analyses-screen.tsx
  • apps/web/src/lib/api/analyses.ts
  • POST /v1/projects/{id}/analyses (startAnalysis)

The browser reaches the API only through the dashboard's own proxy route.

2

The run is stored first

  • apps/api/…/routes/analyses.py start()
  • core/repository_analysis/request.py request_analysis()
  • → db/projects.py get_project()
  • → repository_analysis/intake/git.py remote_repository_url() https only
  • → db/analysis_runs.py request_analysis_run()

Run is queued. A project with an unfinished run answers 409.

3

Its workflow is started

  • apps/api/…/temporal_workflows.py TemporalAnalysisWorkflows.start()
  • core/repository_analysis/workflow_contract.py analysis_workflow_id(), AnalyzeRepositoryInput, ANALYSIS_TASK_QUEUE

Temporal gets three identifiers (workspace, project, run) and nothing else. If it cannot be reached: mark_run_failed(), answer 503.

202 with the run · the dashboard polls it every 2 s · a worker takes the workflow

2 · The workflow — worker/repository_analyzer/workflow.py · AnalyzeRepository.run() orders three activities and decides nothing else

4

Activity start_run: the run is picked up

  • worker/repository_analyzer/activities.py AnalysisActivities.start_run() → core/db/analysis_runs.py mark_run_started()

Run is running. Returns the AnalysisPolicy (time limits, attempts) the workflow uses for the next activity.

5

Activity analyse_and_store: one attempt at the analysis

  • worker/repository_analyzer/activities.py AnalysisActivities.analyse_and_store() runs _analyse_and_store() in a thread and sends a heartbeat every 20 s

5aHold the run's checkpoints

  • CheckpointAccess.of_attempt(run_thread_id(run_id))
  • → core/graph_checkpoints/postgres.py run_checkpoints()

The thread is named analysis-run:<run id> (core/db/analysis_runs.py). One attempt per run at a time (advisory lock); while an earlier attempt still runs, this one is refused and retried.

5bRead the run and its repository

  • _repository_to_analyse() → analysis_run(), get_project(), remote_repository_url()

Already succeeded → nothing to do. The URL comes from the database, never from Temporal.

5cAnalyse — core/repository_analysis/pipeline.py analyze_repository(), called through worker/repository_analyzer/wiring.py analysis_with_configured_models(). Paths in the three boxes are under core/repository_analysis/

Intake

  • intake/__init__.py run_intake()
  • → intake/git.py clone()
  • → intake/secrets.py scan_and_redact()

Clone into a temporary folder; a token goes only to its own host. Secrets are redacted; files are read only through RepoFiles.

Extractors

  • extraction.py run_extractors()
  • plugins in packages/extractors

Deterministic facts from manifests (package.json, Gradle, pyproject …) as hints for the agent.

Analyzer agent (LangGraph)

  • analyzer_agent/graph.py analyze()
  • → analyzer_agent/rules.py resumption()
  • loop call_model ⇄ run_tools:
  • · core/llm.py RouterChatModel.chat()
  • · rules.py run_tool_calls() → tools.py RepoTools
  • · submit → verify() / repair()

A checkpoint is stored after every step. Starts fresh, continues, starts over (new commit) or returns a finished result.

a profile was accepted
5d

Store the draft, finish the run

  • _store() — one transaction:
  • → core/db/evidence_store.py save_analysis_of_project()
  • → core/db/analysis_runs.py mark_run_succeeded()
  • _forget_checkpoints() → core/graph_checkpoints/postgres.py forget_checkpoints()

Run is succeeded with snapshot, evidence and profile version 1 as a draft.

the attempt failed
!

An ApplicationError with a type from steps.py

  • ModelUnavailable, DatabaseUnavailable, AttemptStillRunning, Unexpected, a time limit, a lost heartbeat
Temporal retries: up to 5 attempts, waiting 1, 2, 4 and 8 minutes (policy.py). The next attempt repeats step 5 and continues from the checkpoints.
  • AnalysisFailed, RunUnavailable, attempts used up, cancellation
Not retried: the workflow goes to step 6.
only when steps 4 or 5 ended without a result
6

Activity record_failure: the reason is written on the run

  • worker/repository_analyzer/activities.py AnalysisActivities.record_failure() → core/db/analysis_runs.py mark_run_failed(), then _forget_checkpoints()

Run is failed with a message fit to show. It no longer blocks the project.

the next poll of the dashboard reads the run from the database

3 · What the person sees — apps/api/…/routes/analyses.py get() → core/db/analysis_runs.py analysis_run(); Temporal is not asked

7

succeeded → the profile review

The run links to the profile version it stored. A person reads the draft with its evidence and confidence, corrects it and approves it. Approval is always a human action.

7

failed → the reason, and a new start

The message holds nothing a repository host or a model provider wrote. A new analysis can be started at once.

Meanwhile, in every worker

Checkpoints that a run left behind (a process that died, a workflow that was terminated) are removed at start-up and every 10 minutes. The schedule knows no rule: it runs the cleanups the agents' wiring hands it. The analyzer's touches only threads named analysis-run:….

  • worker/main.py serve_until() → worker/checkpoint_cleanup.py keep_removing_leftover_checkpoints() runs each CheckpointCleanup
  • → worker/repository_analyzer/wiring.py cleanup_of_analysis_runs() → core/db/checkpoint_cleanup.py remove_checkpoints_of_analysis_runs()
