You own `apps/api` (package `openmarketer_api`). Read `AGENTS.md` first. `make api` runs `openmarketer_api.main:app_from_env`; `create_app` builds the same application without services, for tests and `make openapi`. What exists: projects (`routes/projects.py`: create, read one, list; a project response carries `latest_draft_version`, `latest_approved_version` and `unfinished_run_id` from `openmarketer_core.db.projects`), analyses (`routes/analyses.py`): the start route calls the use case `openmarketer_core.analysis_request.request_analysis`, which stores the run, commits and then starts the workflow, and the status and list routes read `openmarketer_core.db.analysis_runs`; the one port is `AnalysisWorkflows` (`analysis_workflows.py`, one async `start`), implemented by `temporal_workflows.py`, the only module that imports `temporalio`, which connects on first use. Routes are plain `def` functions run in worker threads; the workflow start reaches them as a plain function from `dependencies.py`. The API clones nothing, calls no model and reads no token. Profile review calls `openmarketer_core.db.profile_versions` directly (`routes/profiles.py`): latest draft, latest approved, one version by number, the list of versions without profiles (`ProfileVersionSummaryResponse`; `ProfileVersionResponse` is that plus `profile`), edit and approve. Versions are named by number, with `edited_from_version` and `commit_sha`; no response carries a row id of a version or a snapshot. Then local-mode identity (`identity.py`) and the error table (`errors.py`): `Problem` is `code` and `message`, plus `existing_project_id` only on a 409 `project_already_exists` (left out otherwise, never null). The three lists (`listProjects`, `listAnalyses`, `listProfileVersions`) are paged alike through `pagination.py`: `limit` (1 to 100, default 50) and an opaque `cursor`, items under `projects`, `runs` or `versions`, and `next_cursor` (null on the last page). The stores do the keyset query and return a `Page` with `next_before` (`openmarketer_core.db.pages`); the API only writes that position as text and reads it back, and answers a cursor it did not write with 422. A new list uses the same two parameters and the same response shape. A project of another workspace is answered like a missing one: `project_not_found` for a project and the lists under it, `profile_not_found` for a version. After changing a route or a model run `make openapi` and commit `apps/api/openapi.json`.

How to work
- The API is a thin layer. Domain logic lives in `packages/core`; an endpoint validates input, calls core, and maps the result. If you are writing business rules in a route, move them to core.
- Request and response bodies are Pydantic models with `extra="forbid"`. Reuse `openmarketer_core.profile.ProductProfile` for profile content instead of redefining it.
- The OpenAPI document is the contract: the dashboard generates its types from it with `openapi-typescript`. Give every route a response model and a stable operation id, and say so when a change breaks the contract.
- Every route is scoped to a workspace. Approving a profile is an authenticated user action and is recorded with who and when; no route lets a model output approve anything.
- Long work (cloning and analysing a repository) does not run inside a request. Start it and return something the client can poll.
- Errors are explicit: domain errors map to 4xx with a readable message, and nothing leaks stack traces, file system paths outside the repository, or credentials.
- Tests use FastAPI's test client with dependencies overridden; no network, no real model calls.
- Layering: this is an entry point. A route parses and authorises, calls exactly one use case from core, and maps the result or the domain error to a response. Dependencies (session, chat model, current user) are built in FastAPI dependencies and passed in; routes import no SQLAlchemy and no agent code.
- Readability: one router module per resource, request and response models next to the routes that use them, and handlers short enough to read without scrolling.

Done means `make check` passes and new routes have tests for the success path and the main failure paths.
