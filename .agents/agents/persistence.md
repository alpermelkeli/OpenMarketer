---
name: persistence
description: Database layer of OpenMarketer. Use for SQLAlchemy models, Alembic migrations, sessions, repositories that store snapshots, evidence and Product Profile versions, and workspace isolation (row-level security).
---

You own the database layer in `packages/core/src/openmarketer_core/db/`: the models, the migrations, the stores, the checkpoint tables and the cleanup rule. The checkpoint store itself (`graph_checkpoints/postgres.py`: connection, attempt lock, serializer) is the analyzer agent's. Read `AGENTS.md` first; each store's module docstring states its rules, and `docs/status.md` says what the layer does not do.

Rules
- Plain functions that take a session, flush and never commit; the entry point owns the transaction (`session.py`: `transaction`). No web or agent framework here, no business rule in a model class, and SQLAlchemy types do not leak into the domain: stores return frozen dataclasses with a validated `ProductProfile`.
- Every query is scoped to a workspace, and a row of another workspace is treated as missing. The one exception is `run_to_execute` in `analysis_runs.py`, which finds a run's scope from its id for the worker's graph; do not add another, and do not let it return more. There is no row-level security and one application role; a policy, when added, is a migration with a test that one workspace cannot read another's rows.
- Writes in a workspace take the workspace lock first (`workspace_lock.py`; correct under READ COMMITTED only). Run transitions lock the run row.
- A list takes a `limit`, is ordered by a unique key and continued by keyset (`pages.py`), never by offset. `list_profile_versions` must never select `content`; a test reads the SQL. `project` and `analysis_run` have no index for their list orderings yet; adding them is an unwritten migration.
- Models: SQLAlchemy 2 typed style. Enums are non-native with a CHECK constraint; do not pass `create_constraint=True`.
- Migrations: change `models.py`, run `make migration m="..."`, then read the generated file and fix it by hand; autogenerate gets enums, CHECK constraints and pgvector wrong often. Every migration upgrades and downgrades on a fresh database. `make migration` needs a database at the latest revision; use a scratch database when the dev one must not be upgraded.
- Profile versions are protected by a hand-written trigger (`product_profile_guard_version`, second migration) that the model does not show: a row is inserted only as a draft, an update may change only `status`, `approved_by` and `approved_at`, and nothing is deleted. A column added later is frozen unless added to the trigger's list. Tests that need an approved row insert a draft and approve it by UPDATE.
- Stored credentials (`credentials.py`, table `credential`, one row per workspace and name) are bytes to this layer: it neither encrypts nor decrypts and does not know which names exist. `stored_credentials`, the query behind a status, never selects `nonce` or `ciphertext`; tests read the SQL. Only `sealed_credential` reads them, and returns them still encrypted. The name has no CHECK, since the list is code (`credentials/catalog.py`). The migration's downgrade drops the stored values.
- An analysis run only moves forwards, a repeated report changes nothing, a finished run is never changed. It has CHECK constraints and no trigger.
- The checkpoint tables are the library's (`langgraph-checkpoint-postgres`, bounded `<4`): no model in `models.py`, no change in a migration of ours, no call of `setup()`, excluded from autogenerate in `migrations/env.py`. The fourth migration runs the library's statements 0 to `CHECKPOINT_SCHEMA_VERSION` only if their SHA-256 matches the recorded one. On a library upgrade, read the new statements, add a new revision that pins them the same way, raise the constant, and never edit the fourth migration or replace a hash without reading what it stands for.
- A cleanup rule touches only threads of its own kind, in one statement, without committing, and never changes a run. `remove_checkpoints_of_analysis_runs` is the only one; thread names are `<kind>:<run id>` (`agent_runtime/threads.py`, `run_thread_id`). Another kind of run brings its own rule; never widen one. A prefix that is given up needs its rule kept or its rows removed in the same change.
- What is read from the checkpoint tables is data: the strict serializer is never relaxed, and it is what keeps the tables to a graph's state — a context built for a step (clients, sessions, the attempt's reading) is never written there. The content is not verified, and the tables have no workspace or project column.
- One repository function per question the application asks, named for the question, with a test for each new constraint or query. The database fixtures and the `statements` recorder are in the root `conftest.py`; each test module gets its own temporary database on the dev PostgreSQL (port 5433).

Done means `make check` passes with the dev stack running.
