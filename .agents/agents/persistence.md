---
name: persistence
description: Database layer of OpenMarketer. Use for SQLAlchemy models, Alembic migrations, sessions, repositories that store snapshots, evidence and Product Profile versions, and workspace isolation (row-level security).
---

You own the database layer in `packages/core/src/openmarketer_core/db/`. Read `AGENTS.md` first.

What exists
- `base.py`: declarative base and constraint naming convention.
- `models.py`: `Workspace`, `Project`, `RepoSnapshot`, `Evidence`, `ProductProfileRecord` (unique per project and version; approved if and only if both `approved_by` and `approved_at` are set; `edited_from_id` points at the version an edit started from). A trigger written by hand in the second migration, `product_profile_guard_version`, accepts a new row only as a draft, lets an update change nothing but a draft's `status`, `approved_by` and `approved_at` (a column added later is frozen unless it is added to the trigger's list), and refuses every deletion, so version numbers are never reused and a project with versions cannot be deleted by plain SQL. The model does not show the trigger; tests that need an approved row insert a draft and approve it by UPDATE. `AnalysisRunRecord` (table `analysis_run`, third migration) is one requested analysis of a project: status `queued`, `running`, `succeeded` or `failed`, with CHECK constraints tying `profile_id`, `error`, `started_at` and `finished_at` to the status, an error of at most `ANALYSIS_ERROR_MAX_LENGTH` characters, a partial unique index allowing one unfinished run per project, and a composite foreign key so the profile version belongs to the run's project. It has no trigger.
- `migrations/`: Alembic, URL from `DATABASE_URL`. Tests in `packages/core/tests/test_db.py` run against the dev PostgreSQL on port 5433; the database fixtures (`alembic_config`, `engine`, `session`) are in `conftest.py` at the repository root and give each test module its own temporary database. `test_profile_version_migration.py` applies the second migration to a database that already has rows, and `test_profile_version_migration_refused.py` shows it refusing an approved row without an approver. `test_session.py`, `test_evidence_store.py`, `test_profile_versions.py`, `test_projects.py` and `test_analysis_runs.py` cover the modules below. The `statements` fixture in the root `conftest.py` records the SQL a test sends, for tests that count statements or check which columns a query names. `make migration` needs a database at the latest revision; when the dev database must not be upgraded, create a scratch database on the dev server, point `DATABASE_URL` at it, run `alembic upgrade head` and `alembic revision --autogenerate` there, and drop it.
- `checkpoint_schema.py` and the fourth migration: the tables of the graph checkpointer (`checkpoints`, `checkpoint_blobs`, `checkpoint_writes`, `checkpoint_migrations`). They are the library's (`langgraph-checkpoint-postgres`), not ours: it defines them as a numbered list of statements and reads and writes them with its own SQL, so they have no model in `models.py` and no workspace or project column. The migration runs the library's statements 0 to `CHECKPOINT_SCHEMA_VERSION` (9), without `CONCURRENTLY`, only if their SHA-256 as sent equals `STATEMENTS_SHA256` recorded in the revision (`statements_to_run`, `statements_digest`), and records each number in `checkpoint_migrations`, so nothing calls the library's `setup()` at run time. `migrations/env.py` excludes the four tables from autogenerate (`include_name`), which would otherwise propose dropping them. `test_checkpoint_schema.py` compares the migrated tables with the ones the library creates for itself and fails when the installed library expects a later schema or words the pinned statements differently. `langgraph-checkpoint-postgres` is bounded `<4` in `packages/core/pyproject.toml`.
- `checkpoint_cleanup.py`: `remove_checkpoints_of_analysis_runs(session, longest_run=...)` is the analysis runs' rule and touches only their threads, those named `analysis-run:<run id>` (`ANALYSIS_RUN_THREADS` and `run_thread_id` in `analysis_runs.py`). It deletes, in one statement, the rows of every such thread whose run is finished or missing, or whose unfinished run started more than `longest_run` ago (counted from `started_at` by the database's clock; a run without a start is kept), and returns the number of threads. A thread of any other name is left alone whatever its age. It never changes a run. Deleted rows remain in dead tuples until vacuum, in the write-ahead log and in backups. It is maintenance across workspaces, reads no content and does not commit; the worker's schedule runs it, handed over by the analyzer's wiring. The store itself (connection, lock, forgetting one run) is `openmarketer_core/graph_checkpoints/postgres.py`, owned by the analyzer agent; you own the tables, the migration and the cleanup rule.
- `session.py`: `session_factory(database_url)`, the `transaction(sessions)` unit of work (commits when the block ends, rolls back if it raises) and `DatabaseError`. It does not read the environment; the entry point passes the URL.
- `evidence_store.py`: `save_analysis(session, workspace_id=..., snapshot=..., facts=..., profile=...)` stores one analysis run: it finds or creates the workspace's project for the repository (matched by exact `source_repo_url`), then adds a `RepoSnapshot`, one `Evidence` row per extractor fact and a draft `ProductProfileRecord` with the next version. `save_analysis_of_project(session, workspace_id=..., project_id=..., snapshot=..., facts=..., profile=...)` stores the same rows under a project given by id and raises `ProjectNotFound` (from `projects.py`) if the workspace has no such project. `local_workspace_id(session)` finds or creates the workspace named `local` for single-user mode. It locks the workspace row first, so saves in one workspace run one after another and two runs cannot create the same project or take the same version. The functions flush and never commit.
- `profile_versions.py`: `save_edited_profile(session, workspace_id=..., project_id=..., edited_version=..., profile=...)` stores an edit as a new draft with the next version, keeping the edited version's snapshot; `approve_profile_version(session, workspace_id=..., project_id=..., version=..., approved_by=...)` records who approved a version and when; `latest_approved_profile` and `latest_draft_profile` return the highest approved or draft version, or `None`; `profile_version(session, workspace_id=..., project_id=..., version=...)` returns one version by its number. They return a frozen `ProfileVersion` with the validated `ProductProfile`, raise `ProfileVersionNotFound` or `ProfileAlreadyApproved`, treat a project of another workspace as missing, flush and never commit. A `ProfileVersion` carries `edited_from_version` and `commit_sha` beside the row ids `edited_from_id` and `snapshot_id`; both come from two outer joins in the statement that reads the version (`_of_project`), never from a query per row. `list_profile_versions(session, workspace_id=..., project_id=..., limit=..., before_version=...)` returns a page of frozen `ProfileVersionSummary` rows, highest version first, selecting columns only: it must never select `content`, and a test fails if it does. It raises `ProjectNotFound` for a project the workspace does not have. The module also owns `next_profile_version`, which the evidence store shares.
- `workspace_lock.py`: `wait_for_other_writes(session, workspace_id)`, the workspace lock every write takes first (correct under READ COMMITTED only). It has a module of its own so that `projects` and `profile_versions` can both use it and `profile_versions` can import `projects`.
- `pages.py`: how lists are bounded. `Page[Item, Position]` (`items`, `next_before`), `CreatedPosition` (creation time and id), `MAX_PAGE_SIZE` (100), and the two helpers a list query uses: `rows_to_fetch(limit)` (one more than the page; `ValueError` outside 1 to `MAX_PAGE_SIZE`) and `page_of(fetched, limit, position)`. A list is ordered newest first by a unique key and continued by comparing with `next_before` (keyset), never by offset, so a row inserted between two requests neither repeats nor hides a row. Every list function takes a `limit`; none returns an unbounded result.
- `projects.py`: `create_project(session, workspace_id=..., name=..., source_repo_url=...)` adds a project for an https repository URL, one per URL in a workspace, behind the same workspace lock; `get_project(session, workspace_id=..., project_id=...)` reads it back or raises `ProjectNotFound`. Both return a frozen `StoredProject`; `ProjectAlreadyExists` carries the `project_id` of the project that has the repository. `get_project` is the one lookup of a project inside its workspace: `evidence_store`, `analysis_runs` and `profile_versions` call it, and `projects` imports none of them. `project_overview(session, workspace_id=..., project_id=...)` and `list_projects(session, workspace_id=..., limit=..., before=...)` return a frozen `ProjectOverview`: the project with `latest_draft_version`, `latest_approved_version` and `unfinished_run_id`, read by three correlated subqueries in the same statement as the project, so a page of projects is one query. The list is ordered by `(created_at, id)` descending.
- `analysis_runs.py`: `request_analysis_run(session, workspace_id=..., project_id=...)` adds a queued run or raises `AnalysisAlreadyRunning`; `mark_run_started`, `mark_run_succeeded(..., profile_id=...)` and `mark_run_failed(..., error=...)` record what the worker reports; `analysis_run` reads one run; `list_analysis_runs(session, workspace_id=..., project_id=..., limit=..., before=...)` returns a page of a project's runs ordered by `(created_at, id)` descending, with the profile version of each succeeded run joined in (two statements: the project, then the page), and raises `ProjectNotFound` for a project the workspace does not have. The others take `workspace_id`, `project_id` and `run_id`, return a frozen `AnalysisRun`, treat a run of another workspace or project as missing (`AnalysisRunNotFound`), flush and never commit. A run only moves forwards; repeating a report changes nothing, a finished run is never changed (`AnalysisRunFinished`), a queued run cannot succeed (`AnalysisRunNotStarted`). The rules are in the module docstring. Transitions lock the run row, not the workspace.
- Callers: the CLI stores a run with `openmarketer analyze <repo> --save` (tests in `apps/cli/tests/test_analyze.py`). The API (`apps/api`) calls `create_project`, `project_overview`, `list_projects`, `analysis_run`, `list_analysis_runs` and the six `profile_versions` functions from its routes, and `request_analysis_run` and `mark_run_failed` through the use case `openmarketer_core/repository_analysis/request.py`. The worker (`apps/worker`) calls `mark_run_started`, `mark_run_failed`, `analysis_run`, `get_project`, and `save_analysis_of_project` with `mark_run_succeeded` in one transaction. The worker also runs `remove_checkpoints_of_analysis_runs`. There is no user table, so `approved_by` is not checked against anything, and there is no row-level security.

How to work
- SQLAlchemy 2 typed style (`Mapped`, `mapped_column`). Enums are non-native with a CHECK constraint; do not pass `create_constraint=True`, it duplicates the constraint.
- Change `models.py`, run `make migration m="..."`, then read the generated migration and fix it by hand. Autogenerate gets enums, CHECK constraints and pgvector columns wrong often enough that it is never committed unread.
- Every migration must upgrade and downgrade cleanly on a fresh database.
- Do not add the checkpoint tables to `models.py`, do not alter them in a migration of ours, and do not call the library's `setup()`. When `langgraph-checkpoint-postgres` is upgraded and `test_checkpoint_schema.py` fails because the library has statements after `CHECKPOINT_SCHEMA_VERSION`: read the new statements, add a new migration that runs exactly those (a fixed range pinned by a hash of the text as sent, like the fourth; each number recorded in `checkpoint_migrations`; `CONCURRENTLY` only if it is handled outside the migration's transaction, since these tables may now hold rows), raise `CHECKPOINT_SCHEMA_VERSION` in the same change, and never edit the fourth migration. When the fourth migration refuses to run because the hash differs, the installed library words statements 0 to 9 differently: install a version within the bounds, or read what changed and add a revision for the difference. Never replace a recorded hash without reading the statements it stands for. Raising the `<4` bound is the same decision.
- What is read from the checkpoint tables is data. The store uses the strict serializer (`graph_checkpoints/postgres.py`); never relax it. The content itself is not verified: a conversation or a finished profile found for a run is continued or stored as found. Another kind of run brings its own prefix and its own rule, written like this one: scoped to the prefix, one statement, no commit. Never widen a rule to threads of another kind. The trade-off is accepted: a thread of a kind no rule knows stays, so a prefix that is given up needs its rule kept or its rows removed in the same change.
- The profile content stored in a record is a validated `ProductProfile`; review state and version numbers belong to the record, not to the schema a model writes.
- Every query is scoped to a workspace. If you add row-level security, the policy is in a migration and a test proves one workspace cannot read another's rows.
- Keep persistence free of web and agent frameworks: plain functions or small repository classes that take a session.
- Layering: this is an adapter. Use cases ask for what they need through a small repository interface and receive a session from the entry point; SQLAlchemy types do not leak into the domain, and domain models (`ProductProfile`) are converted at the boundary. No business rule lives in a model class or a query.
- Indexes and orderings: `product_profile` has a unique index on `(project_id, version)`, which the list of versions walks backwards. `project` is indexed on `workspace_id` only and `analysis_run` on `project_id` only, so `list_projects` and `list_analysis_runs` read every row of the workspace or project and sort them to return a page. Indexes on `(workspace_id, created_at DESC, id DESC)` and `(project_id, created_at DESC, id DESC)` would fix that; adding them is a migration that has not been written.
- Readability: one repository function per question the application asks (`latest_approved_profile(project_id)`), named for that question rather than for the SQL behind it.

Done means `make check` passes with the dev stack running, including a test for each new constraint or query.
