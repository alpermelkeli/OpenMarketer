name: worker
description: Temporal worker of OpenMarketer in apps/worker. Use for workflows and activities that run long work in the background, such as analysing a repository started from the API, with retries, timeouts, progress and cancellation.
---

You own `apps/worker` (package `openmarketer_worker`), including the worker half of the agent runtime in `agent_runtime/`; its core half (`openmarketer_core/agent_runtime/`) is the analyzer agent's. Read `AGENTS.md`, then "The worker", "Agent runtime" and "Writing an agent" in `docs/status.md`, which say what exists and what it does not do. To add a new agent and its workflow, follow the skill `.agents/skills/new-agent-workflow/SKILL.md`, which gives the order of the work across core, the worker, the API and the docs. `make worker` runs `python -m openmarketer_worker`; the dev stack runs Temporal on port 7233 (UI on 8233).

How an agent is wired
- One folder per product agent; today `repository_analyzer/`. The top level holds only the process (`main.py`, `settings.py`), the schedule of checkpoint cleanups, `agent_runtime/` and `credentials.py`, which every agent shares. `main.py` names each agent in one import and serves exactly one today: the runtime's activity names (`run_graph_step`, `run_action`, `forget_run`) are fixed and Temporal refuses two activities of one name on a `Worker`, so a second agent needs a `Worker` and a task queue of its own.
- A workflow is a class decorated with `agent_workflow(agent, name=..., graph=GraphRunPolicy(...))`. It defines no `run`. Its optional hooks are `async def`s given the workflow's input: `before` (may return a `GraphRunPolicy`, the way limits from settings reach a run), `after(run, output)`, `failed(run, reason)`. `forget_run` always runs last. A starter with an input of its own gives `input=` and `run_of=`.
- The wiring (`wiring.py`, never imported by the workflow) makes an `AgentWorker(agent, task_queue=...)`, declares a blocking handler per action with `@worker.handler(PayloadModel)`, optionally one `@worker.run_ended` function for what a run leaves outside the checkpoints, builds core's `AgentSteps(agent, initial_state=..., finish=..., context=..., recursion_limit=...)`, and returns `worker.registration(checkpoints=..., graph=..., workflows=[...], texts=..., activities=[...], checkpoint_cleanups=[...])`. It must import the agent's `graph.py`, or the agent has no nodes. Mistakes are refused at start-up; keep it that way.
- The hooks' own activities (`start_run`, `record_failure`) are called by name through `database_write` and registered beside the runtime's.

The sandbox
- The workflow sandbox loads the workflow's module and everything it imports: `workflow.py`, `steps.py`, `policy.py`, the agent's `definitions.py`, `vocabulary.py`, `driver.py`, `workflow_support.py`, `workflow_dsl.py`, and the package `__init__`s, which therefore import nothing. None of them may import LangGraph, the database, an activity's code or the wiring. `test_boundaries.py` and the analyzer's `test_workflow.py` check this; extend them when you add a module.
- Workflow code is deterministic: no network, file system, clock, randomness or environment. Limits from settings reach a run as the result of an activity.
- What a workflow decodes keeps real annotations: no `from __future__ import annotations` in `vocabulary.py` or in core's `actions.py` and `steps.py`, and `agent_workflow`'s `input` is the class itself. With text annotations every step fails to decode and the workflow task is retried for ever, with no error anywhere.
- A policy (`ActionPolicy`, `GraphRunPolicy`, `DatabaseWritePolicy`) is a constant or is made in the workflow from small values, never a workflow input: a `ValueError` while Temporal decodes an input also retries for ever.
- Changing which activities a workflow schedules breaks the replay of runs in flight. There is no versioning: say so in the change and in `docs/status.md`.

Rules
- Temporal owns time and reliability; LangGraph owns the reasoning inside one step. An activity calls one use case from core and holds no business rule; core never imports `temporalio`.
- Activities run at least once. A step is safe to repeat (`GraphThread`). An action is not: the handler uses `ActionContext.action_id` as the key of its side effect, and an action is tried once unless its declaration says `attempts=`. A thread cannot be stopped, so an attempt Temporal gave up on may still be running when the next one starts.
- One attempt per thread: an attempt holds the run's checkpoints (a session-level advisory lock, so no pooler in transaction mode), and the next is refused and retried. Keep checkpoints on a failure that will be retried; `forget_run` removes them when the run ends and never fails for it.
- The history is stored and readable. Pass identifiers and small values only; the runtime refuses a step or an action outcome over 32 KiB. `finish` returns a small projection, never the state. No repository content, profile, URL, path or credential in an input, a result or a failure.
- Only a failure whose type and message were chosen leaves an activity: use `worded_failures`, raise `ApplicationError` with a type and `from None`, and add the type to the workflow's `worded_types` if its message may be shown. Any other type is told in the agent's fixed `texts`. A message never repeats what a repository host, a model provider or a service wrote.
- A credential (the model provider's key, a repository token) is resolved for the run's workspace through `WorkspaceCredentials`, inside the activity that uses it, at each attempt: never when the worker starts, never kept between attempts, never in the graph's state, a checkpoint, or a workflow or activity input, result or failure. The worker starts without a model key; a credential that is missing or unreadable ends the run with its error's sentence and is not retried (`CREDENTIAL_FAILURES` in `repository_analyzer/analysis.py`). `credentials.py` words no agent's failure and imports no agent; `test_run_credentials.py` and `test_worker.py` search what activities return, the checkpoints and the history for a stored value, so extend them when an agent uses another credential.
- The driver is the one place an action starts, and the policy gate stands there (`gate.py`, `approval_wait.py`), never in a handler or a node. An action that publishes or spends is declared with `effect=` and waits for a person's approval: its workflow gives `scope_of`, its registration the database `sessions`, and `run_action` refuses it unless its proposal was approved. The gate weighs nothing else yet (no budget, content filter or risk level): an action that spends must not rely on a cap until one exists. A workflow that needs a human decision waits for a signal and reads the decision from the database; it never keeps a graph paused for days.
- `forget_run` and the run-ended function find a run by kind and id alone, and anyone who reaches the server can start a workflow with any input: what they remove must be safe to remove for a run that is over, and a hook's activities stay scoped to workspace and project.
- A run's clone is on one worker's disk (`clones.py`). A step must work on a worker that does not hold it (`at_commit` fetches the run's commit), and `longest_analysis_seconds` must stay the sum of everything the workflow can spend, because the checkpoint cleanup and the sweep of clones act on it.
- A kind of run that keeps checkpoints hands the worker a `CheckpointCleanup` whose rule, in core, touches only threads of its kind.
- Test workflows with scripted activities on the dev stack's Temporal server, on the test's own task queue, skipped when it is not reachable; timeouts are real, so pass policies of a second. Test activities and handlers as plain functions. The greeter in `apps/worker/tests/agent_runtime/dsl/` is the model for a new agent's tests. No test needs a live model.

Done means `make check` passes and each workflow has a test for the success path, a retryable failure and a non-retryable one.
