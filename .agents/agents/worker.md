---
name: worker
description: Temporal worker of OpenMarketer in apps/worker. Use for workflows and activities that run long work in the background, such as analysing a repository started from the API, with retries, timeouts, progress and cancellation.
---

You own `apps/worker` (package `openmarketer_worker`). Read `AGENTS.md` and the section "Agent graphs and durable workflows" of the design report first. `make worker` runs `python -m openmarketer_worker`, and the dev stack runs Temporal on port 7233 (UI on 8233).

What exists
- The package has one folder per product agent, so the top level does not grow as agents are added. Today there is one, `repository_analyzer/`; the paths below without a folder are in it. At the top level are only `main.py`, `settings.py`, `__main__.py`, `checkpoint_cleanup.py`, which is not an agent's because the checkpoint tables are shared by every graph, and `__init__.py` with `AgentRegistration` (task queue, workflows, activities, checkpoint cleanups): what an agent's wiring hands to the process. The workflow sandbox loads `__init__.py`, so at run time it imports only the standard library.
- `workflow.py`: the `AnalyzeRepository` workflow. It calls three activities by name: `start_run`, `analyse_and_store`, and `record_failure` whenever one of the first two ends without a result (also on a timeout and on cancellation). It imports only `steps.py`, `policy.py` and the contract from core, which the workflow sandbox can load.
- `openmarketer_core/repository_analysis/workflow_contract.py` (in core, no `temporalio`): what the API and the worker share. Workflow name, task queue, `analysis_workflow_id(run_id)` and `AnalyzeRepositoryInput` (workspace, project and run identifiers, nothing else).
- `steps.py`: activity names, the `RunFailure` input, the failure types (`NOT_RETRIED` lists those that end a run at once) and the fixed messages. `policy.py`: every timeout and retry number, with the reasons. `AnalysisPolicy` is configuration and reaches the workflow as the result of `start_run`.
- `activities.py`: `AnalysisActivities(sessions, analyse, checkpoints, policy)`, where `checkpoints` is a `CheckpointAccess` (`of_attempt`, `forget`) built in `wiring.py` from core's `run_checkpoints` and `forget_checkpoints`. `analyse_and_store` takes the run's checkpoints for the attempt before it reads the run, so the analyzer continues from what an earlier attempt stored; it is refused with the retried failure `ATTEMPT_STILL_RUNNING` while an earlier attempt still holds them. The checkpoints are forgotten after the profile is stored and when `record_failure` records the failure. Each activity calls core and raises only `ApplicationError`s with a type from `steps.py` and a message that may be stored and shown; the original error is logged and not attached as a cause. `analyse_and_store` runs the blocking work in a thread and sends heartbeats.
- `settings.py` (in the folder): `RepositoryAnalyzerSettings`, which fills the policy from `ANALYSIS_TIMEOUT_MINUTES` and `ANALYSIS_MAX_ATTEMPTS`.
- Top-level `settings.py`: the process's own settings only (`DATABASE_URL`, the Temporal address and namespace, `WORKER_MAX_CONCURRENT_ACTIVITIES`), with `SettingsError` and `positive_number`, which the agents' settings use. Activities read no environment.
- `wiring.py`: sets the analyzer up for the installation when the worker starts. `repository_analyzer(environ, sessions, database_url)` builds what an analysis depends on (the agent's settings, the model router, the extractors, the repository tokens, access to the runs' checkpoints) and returns an `AgentRegistration`; its parts are `registration`, `cleanup_of_analysis_runs`, `analysis_with_configured_models` and `checkpoints_in`. It holds no rule, does not connect to Temporal, and raises `SettingsError`, `ConfigError`, `IntakeError`, `DatabaseError` or `OSError`, which `main.py` words. The workflow never imports it.
- Top-level `main.py`: the process only. It reads the process's settings, builds the session factory, connects to Temporal, builds the `Worker` from the registration (`build_worker`), handles signals, serves with the cleanups (`serve_until`) and turns the start-up errors above into `StartupError`. It names the analyzer in one import.
- `checkpoint_cleanup.py` (top level): the schedule, and no rule; it imports none from core. It is given `CheckpointCleanup`s (a name for the runs in the log, and a function that removes within a session and returns of how many runs), and when the worker starts and every ten minutes (`CLEANUP_EVERY_SECONDS`, in the same module) runs each in a transaction of its own. One that fails is logged and does not stop the others, the schedule or the worker; with no cleanups it does nothing. The analyzer's cleanup comes from `wiring.cleanup_of_analysis_runs`: core's `remove_checkpoints_of_analysis_runs` with `longest_analysis_seconds(policy)` from the analyzer's `policy.py` as the time a run can last, so that the checkpoints of a run left `running` by a terminated or lost workflow go too (the run is not changed). A change to the attempts, timeouts or waits changes that bound through the function; keep it the sum of what the workflow can spend. The lock that keeps one attempt per thread is a session-level advisory lock, so the worker needs a direct or session-mode database connection, not a pooler in transaction mode.
- Tests: `apps/worker/tests` keeps `conftest.py`, `test_settings.py` (the process's settings), `test_checkpoint_cleanup.py` (the schedule, with made-up cleanups) and `test_worker.py` (workflow, real activities and PostgreSQL together, and the process). `apps/worker/tests/repository_analyzer/` has `test_activities.py` (activity environment and PostgreSQL, and the cleanup), `test_workflow.py` (the workflow with scripted activities), `test_policy.py`, `test_settings.py` (the agent's settings), `test_wiring.py` (what the wiring builds, registers and raises) and `test_checkpointed_analysis.py` (the activities with real git, gitleaks, the real graph and checkpoint store, and a scripted model: a retried attempt continues). `docs/status.md` lists what the worker does not do, including the failures that leave a run unfinished.

How to work
- Temporal owns time and reliability; LangGraph owns the reasoning inside one task. A workflow orchestrates; an activity does the work by calling one use case from core (`run_intake`, `analyze`, a persistence function).
- Workflow code must be deterministic: no network, file system, clock, randomness or environment access, and no imports that do those at module level. Everything with a side effect is an activity.
- Activities are retried, so make them idempotent. Writing a snapshot or a profile version twice must not create two; use a key derived from the workflow run.
- Checkpoints: keep a run's thread on a failure that will be retried, and forget it when the run ends, succeeded or failed. Forgetting must never fail an activity: the run's outcome is recorded by then, so log it and leave the rows to the cleanup. One attempt per thread: an attempt holds the run's checkpoints for as long as its thread works, even after Temporal has given up on it, and a second attempt is refused and retried, never allowed to write the same thread. Checkpoints hold repository content: they stay in the database and never enter an activity input, a result or a failure.
- Give every activity a start-to-close timeout and a retry policy chosen for its failure modes. A rejected profile or an exhausted budget is not retryable; a rate limit (HTTP 429) is, with backoff. An analysis gets five attempts because an attempt continues from checkpoints and repeats only the clone, the scan and the extractors; the reasons are in `policy.py`. Long activities send heartbeats so cancellation and worker crashes are noticed.
- Pass identifiers and small values between workflow and activities, never repository content, profiles in bulk, or credentials: workflow history is stored and visible in the Temporal UI. That includes failures: raise an `ApplicationError` with a chosen message and `from None`, because Temporal stores the message and every cause of whatever an activity raises (and, on its own, the stack trace: source files and lines, no values). A message must not repeat text written by a repository host or a model provider; core gives fixed sentences for those (`repository_analysis/intake/git.py`, `llm.py`) and logs the rest.
- A workflow that needs a human decision waits for a signal; it never keeps a graph paused for days.
- Layering: this is an entry point. Workflows and activities contain no business rules, and core never imports `temporalio`. Dependencies (session factory, chat model) are built when the worker starts and handed to the activities.
- Structure: one folder per product agent. Its workflow is in `workflow.py`, named for what it achieves (`AnalyzeRepository`), with its policy beside it in `policy.py`; there is no worker-wide policy module. The top-level `settings.py` holds nothing of an agent and never imports one; each agent reads its own settings in its folder. An agent's wiring is in its folder too (`wiring.py`, returning an `AgentRegistration`), and `main.py` holds only the process: it names each agent in one import and knows nothing else of it. A kind of run that keeps graph checkpoints names its threads with its own prefix and hands the worker a `CheckpointCleanup` whose rule, in core, touches only those threads.
- Readability: activity inputs and results are small dataclasses, not positional arguments.
- Test workflows with scripted activities against the dev stack's Temporal server, on a task queue of the test's own (the `temporal` and `task_queue` fixtures), and skip when it is not reachable. The time-skipping test environment downloads a server on first use, and tests use no network; timeouts in tests are therefore real, so pass a policy with timeouts of a second. Test activities as plain functions in `ActivityEnvironment`. No test needs a live model.

Done means `make check` passes and each workflow has a test for the success path, a retryable failure and a non-retryable one.
